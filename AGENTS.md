# diffalanche — agent guide

diffalanche is a local code-review tool for a folder that holds many independent git repositories: one merge-request-style review across all of them, comments as JSON on disk, a CLI for coding agents. Requirements are in [docs/SPEC.md](docs/SPEC.md); the UI design is in [docs/design/HANDOFF.md](docs/design/HANDOFF.md) with a working prototype next to it. Read the spec section that your task names before touching code.

Rules for every change:

- **The tool never writes to a reviewed repository.** No commits, index changes, resets, or file edits; git is read through the `git` binary only. The only writable location is the data directory.
- **Server and CLI code use only APIs shared by Node and Bun.** Runtime-specific calls (`Bun.*`, Node-only modules without a Bun counterpart) are not allowed outside build scripts and `src/server/runtime.ts` — the single module that chooses between Bun's server and the Node adapter ([ADR-008](docs/adr/adr-008-diff-rendering-verdict.md)). A second such module is a new decision, not a convenience.
- **The UI follows the handoff, not the prototype line by line.** Tokens, layout, and behaviour come from `docs/design/HANDOFF.md`; the diff itself is rendered by the chosen library, and the prototype's hand-drawn diff is only a layout reference.
- **A UI change starts with the Impeccable context loader.** Before editing anything under `src/ui`, run `~/.claude/skills/impeccable/scripts/impeccable context --target <file>` from the repository root and follow what it loads: `PRODUCT.md`, `DESIGN.md`, and the surface brief of the screen. Tokens and visual rules come from `DESIGN.md`, the handoff stays the source of layout and behaviour, and the two never disagree — a value that changes in `src/ui/tokens.css` changes in `DESIGN.md` in the same pass. Run the skill's `audit` and `polish` on the touched surface before reporting, and name in the result every finding the pass did not fix.
- **The spec states behaviour and contracts, not components** (DA-112). Section 5 of [docs/SPEC.md](docs/SPEC.md) says what the user and the agent can do; the on-disk format, the CLI and the budgets say it in numbers. A component name, a module path or a description of how today's build works belongs to the [reference](docs/reference/README.md) or to an ADR — in the spec it reads like a requirement and goes stale like an implementation. There is no gate for this: the section's only identifiers are contract values, so a check would pass anything that keeps its prose about internals out of backticks.
- **Performance budgets are a gate.** Section 6 of the spec is checked in CI on the synthetic review; a change that regresses it is not done.
- **A comment in code is at most two lines** ([ADR-011](docs/adr/adr-011-comment-length.md)). `//`, `/* */` and JSDoc alike, in `.ts`, `.tsx`, `.css`, `.yml` and shell — say *why* in one breath and let the code say what it does. Knowledge that does not fit goes to its [reference](docs/reference/README.md) section, or to an ADR when it is a decision, and the comment left behind is the pointer. Markdown is prose and has no limit. `bun run check:comments` holds the rule: it is one of the `gates` and a step of CI's `check` job.

## Tasks and decisions — backslop

The task tracker and decision log live in `docs/` and are managed with `npx --no-install backslop` (configuration: `backslop.json`, task prefix: `DA`). There is no task list in files: `npx --no-install backslop status` prints active work, the queue, deferred work, triage, and minor entries by scope. The operating rules are in `docs/backlog/README.md`, who decides what in `docs/ROLES.md`; terms are in `docs/GLOSSARY.md`. The layout version is the `version` field in `backslop.json`; update backslop with `npx --no-install backslop upgrade` when you decide to, not because of someone else's commit.

**Agent startup (before task selection or implementation).** Read `tools` and `cli` in `backslop.json`. If your current harness is selected, run `npx --no-install backslop lint --require-adapter <tool>` from the project root, replacing `<tool>` with your current harness id: `claude`, `cursor` or `codex`. This read-only check requires only that configured adapter's outputs even when Git ignores them. Missing or invalid outputs of another adapter do not trigger startup repair. If it reports missing or invalid outputs of your current adapter, run `npx --no-install backslop init` with no selection, hook, language or upgrade flags, then repeat the check. When it passes, do not initialize again. With `tools: []` or an unselected harness, do not add an adapter. Use `npx --no-install backslop lint --require-adapters` separately to diagnose all configured adapters. Other lint errors still need their own fix; they are not a reason to keep rerunning init.

Use exactly the project's configured CLI, including its pin and quoting. Preserve config values, documents, task status/order, custom `CLAUDE.md`, unmanaged `AGENTS.md` text and foreign harness settings. A missing CLI, denied access, invalid config, unsafe path or foreign-file conflict is a blocker: report the exact command and refusal, do not substitute an unpinned CLI, overwrite foreign files, install globally or request credentials in chat. After restoration, read the applicable generated instructions directly if the current session has not discovered them: `.claude/skills/backslop-task/SKILL.md`, `.cursor/rules/backslop-task.mdc` or `.agents/skills/backslop-task/SKILL.md`. Restart only if a required harness capability needs it, and name that capability; generated files alone do not prove a role or MCP server is running.

**Skills (when an adapter is selected):** `backslop-task` — the lifecycle of one task; `backslop-batch` — a worker run by tracks; `backslop-seed` — populate documentation after installation; `backslop-writer`, `backslop-techdoc` and `backslop-humanizer` — the documentation currency and style pass, and the writing rules it applies.

When an adapter is selected, before a release commit, run the `backslop-writer` pass in release mode over the diff since the previous tag.

The stop hook runs `lint` and prints the kept errors in changed files, subtracting pre-existing local missing-link identity counts when a compatible first-start baseline is available: fix the reported errors, do not bypass the hook.

**Change procedure.** There are two roles: the worker implements and verifies (steps 1–4), the approver accepts and closes (5–7); a single agent performs both roles in order.

1. **Task.** Take the first queued task (`npx --no-install backslop status`) or create one: `npx --no-install backslop new <slug> --title "…"` puts it in triage; `--queue` puts it directly in the queue. A small change without a tracker record is allowed if one pass fully implements it and it does not change a contract. A finding carries a cost label: fix `critical` now, fix `major` within the current task's scope now, file `major` outside it with `npx --no-install backslop new <slug> --parent N[.M]`, then fill the `Evidence:` line of its Context, and file `minor` with `npx --no-install backslop new <slug> --parent N[.M] --minor --evidence "…"` — without evidence the command refuses. A `major` or `critical` hypothesis is filed with `npx --no-install backslop new <slug> --parent N[.M] --minor --cost <level> --hypothesis --evidence "…"`; only a minor finding uses plain `--minor --evidence`. For a run, make one planning commit containing only the tasks it creates and the track it takes: run `npx --no-install backslop new` for each task and one `npx --no-install backslop mv N M K active` for the track. A task taken later in the run goes into the next planning or acceptance commit, never a separate take commit.
2. **Change.** Reverse a previous decision by clean removal, without strikethroughs or “cancelled” notes. Preserve the style of the existing file. Use terms from the glossary; if a required term is missing, propose it to the owner rather than silently inventing it.
3. **Documentation in the same pass.** An undocumented change is incomplete: update the relevant `docs/reference/` section, the affected subsystem README, and CHANGELOG. An architectural decision needs `npx --no-install backslop adr <slug>` and a row in `docs/README.md`; a new decision on a question already decided rewrites that ADR. A documentation fix carries a check that fails on the old text: a `quote:` block, a test or a lint rule. Documentation does not cite tasks: state the contract, the rationale or the measurement.
4. **Gates before reporting.** `npx --no-install backslop gates` is green: the commands in `gates` in `backslop.json`, the exit code of each, and the “gates N, green M” count. An entry with a `when` scope is skipped on untouched paths: a skip goes into the separate “not run N” number, never adds to the green count, and is named in the report on a line of its own. Commit to your branch with the `DA-N:` prefix before reporting; nothing stays uncommitted. For a committed branch, run `npx --no-install backslop gates --require-clean --base <base>`, where `<base>` is the commit before the task was taken: without `--base` only uncommitted paths count and scoped gates are skipped. Verify a test change with a mutation probe: commit first, then run the probe — `npm run probe`.
5. **Acceptance and archive** are one approver pass: review the diff, run `npx --no-install backslop archive N`, complete `result.md` (outcome, what was done, verification), run `npx --no-install backslop fold N > "$(git rev-parse --git-dir)/BACKSLOP_DRAFT"` — it folds the directory into a `docs/archive/LOG.md` line and prints the task body on stdout as a commit message draft, which lands outside the working tree. Do not commit between `archive N` and `fold N`: that commit would become the journal line's revision, and a squash would drop it from history. The final acceptance commit carries the draft as its message: `git add -A`, `git reset --soft <base>`, `git commit --cleanup=verbatim -F "$(git rev-parse --git-dir)/BACKSLOP_DRAFT"` — keep the body; a `fixup` onto the worker's commit discards the draft. **Attachment branch:** while the task directory holds an attachment, `fold` refuses until the attachment is in `HEAD`, so squash first, with the directory in the tree: `git add -A`, `git reset --soft <base>`, `git commit -m "DA-N: <what was done>"`; then run `npx --no-install backslop fold N > "$(git rev-parse --git-dir)/BACKSLOP_DRAFT"` and commit its result with `git add -A` and `git commit --cleanup=verbatim -F "$(git rev-parse --git-dir)/BACKSLOP_DRAFT"`. The journal line names the squash commit, which keeps the directory with its attachments; the task reaches the main branch as those two commits, and nothing is squashed after the fold. On Windows, run this recipe in Git Bash.
6. **Triage review** follows closure immediately and is complete when every entry still in `triage/` has a named next step: merged, moved, or closed by the owner’s decision (`docs/backlog/README.md`, § Triage cadence). A next step is, for example, a merge into another task, a clarified wording, `npx --no-install backslop mv N queue`, or `npx --no-install backslop mv N deferred` with a return condition. Ask the owner only before rejecting an entry.
7. **Commit.** Start the message with the task number: `DA-N: <what was done>`. A task reaches the main branch as one commit, or as two in the attachment branch of step 5: review fixes are squashed into the acceptance commit of step 5, and so is a separate planning or take commit when it took this task alone, contains only this task's creation and take, and `git rev-list <take>..HEAD` prints nothing: the `reset --soft` of step 5 goes to `<take>^`. Otherwise the planning or take commit stays a commit of its own and the acceptance commit says so: the acceptance of one task never absorbs the take of another, and the `reset --soft` goes to `<head>`, main’s head immediately before the current integration, never to a take commit that took several tasks, which would replace the earlier acceptances above it and lose their drafts. After it, commit the changes of the triage review of step 6 as a separate commit with the subject `DA: triage after DA-N`, so task N's commit carries no status moves from that triage review. Nothing is squashed after the fold — a squash would discard the draft, the only storage of the task body. `npx --no-install backslop lint` is green on the final commit; then push.

Worker boundaries: change only the assigned branch or worktree; create new finding files only with `npx --no-install backslop new`; never edit, move or archive an existing task file (no `mv`, no `archive`); do not touch `docs/archive/`; closure and triage belong to the approver.

**Talking to the owner.** A message to the owner — a question, a status, a run report — is read without the queue, the run or your context open. A question is answered from its own text: it says what is asked, why, and what each answer changes, so the owner decides rather than presses the recommended option. Use no term or abbreviation you coined yourself (a worker slug, “piece”, a review code such as F1); a definition new to the owner is used only after they confirm it. Name a task by its number and its title, `DA-N — <title>`, never by the number alone: the title goes at the first mention in a message, in every heading and in every table row; later mentions in the same paragraph may use the number alone; each list item counts as a paragraph.
