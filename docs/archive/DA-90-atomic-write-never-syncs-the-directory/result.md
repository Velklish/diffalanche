# DA-90 · Result

**Closed 2026-09-18.** Completed. `writeFileAtomic` opens the destination directory after the rename and syncs it, and takes a third argument `{ durable?: boolean }`. `review.json`, `comments.json` and `current` pay for that flush; `diff.json` and the lock's `info.json` pass `durable: false` — a cache git recomputes and a file that does not outlive a crash — so the measured scan path pays nothing. The choice belongs to the caller and the function never inspects the path: the default is durable, because a forgotten opt-out costs milliseconds and is caught by the perf gate, while a forgotten opt-in costs a write and is caught by nothing. After review the `catch` is split by what the failure means: failing to open the directory is legitimate on some platform and does not break the write, and the flush itself may only fail with `EINVAL` or `ENOTSUP`; any other error, `EIO` first among them, goes to the caller — and goes as a `StorageError` naming the directory, so the CLI prints one line and exits 1 rather than a stack and 2. Two things stay open and are named as such in the reference: Windows was not tested, so the task's claim that a directory cannot be opened there remains a hypothesis and is written down as a hypothesis; and the drive cache is not closed, because on macOS `fsync(2)` does not reach it and neither Node nor Bun exposes `F_FULLFSYNC`. The directory entry of the session directory one level up is still unsynced — filed as [DA-90.1](../../backlog/triage/DA-90.1-session-directory-entry-is-not-synced.md), in triage.
