# DA-103 · Result

**Closed 2026-09-18.** Completed. `repositoryIgnore` and `insideGitDir` were both anchored at the watched repository's own `.git`, so a repository nested inside it — a plain clone, or an old-style submodule with a real git directory in the working tree — had its whole object store inside the watch: a `git fetch` down there cost a `check-ignore` process and a full `rescanRepository` per debounce window, and in the polling fallback `snapshot` descended and `stat`ed every loose object, pack and ref on every tick, while the outer change set could not move a line. **The decision differs from the plan, and the difference is the point.** The plan was the task's third candidate — prune what is unambiguously internal: `objects/`, `logs/`, `refs/`, `modules/`. Writing it showed that to be the worst of the three: `git commit` in a nested repository does not touch `.git/HEAD` — HEAD stays the symbolic `ref: refs/heads/main` and what moves is `refs/heads/main` — so pruning `refs/` would have hidden the very change that moves a tracked gitlink and the outer diff with it, while `FETCH_HEAD` is not in that list and the fetch noise would have survived; the task's phrase "a nested `HEAD` (the file that moves when a gitlink does)" holds for a checkout and not for a commit. Shipped instead, narrower: inside a nested `.git`, report `HEAD`, `packed-refs` and anything under `refs/heads/`; prune everything else and do not walk into it. Those three are what a gitlink's position is made of — `HEAD` for a checkout or a detached move, the branch ref for a commit, `packed-refs` for a packed repository — and what is left out is bookkeeping the outer change set cannot see; a `git fetch` writes `objects/`, `logs/`, `refs/remotes/` and `FETCH_HEAD`, all four pruned. Applied in both places the task requires: the ignore predicate, and `insideGitDir`, which now matches any `.git` segment so such a burst spawns no git process at all. The repository's own `.git` keeps exactly the rules it had. A modern submodule was never affected — its git directory is a file pointing into `.git/modules/`, which the anchored branch already pruned as a directory. `src/core/scanner/index.ts` and `src/core/git/index.ts` were read and not changed.

**Verification.** Three new cases. `what a repository's watch reports > shows a nested repository's gitlink and none of its bookkeeping` pins the predicate in both directions, including that the repository's own `.git` is untouched. `watching a tree > does not walk into a nested repository's git directory` covers the walk, where the cost is continuous: a write under `vendor/lib/.git/objects/` and a `FETCH_HEAD` produce nothing while a working file of the nested repository produces its path, and a write to `vendor/lib/.git/refs/heads/main` is reported. `watcher > wakes for a burst from a nested repository's git directory, and not for its objects` holds the other half of the change: a plain nested clone under a `nested/` rule, so git answers that everything there is ignored, and the write to its `HEAD` still wakes the watcher — which can only hold while the burst never reaches `check-ignore` — while a write to its object store says nothing with a hidden change waiting to be announced. The fixture's own `vendor/lib` could not be used for that last one: it is a modern submodule, the case this task says was never affected.
