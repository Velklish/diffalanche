# DA-91 · Result

**Closed 2026-09-18.** Completed. The entry point handed `process.stdout.write` to the command layer and nothing listened for the stream's errors. `run()`'s `try`/`catch`, which exists to map every failure onto an exit code, cannot see this one: `write` returns a boolean and the `EPIPE` arrives later as an `'error'` event on the socket, not as a rejection of the awaited `dispatch`. The writes are single and large — `diff` emits the whole change set in one call — so the pipe buffer is no protection, and `diffalanche diff | head` ended in a Node internals stack trace at exit 1: the exit-code table's row for a refusal the tool never made. Decided and written into the table's section: **a reader that goes away is exit code 0 and nothing on stderr** — the reader got what it asked for, and `head` is a normal way to use a CLI. **Any other stream fault is not swallowed with it**: a full disk on a redirected stdout is one line naming the stream and exit code 2, because output the person asked for did not arrive. The handler lives in one place, `processOutput()` in `src/cli/output.ts`, and both entry points call it — `src/cli/index.ts` and the binary entry `scripts/build.ts` generates, whose wiring was duplicated verbatim, so a handler added to one would have left the other exactly as it was. Its two streams are parameters defaulting to the process's own, which is what lets the non-`EPIPE` branch be driven by a verdict without a full disk.
