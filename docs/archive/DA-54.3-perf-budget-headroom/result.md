# DA-54.3 · Result

**Closed 2026-09-21.** Completed, and it produced [ADR-013](../../adr/adr-013-perf-gate-off-ci.md). `bun run perf` holds a development machine to the specification's numbers, and under load those numbers are the machine's rather than the code's: taking the whole subject of a task out of the code did not make the gate pass, and across paired runs the sign of the difference flipped both ways. The gate now reads the one-minute load average per core at **both ends** of the run and, above 2.5 per core, prints `unable to measure` with the load named and exits 1 **without a budget verdict** — before the fixture and before the browser, so nothing is compared and no number is invented. A red `bun run perf` is therefore exactly one of three things and the output says which: `over budget`, `not measured` (DA-69's `UNMEASURED`), or `unable to measure`. On a GitHub-hosted runner the precondition is off — a runner's load is nobody's to control, `RUNNER_ALLOWANCE` stands in for it there, and the `perf` job's own fixture generation would otherwise trip the check on four cores. `DIFFALANCHE_PERF_IGNORE_LOAD=1` measures anyway and prints **Not evidence.** above the table with the load beside it: a bypass invisible in the output would be the development allowance the ADR rejects, under another name.

**Verification.** The threshold is measured, not chosen. Fifteen `bun run perf` runs of one session on one machine (Apple M1 Pro, 8 cores), each recorded with the busier of the two load readings around it and the CPU-per-frame median it produced: below 2.5 per core the band is 8.6–9.1 ms, half a millisecond wide, and the long-task count is stable; above it the band is 8.6–10.2 and the long-task count starts flipping between trees on the same commit. The table of all fifteen pairs is in ADR-013. Mutation probe 3 of the track, on `a009129`: `perf/load.ts:36` made `tooBusy` always false, run exit 1, reddening `declines above the ceiling and answers below it`; `git status --porcelain` empty at both ends. **And it fired in the wild the same evening it landed, twice, unplanned** — in the worker's shipping gate chain at 3.00 per core, refusing in 271 ms before the fixture and before the browser, and in an earlier chain at 24.64 over 8 cores, 3.08 per core, in 321 ms. Both refusals are `unable to measure` and neither compared a budget line. That is the seventh gate of this track's own record red by design rather than by defect.

**What this pass opened.** The precondition reads only the one-minute average, and the one-minute average can say "quiet" while the five- and fifteen-minute averages say the machine is still draining the previous run — observed the same evening at 6.19 against 12.50 and 19.12, with the numbers coming out 1.2 ms and 40 ms worse than the same branch measures when the machine really is idle. Filed as **DA-54.5**, with all three of the day's cases including a neighbouring worker's 575 ms against 258 ms on one sha, which is the size of the noise that gets through; a later commit of this track points DA-54.5 at DA-60, the flaky-test hardening card, as the same problem approached from the other end. The UI gate has no load precondition at all and is filed as **DA-54.4**. Both are in `triage/`; routing them is the orchestrator's move.

**The gates of the merged track.** The full gate list ran once on the tree the seven tasks make — `d76d804`, tree clean, `gates 7, green 6`, with the one red being `bun run perf` refusing to erase a pre-stamp fixture rather than returning a budget verdict. The commands, their exit codes and counts, the fifteen per-commit typechecks and how the track was integrated into `main` are in [the result of DA-63](../DA-63-perf-gate-erases-fixture/result.md); this task points there rather than repeating them.
