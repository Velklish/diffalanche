# DA-76.1 · Result

**Closed 2026-09-22.** Completed. A file that changes type is one entry, and the entry carries both halves. Git cannot write a tracked file becoming a symbolic link as one patch, so it writes two for the one path — a deletion of the old mode and an addition of the new, adjacent and in that order — and the de-duplication DA-76 added never saw them, because it reconciles the diff against `ls-files --others` and both of these come from the diff. Reproduced on git 2.54.0 (Apple Git-157). **The decision**: the pair parts company with `git rm --cached`, which is one file named twice where keeping one naming is right; a type change is two real halves of one change, and dropping either loses what the reviewer came for — the content that left, or the link that arrived. For a tracked file replaced by a link to `/etc/hosts`, the link is the finding and the old content says what was lost. So `parseDiff` folds an adjacent deleted-plus-added pair on one path into one entry: both patches in the order git wrote them, both hunk lists, additions and deletions summed, `oldPath` still null, and status **`modified`** — the path is on both sides of the change, which makes `deleted` and `added` each untrue about it. The condition is deliberately narrow: **only** a deletion beside an addition on one path is joined, so any other repeat of a path stays two entries where somebody can see it.

**When one half has no content.** A binary file, or one over the size limit, replaced by a link gives a deletion with no patch beside an addition with one. Taking the omission for the whole entry would hide the link, which is the one thing the entry exists to show, so the merged entry carries the half that has content, the counts are still summed, and the skipped side becomes a repository warning through a new optional `notes` sink on `PatchOptions`. Both halves omitted is the only case where the entry is omitted too. **The sink's weakness is that it is an out-parameter a caller can forget**; closing that means changing `parseDiff`'s public return shape, which is a contract change and is filed as `DA-76.3`. What landed here instead is a line in `docs/reference/02-git.md` naming the caller's obligation — "That warning travels through `notes` in `PatchOptions`, which the caller supplies and `readRepositoryChange` does: a caller that wants the warning has to pass the array, and one that does not simply does not hear about it." That line is in the diff, and DA-76.3 cites it as done.

**What it cost the UI, measured.** One `patch` string holding two patches is a shape every patch reader in `src/ui` had to learn: each skipped to the first `@@` and then read to the end, so the second patch's `--- /dev/null` and `+++ b/…` counted as a deletion and an addition. Before the fix, on the reproduction: `measurePatch` answered **140 px** for the pair against **48 + 48 = 96 px** for the halves measured apart — 44 px of phantom rows in the height a card claims before it is mounted, which is the scroll-anchoring arithmetic of ADR-008; `firstAddedLine` answered **3** for a file whose first added line is **1**; `splitHunks` put the whole second file header inside the first hunk's body. Six readers now stop at a `diff --git` line — `measurePatch` and `hiddenLines`, `splitHunks` and `hasNewLine`, `firstAddedLine`, `preview` — with no signature changed and no parameter added. The seventh site is the file card, and covering it moved the merge the renderer mounts out of `ReactDiffFile.tsx` into `mergedPatch` in `src/ui/patch.ts` — not for tidiness: the verdict meant to cover it tested `parseDiff`, the library, so reverting the renderer to `[0]` would have left it green, and it could not be tested in place because importing the `.tsx` pulls React and `react-diff-view/style/index.css` at module level with no CSS handling declared for vitest here.

**Verification — nine mutations, one per site, each with its expected verdict written down first.** Q1, the merge removed from `parseDiff`, through Q9, the `files.length === 1` early return removed so that merging becomes unconditional: every probe exited **1** and reddened its own named target — 36 verdicts, 35 passed, 1 red, 0 unaccounted on Q1, and 1 failed of 9 on the re-run of Q9. `git status --porcelain` was empty before the first mutation and after the last restore, and each mutation asserted its exact target string before running. The verdicts live in `tests/ui-type-change.test.ts` and `tests/git.test.ts`. The track's integration gate, the per-commit build and the landing of the four commits into `main` are recorded once, in [DA-67](../DA-67-two-writes-outside-the-session-lock/result.md): `gates 7, green 5` on `e69f21f`, four of four commits typechecking standing alone.

**Three things the run got wrong first, kept because they are the method.** The first pass ran its nine probes against a file that was already red on the clean tree, which makes every exit code worthless — a file with a standing failure fails under any mutation. Eight of nine were readable anyway, because they reddened their own target *in addition to* the standing one; **Q9 was not**, its target being the standing failure itself, so it was withdrawn and re-run against a green file. An exit code answers "something broke"; a verdict name answers "the thing I aimed at broke", and on a suite with any standing red only the second question can be asked. The standing red was then a wrong expectation rather than wrong code: `mergedPatch("")` returned an object where the verdict expected `null`, because `parseDiff("")` from react-diff-view yields one file rather than an empty array — the same object the renderer produced before the change — so the expectation was corrected to assert what the code always did and the library was not bent to fit the test. And two verdicts that could not have gone red were caught while planning the probes: `hasNewLine` on the type change, where a misread `+++` advances the new-side counter for exactly zero lines and no query can see it, moved to a fixture where the misread header would be a sixth new-side line; and "gives the renderer every hunk of the entry", which called `parseDiff` directly and so tested the library, which is what led to extracting `mergedPatch`. One verdict is knowingly kept that no mutation of ours can redden — `hiddenLines(BOTH, {0: true, 1: true})` is empty whether the scanner works or not, because a type change has no context to hide — as a pinned fact about the domain.

**The perf question, and the attribution withdrawn.** The first attribution claimed no patch reader runs on the edit path. That claim was false and was withdrawn against a measurement rather than against an argument: three readers do run there, and their whole cost is tens of microseconds per call against the **57 ms** between the medians, so the added check cannot explain the difference. The reading is in the track's `evidence-batch2-2.md`; its per-side deltas were removed because base and branch ran in one process with a fixed order, which measures JIT warm-up alongside the code.

**Documentation in the same pass.** `docs/reference/02-git.md` — the qualification to "one path is one entry", the warning's wording, and the caller's obligation — `docs/reference/08-ui.md` for the readers that stop at a `diff --git` line, `docs/reference/06-cli.md`, and a `### Fixed` entry in `CHANGELOG.md`.

**Filed, not closed.** `DA-76.2`, a merged type change being `modified` in the core and `add` in the renderer, and `DA-76.3`, `notes` as an out-parameter — both recorded in `main` already and neither acted on here. And [DA-76.4](../../backlog/minor/DA-76.4-parse-diff-may-cost-ten-ms-on-the-rescan-path.md), opened during this acceptance: `baseline()` in `tests/watcher.test.ts` is very nearly a direct reading of `readRepositoryChange` and so of `parseDiff`, and across eight alternating runs the merged tree sits about 10.63 ms above the base on about 70 ms — but only after a post-hoc exclusion of each side's first run, so it is a hypothesis with a stated plan and not a measured cost.
