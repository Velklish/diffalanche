# DA-53.1 · Result

**Closed 2026-09-18.** Completed. `PUT /api/sessions/:name/scope` replaces a scope and the scope editor writes through it; the CLI had only `review scope add`, which widens, and nothing is wider than the whole root, so a session without a scope was refused by name. The same operation existed on one side of the product and not on the other: a human with the editor could narrow a review into a task, an agent at the terminal could not. `review scope set` now replaces the scope outright. It narrows whatever it does not name, so it takes `--drop-comments` and refuses without it exactly as `review scope remove` does — with the count and the ids, writing neither the scope nor `comments.json`. One write is one state, on both sides. Two things it deliberately does not do, both written down rather than left to be inferred. It has no spelling for "none", so putting a task back to the whole root is still the editor's alone: the entry asked for a way to *give* a scope, and taking one away is a different operation. And the scope of a task does not follow a renamed file — the entry's second question, which the entry itself calls the owner's, so it went to triage as `docs/backlog/triage/DA-53.2-should-a-scope-follow-a-rename.md` carrying the alternative that was already measured and rejected during DA-53's review.
