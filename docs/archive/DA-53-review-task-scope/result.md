# DA-53 · Result

**Closed 2026-09-10.** Completed, and it is the foundation the three UI tasks stand on. `review.json` gained `scope`, `status`, `closedAt` and `closedBy` at `SCHEMA_VERSION` 2; version 1 still reads — as the whole root, open — and is written back as 2 by the next write, so a data directory upgrades itself as it is used, while `diff.json` of an unknown version is discarded and rescanned because it is a cache. `scanReview` takes the scope and runs `readRepositoryChange` only for the repositories the scope names, so a task over two of twenty-one repositories does not pay for the other nineteen. `diff`, `list`, `show` and `export` answer inside the scope; a comment anchored outside it is refused by name, and the refusal says what the task *is* about. `review new` builds a scope from repeated `--repo` and `--path` and can leave `current` alone with `--no-use`; `review scope`, `scope add` and `scope remove [--drop-comments]` read and edit it; `review close` and `review reopen` set the status. The HTTP routes the UI needs are in place, including the whole-root candidate list a scope editor picks from and the 409 that names how many comments a narrowing would delete.

Two decisions were taken with the owner during the pass and are in [ADR-010](../../adr/adr-010-review-task-scope.md) beside the seven from the interview. A comment on an anchor outside the scope is **refused**, because a comment nothing can read back is what product principle 5 forbids — the carve-out decision 2 makes is about the screen, not about writing unreadable data. And `review close`/`reopen` require `--role human`, extending to a task the rule [ADR-004](../../adr/adr-004-agent-contract.md) has held for a thread since it was written.

**Renames are matched literally, and that is a reversal made during the review round.** The first implementation kept a file in the change set when *either* of its names was in the scope. The review found the other half missing — the task showed a renamed file and refused a comment on it — and the obvious fix, resolving renames on write too, was tried and measured: the comment then landed but `list` did not return it, because the comment sits under the new name and the scope holds the old one. Closing that in turn would mean resolving renames on every read of the comments, from a change set that stops carrying the rename the moment it is committed. So the rename branch was removed instead: a file whose name changed is at a path the scope does not name, and nothing outside the scope is shown (decision 2), while the path the scope holds simply has nothing to show — decision 5, the same answer a file that stopped changing gets. The scope does not follow a rename; a new name is added with `review scope add`, and whether it should follow `git mv` is left to the owner.

**Verification.** Six gates run by the approver on the merge commit itself, not on the worker's branch — the branch stood on `1193ab3` and main had moved: `backslop lint` 0, `bun run lint` 0, `bun run typecheck` 0, `bun run test` 0 (433 tests), `bun run test:bun` 0 (433), `bun run perf` **0** — 7.8 ms against the 8.3 ms budget, every line inside. `bun run test:ui` 0, 66 tests. The perf gate that both workers reported red on their own branches passes on the merged result; the load average was 20.5 at the time, so the earlier failures were the machine, exactly as the paired measurements said.

Every line of the task's verification section has a test in `tests/scope.test.ts` and `tests/scope-scan.test.ts`. The cheap-scan probe counts `git` processes through a shim on `PATH` and asserts twice: two repositories touched with a scope of two, and all twenty-one touched without one — without the second assertion the probe could be green from measuring nothing. Nine mutation probes were run after the commit, and one survived: `addComment` without the scope check stayed green, because the tests went through the CLI and the CLI refuses earlier, so the path HTTP uses was not covered. Two tests were added and the probe went red. Its consequence was a second finding: the scope check in `src/server/app.ts` turned out to be dead — removing it reddened nothing, since the domain check gives the same `out-of-scope` and the same 400 — so it was removed. The identical check in the CLI was kept and its reason written down: it stands before `refreshRepository` and saves four git processes on a refusal.

An isolated reviewer read the whole diff — 4694 lines, 50 files — and raised ten findings, all closed. It ran no commands: the tool has them disabled for a reviewer, and it said so rather than implying it had measured. Three of the ten were behaviour: the rename asymmetry above; `reply`, `resolve` and `reopen` not checking the scope while `get` and `list` did, so one id got two answers; and a failed read of `reviews/` being recorded as an empty snapshot, which would make the next successful pass emit `sessions-changed` for every session and push the replay out of the SSE ring. The rest were documentation and nits. Three of the mutation probes for the new fixes survived on first run — the behaviours had no tests — which is what a probe is for; the tests were written and the probes went red.
