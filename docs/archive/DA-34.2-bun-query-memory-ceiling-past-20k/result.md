# DA-34.2 · Result

**Closed 2026-09-24.** Completed. The embedding model runs in a process of its own: the server's first `GET /api/suggest` and the commands that embed — `suggest` and `index rebuild` — start a child that holds only the model (`src/core/ml/embed/child.ts`, `spawned.ts`), and the index, its update and its search stay in the process that asked. The worker thread of DA-34.1 (`threaded.ts`, `worker.ts`) is removed: a process is off the event loop too. Decisions this acceptance records:

- **The direction is the owner's, the design is [ADR-016](../../adr/adr-016-model-in-a-process-of-its-own.md), accepted.** Of the candidates in the task, the owner chose the model in a process of its own on 2026-09-24 (the orchestrator's ruling for this acceptance); the `ml3` worker designed it within that, and the orchestrator accepted the design the same night. ADR-014's 768 MiB ceiling holds per process.
- **Every process under the ceiling, measured.** Each process's own `maxRSS`, two runs a cell, Bun 1.3.14 and Node 25.2.1, 2026-09-24 at load averages of 6.8–10.2 on 8 cores: a query's own process 71–343 MiB to 100 000 comments; the server 383–585 MiB to 50 040 (the 10 040 and 50 040 cells on a stand-in index — random vectors, real comments); the model's process 627–737 MiB whatever the index held. On the base `66b749b`, alternating, one process: a query over 50 000 on Bun 846 and 853 MiB, the server after its first suggestion 871–995 MiB on both runtimes. `perf/index-scale.ts query` and `serve` print each process's peak ([09-ml.md](../../reference/09-ml.md#in-a-process-of-its-own)).
- **The model's process is ADR-014's process itself.** In ADR-014's shape — the model loaded, 200 texts embedded — it peaked at 710–751 MiB on Bun across the binary and `child-entry.ts`, 681–707 MiB on Node: 17 MiB of headroom on Bun. Only ADR-014's levers move that, so it is the owner's entry [DA-34.3](../../backlog/minor/DA-34.3-model-process-headroom-on-bun.md), left in `minor/`.
- **The event loop stays free.** DA-34.1's measurement again, `perf/run.ts --lag` / `--embedding child` on the branch against `--embedding worker` on the base, six rounds alternating: "Update after an edit in one repository" at medians of 292 ms without embedding, 305 ms with the child, 304 ms on the base's thread. One child run of the six, 719 ms and the first of its series, is counted and not explained.
- **How the child is started.** `node dist/embed-child.js` on the npm channel, the binary itself on a binary — no argument and `DIFFALANCHE_EMBEDDER=1`, which the child removes once read, so a user who sets it gets an ordinary command. The branch is on the channel, not on the runtime, so no second runtime-specific module (ADR-008). The server keeps the child until `close()` and starts another when one ends; a command ends it once it has answered, and one that never closes it still exits. A child that cannot start, cannot load the model, writes what is not an answer, or ends under a request is a `ModelError` and the route's 503.
- **Not measured:** `index rebuild` after the split; the child's start on Linux and Windows; Bun's `maxRSS` unit on Linux (perf assumes kilobytes there).
