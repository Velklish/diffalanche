# DA-24.1 · Result

**Closed 2026-09-22.** Completed. The server holds one built review document **per session** instead of one at a time, so the first build of a session is paid once and a return visit is answered from memory. A `Map<string, Held>` bounded to four entries (`DOCUMENT_CACHE_LIMIT`) carries, per session, its own version counter, pending build, payload and comment marks; the least recently asked-for is dropped, and an entry with a build in flight is passed over so no in-flight build loses the version it started on. Four is the bound because a document is megabytes and so is the serialised string beside it. Every write invalidates only the session it names, and **`POST /api/sessions/:name/use` invalidates nothing** — moving `current` changes which document a request without `?review=` resolves to, not what any document says. A comment, a reply, a resolve and a reopen now re-read the comments of that session alone rather than dropping its document: a comment does not move the working tree, and on a task the watcher does not follow, a rebuild meant reading every repository of the scope for every write.

**The card's mechanism was out of date, and this is the line for its file.** The card was written 2026-09-05, before ADR-010 and DA-55. The page does not switch a task with `POST /api/sessions/:name/use` at all — `switchSession → showTask → loadReview` writes `?review=<name>`. So the cold path was never only the first switch after `use`: *every* switch to a named task was cold, because `other()` built the document per request and kept nothing.

**The perf line changed shape with the task, which is why the numbers below are not one comparison.** `Switching review sessions` lost its `pendingUntil` in `perf/budgets.ts` and became the budget of a **return visit**; the harness now makes the first, cold switch of a session before the measured pair and prints it unbudgeted, so the path no budget covers is named rather than warmed away.

**Verification.** The integration gate on `e3224ca`, below, put the line at **83.5 ms against a budget of 100 — `ok`**. The same command on `ee5f539`, the `main` this track was merged into, measured **137.5 ms** on that line, where it was not held to the budget at all but printed with the `DA-24.1` marker. The two readings were taken four minutes apart under one holding of the run's machine lock, so they are a *pair* rather than two separate evenings — which is what the worker's earlier reading, **78.6 ms against a base of 95.1**, was not.

**What those two pairs establish, and what they do not.** Both pairs point the same way, and they were taken by different sessions on different trees. That is enough to say the direction is confirmed and to lift the line's `pendingUntil` on evidence rather than on faith. **The magnitude is not claimed**: it is one sample per side in each pair, the line is machine-dependent, and the two sides do not measure the same event — on `ee5f539` nothing is held, so both switches of every process are full builds, while on `e3224ca` the cold build is paid and printed separately and the measured pair is warm both ways. That difference *is* the task's subject rather than a confound to apologise for: before this change a warm return visit did not exist to be measured, because no document was kept.

**The cold number, recorded because it is inconvenient, and what it is a number about.** Printed unmeasured on `e3224ca`: **794.6 / 910 / 571.6 ms**. The worker measured **575 / 770.1 / 629.6 ms** on `cb468c8`. The card's own text records **513 ms**. Every one of those six readings is higher than the card's, on a card about making this faster. The conditions are not comparable — different date, different machine load, and the perf fixture moved under another track of this same wave — so **no conclusion is drawn in either direction**. It is written down because a number that is inconvenient and quietly absent from a report is the failure this batch kept finding in other forms.

The cause of the cold path's cost is recorded by the branch itself in `docs/reference/11-perf.md`: the copy no longer spares the run a scan, because the server trusts `diff.json` only for the session the watcher follows and the harness's scratch session never is one, so its first build reads the whole root from the working tree. **That is an explanation and not an excuse, and it also bounds what the number is about**: it measures the first build of the harness's own scratch session, which is not necessarily the cold path a person meets — a person's task is the one the watcher follows as soon as the server is looking at it.

**Documentation in the same pass.** `docs/reference/07-server.md` (the review document and its per-session cache), `docs/reference/11-perf.md` (what the switch line measures), and a `### Changed` entry in `CHANGELOG.md`.

**Filed, not closed.** [DA-55.5](../DA-55.5-startup-trusts-a-cache-nothing-refreshed/task.md) — the first document of a server's lifetime is built from a cache nothing has refreshed — was filed by this track and triaged to the queue at this acceptance. Its "Out of scope" names the cold path as DA-24.1's and settled.
