**Closed 2026-09-19.** Completed. A patch git writes without `---` and `+++` lines has no hunks, so `gitdiff-parser` has nothing to tell an addition from a change with and answers `modify`. That made a staged binary addition and a binary deletion both `modified`, with the path and `omitted: "binary"` right beside the wrong status. `headerPaths` already walks the region above the first hunk; it now reads `new file mode` and `deleted file mode` there and returns what it found, and `parseFile` prefers that over the parser. Only that region is read, because a `GIT binary patch` payload is arbitrary and a line-anchored match over the whole patch would be matching against file content. The empty-file case the card raises is closed here rather than filed separately: a staged empty text file takes the same route for the same reason — the missing read, not binaries — and it is the same three lines. `path = status === "deleted" ? oldName : newName` now takes a different branch for a deleted binary. Both halves of its `diff --git` line carry the same name, so the value does not change; that was checked rather than assumed, and `oldPath` stays `null` for anything but a rename.
