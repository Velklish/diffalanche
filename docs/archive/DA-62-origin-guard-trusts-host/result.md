**Closed 2026-09-18.** Completed. Both origin guards compared the request's `Origin` with `new URL(c.req.url).origin`, and the runtime builds that URL from the request's own `Host` — so the question they asked was "does the client's `Origin` match the client's `Host`", which a client controls on both sides and a DNS-rebinding page satisfies with no bug in the browser. A third guard now runs first, on `/api/*`, and asks what the two could not: is the host this request arrived on one this server answers for. The names are `127.0.0.1` and `localhost` as the URL parser normalises them, compared whole; anything else is a `403` `error: "forbidden"` naming the host, and so is a `Host` that is not a host at all. It covers reads as well as writes, because what is behind these routes is the absolute root path and the patch of every changed file, which a rebinding page reads with a `GET`; the built page is not behind it, the assets being the same bytes for everyone. Only the name is compared, not the port — a request reached this server because it dialled the port the socket is on, and a browser copies into `Host` the authority it dialled, so a second diffalanche on another loopback port is the origin guard's question, and that guard now rests on a host it can trust. A request with no `Origin` keeps passing: it is not from a page, the CLI and an agent send none, and carrying that is what the host check is for.
