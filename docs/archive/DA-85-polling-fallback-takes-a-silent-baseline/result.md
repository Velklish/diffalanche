# DA-85 · Result

**Closed 2026-09-18.** Completed. Of the two candidates the second was taken — **re-announce**. The walk that replaces a failed watch keeps its silent baseline, and the takeover itself is the signal: once the replacement's baseline is taken, `TreeWatcherOptions.onFallback` fires and `startWatcher` reads that tree whole — a repository is rescanned, the data directory is reloaded. "Report from the start" needs a snapshot handed over from the native path, which has none. Re-announcing costs one rescan per tree and cannot under-report, because the rescan reads the repository's whole change set whatever name the watch failed to deliver; the `files` of that `diff-changed` are empty, since a takeover names no path. The degradation is surfaced by a new `WatcherOptions.onFallback`, said once for the first tree that falls back — the runtime gives up, not one tree — and `src/server/serve.ts` turns it into one line on stderr. `Watcher.polling()` is removed: it had no consumer in `src/`, and the signal is now pushed rather than polled. `TreeWatcher.ready` became a getter over the live source, `TreeWatcherOptions.native` is injectable and reaches `watchTree` through `WatcherOptions` as well, so the failure is driven rather than waited for at both levels, and the former private `Inner` is exported as `TreeSource`. **What this deliberately does not cover:** a runtime that never had a recursive watch still starts on the walk in silence — the probe answering `false`, or `watch()` throwing so `native` returns `null`. Firing the same signal there would make the startup path re-read every repository right after the server's own scan, for a window that does not exist at startup, and DA-85 is scoped to what happens after the watch is gone. Both claims in the reference and the changelog say "a watch that dies after it started", and the startup case is filed as [DA-85.1](../../backlog/triage/DA-85.1-runtime-without-recursive-watch-says-nothing.md), in triage.
