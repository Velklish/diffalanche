# DA-31.1 · One unit test file fails under heavy machine load

- **Scope:** 11-perf (see [reference](../../reference/README.md))
- **Created:** 2026-09-05
- **Dependencies:** none
- **Taken:** 2026-09-05

## Context

Found while verifying `scripts/release.ts` (DA-31), whose preflight runs
`bun run test`. On a clone of `ceba421` with the same tree, the same suite was
run five times back to back while the machine carried the parallel worker
sessions of this run (load average 18 to 31 on an M1 Pro):

| Run | Result | Duration |
|---|---|---|
| 1 (`release --dry-run`) | 23 files, 310 tests, all passed | 32.30 s |
| 2 (`release`) | 22 passed, **1 file / 1 test failed** | 31.61 s |
| 3 (`bun run test`) | passed | — |
| 4 (`release`) | 22 passed, **1 file / 1 test failed** | 21.48 s |
| 5 (`release`) | 23 files, 310 tests, all passed | 21.95 s |

And on `31b55d5`, on the same machine:

| Run | Result | Duration |
|---|---|---|
| gate | **3 tests failed**, 307 passed | 32.38 s |
| next six | 310 passed, every time | 16 to 20 s |

It happened once more on the review-fix commit, and worse: `bun run test` came
back `3 failed | 307 passed` in 32.38 s at a load average of about 13, while
`bun run test:bun` on the same tree, minutes later, passed 310/310. Six runs
after it — one immediately, then four in a row hunting for it, then the gate —
all passed 310/310 in 16 to 20 s.

The same tree passes and fails without changing, so the failure is timing, not
logic. Which tests they were is still not recorded: every failing run so far was
either filtered to the release script's own output or tailed to its summary, and
the names sit in the lines between. That is the one thing the next run of this
has to keep.

The suspects are the tests that print a measured number —
`update after an edit: 331.3 ms`, `edit to diff-changed: 758 ms, then 426 ms`,
`check-ignore over 50 paths: 24.0 ms` — because those are the ones with a clock
in them, and the watcher's debounce is 100 ms. That is a hypothesis; the failing
name is the first thing to get.

## Work to do

- Reproduce with the failing names in hand: run the suite in a loop under
  artificial load and keep the **full** output of each run, not its summary —
  four runs at a load average of 13 did not reproduce it, so the loop has to be
  longer than that or the load heavier.
- Decide per test: widen the margin, wait on the condition instead of the clock,
  or accept and mark it.
