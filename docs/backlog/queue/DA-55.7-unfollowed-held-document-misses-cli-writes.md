# DA-55.7 · A held document of a task nobody follows keeps what the CLI wrote to it out

- **Order:** 790
- **Scope:** 07-server, 05-watcher (see [reference](../../reference/README.md))
- **Created:** 2026-09-24
- **Dependencies:** none
- **Parent:** DA-55.6
- **Cost:** major, a hypothesis read from the code and not reproduced

## Context

Raised by the reviewer of DA-55.6 and filed at the orchestrator's request. **Not
reproduced: everything below is read from the code.**

The server keeps up to `DOCUMENT_CACHE_LIMIT` built documents, one per session,
including sessions no window is on and that are not current. What drops or
refreshes a held document is either a write through the API, which names its
session, or an event of the watcher:

<!-- quote:../../../src/server/serve.ts -->
```ts
    if (event.type === "session-changed") {
      review.invalidate(event.name);
      return;
    }
    // The frame names the session its thread belongs to, and the watcher now
    // follows more than one ([05-watcher.md](../../docs/reference/05-watcher.md)).
    review.invalidateComments(event.session);
```
<!-- /quote -->

The watcher sends those events only for the sessions it follows:

<!-- quote:../../../src/core/watcher/index.ts -->
```ts
  /** The tasks followed: the current one, and the ones windows are open on. */
  function followedSessions(): string[] {
    const named = new Set<string>(options.sessions?.() ?? []);
    if (session !== null) named.add(session);
    return [...named];
  }
```
<!-- /quote -->

So a task whose document is held, that is not current and that no window is on,
hears nothing when a terminal writes to it — `review comment`, `reply`,
`resolve` into its `comments.json`, or a base or scope change into its
`review.json`. Its held document keeps the old comments and the old session.
The next window that opens it by `?review=` would be served that document, and
so would the window on the pointer once `current` moves to it: DA-55.6 refreshes
the change set on a move and nothing else. The change set is covered in the
ordinary case — `repositoryChanged` drops held documents whatever session the
watcher follows — but not in the two corners below.

Two narrower hypotheses of the same kind, raised by the reviewer of DA-55.6's
review round and **equally unreproduced**:

1. **An edit the move's read absorbed, which matches the replaced cache.** The
   read of a task `current` moves to picks up an edit made while it runs, so that
   edit's own rescan finds nothing new and says nothing. If the edit brought the
   repository back to what the replaced `diff.json` said — a revert of a change
   made while nobody followed the task — the read finds no difference either: no
   frame, no `onRepositoryChanged`, and the held documents of other tasks that
   show the repository as it was before the edit are never dropped.
2. **A build that starts during the read.** Until the read lands the task is not
   the followed one, so a build of it begun in that window is `followed=false`,
   and when it resolves after the move it is kept without the change set a later
   rescan handed over:

<!-- quote:../../../src/server/review.ts -->
```ts
          const settled = followed ? withAdopted(built, entry) : built;
```
<!-- /quote -->

   and from then on `repositoryChanged` passes it over as the followed session's:

<!-- quote:../../../src/server/review.ts -->
```ts
        // The followed session's document is patched by the rescan itself.
        if (name === followed) continue;
```
<!-- /quote -->

   A candidate fix is to judge `followed || watched() === session` when the
   build resolves. Recorded, not fixed.

## Work to do

- Reproduce first, as a test: hold a document of a task (open it by `?review=`,
  close the window), write a comment to it with the CLI, open it again, and see
  whether the comment is there. A hypothesis that does not reproduce closes the
  task, with the test that tried it.
- If it reproduces, decide the shape: invalidate every held session on a burst of
  the data directory (cheap, since only the file bytes are dropped), or have a
  move of `current` and the opening of a stream re-read what they are about to
  serve.
- Try the two narrower corners the same way: a revert landing inside the move's
  read, and a build of the task begun during it.

## Out of scope

- The change set of such a task in the ordinary case, which `repositoryChanged`
  already covers.

## Verification

- A comment written by the CLI to a task whose document is held and which nobody
  follows is in the document the next window on that task is served.
