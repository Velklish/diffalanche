# DA-56.3 · Run perf over the merged DA-53…DA-56 package and fix what it finds

- **Order:** 370
- **Scope:** 11-perf (see [reference](../../reference/README.md))
- **Created:** 2026-09-10
- **Dependencies:** none

## Context

`bun run perf` is one of the six gates. Partway through the package of DA-53…DA-56 the owner moved it out of the per-task gates and into a single pass after all four, so that the run would stop paying for a browser benchmark on every acceptance. Then the package finished and the owner chose to close it without that pass, deferring the performance work here.

So four tasks reached the main branch on **five of six gates**, and this entry is the sixth.

What is known, and what it is worth:

- DA-53 and DA-54 were each measured before the decision. On the merge commit that carried both, the whole gate passed: CPU per frame **7.8 ms** against the 8.3 ms budget, every line inside, at a load average of 20.5.
- DA-55 measured itself against its own base and came out better on every line — CPU per frame 8.0 against the base's 8.3, session switching 89.8 against 109.3. That comparison also caught a real regression it had introduced and fixed: the skeleton was being mounted between two reviews, costing 40 ms on a switch.
- Between DA-55's two commits the update line stepped from 260 ms to 341 against a 300 ms budget, held across three machine states, and the cause was never found. That is [DA-55.2](../../archive/DA-55.2-update-budget-step-up/task.md), and it is the one number that was over budget when anybody last looked.
- DA-56 was never measured at all. Its own report says so plainly: the history row grew heavier — up to six chips, a filter on every render, `data-session-status` and a focus restore on each press — and "I cannot claim it is free, I did not measure it."

## Work to do

- Run `bun run perf` on the merged main and record every line with the load average beside it. On this machine that needs `DIFFALANCHE_DATA_DIR=.diffalanche` until [DA-54.1](../active/DA-54.1-e2e-fixture-ignores-user-config.md) lands.
- Read the result against the numbers above rather than against the budget alone: `updateMs` is the line already known to be over, and `cpuPerFrameMs` has about half a millisecond of headroom on a quiet machine ([DA-54.3](DA-54.3-perf-budget-headroom.md)).
- Whatever is over, attribute it before fixing it. Four tasks are merged now, so a red line does not say whose it is; the base to compare against is `1193ab3`, the commit the package started from.
- [DA-55.2](../../archive/DA-55.2-update-budget-step-up/task.md) folds into this pass if the step is still there: its own entry exists because the measurement was deferred, and this is the deferred measurement.

## Out of scope

- Adding a budget for `sessions-changed` ([DA-56.1](DA-56.1-sessions-changed-has-no-budget.md)) — a different question, though this pass is a natural moment to settle it.

## Folded in: DA-55.2 · The update budget stepped from 260 ms to 341 ms inside DA-55's review round, and the cause was never found

Merged 2026-09-18 during the pre-run triage: this pass is the deferred measurement DA-55.2 asked for. Its text follows in full.

### Context

DA-55 was measured twice: once when its code first landed, and once after the review round. Between the two, `Update after an edit in one repository` moved from inside its budget to over it.

| | first render | scroll CPU/frame | jump to a file | switching sessions | **update after an edit** |
|---|---|---|---|---|---|
| budget | 500 ms | 8.3 ms | 50 ms | 100 ms | **300 ms** |
| `fd6e2d1`, before the round | 84.9 | 8.0 | 12.0 | 89.8 | **260** |
| `bbe1c5a`, after it | 85.7 | 8.1 | 9.4 | 82.8 | **341 — FAIL** |

Every other line stayed put or improved. Three runs of three on `bbe1c5a` gave 344/341/341, 365/329/329 and 338/331/331, at load averages of 8.6, 4.9 and 5.4 — a step that holds across three different machine states rather than a number that wanders with load.

That brackets the cause to the review round itself, whose diff is small: one overlay rendered at a time instead of two, `markSelfSession` in `applyScope`, `aria-pressed="mixed"`, the confirmation applying its own scope, a failure screen for a bad `?review=`, and `freshRepository` on the server. The worker looked for a suspect among them and found none: `repository(repo, undefined)` still goes the old way through `current()` and never enters `freshRepository`, and `CentrePanel` gained no subscriptions — it lost some.

**What weakens the evidence, stated plainly:** the 260 ms of `fd6e2d1` was measured in an earlier session under different machine conditions and was not re-measured beside the 341. One run on `fd6e2d1` would have settled it in under a minute; it was not done, because the owner decided during this run that `perf` moves to a single pass after all four tasks. The cost of that trade is recorded here rather than argued: attribution is cheap while the two commits are one branch apart, and expensive once several tasks are merged.

### Work to do

- Re-measure `fd6e2d1` and `bbe1c5a` back to back on the same machine state. If the step survives, bisect the review round — it is six changes, so three runs settle it.
- If it does not survive, the entry closes with the numbers and the earlier reading is written off as machine state. That is a legitimate outcome and should be recorded rather than left as a suspicion.
- Whatever it turns out to be, the update path is the one budget a live review leans on hardest: it is the one that runs on every save while somebody is reading.
