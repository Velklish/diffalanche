# DA-56.6 · The 35% step in the update budget is DA-55's commit, and the cause inside it is not found

- **Order:** 710
- **Scope:** 08-ui, 05-watcher (see [reference](../../reference/README.md))
- **Created:** 2026-09-21
- **Cost:** major
- **Dependencies:** none

## Context

[DA-56.3](../../archive/DA-56.3-perf-pass-over-the-package/task.md) closes on attribution,
not on a fix. It attributed the step; this entry is the fix.

`Update after an edit in one repository` is budgeted at 300 ms and is the one
budget a live review leans on hardest: it runs on every save while somebody is
reading. Thirteen `bun run perf` runs on 2026-09-21, one 8-core M1 Pro, load
average 7.6 to 10.8 throughout, the machine otherwise idle:

| commit | task | update after an edit |
|---|---|---|
| `1193ab3` | before the DA-53…56 package | **244, 267, 286 ms** ok |
| `2925a19` | DA-54 | **283 ms** ok |
| `4be4936` | DA-53 | **297 ms** ok |
| `1079222` | **DA-55** | **334 ms** FAIL |
| `a8d673b` | DA-56 | 344 ms FAIL |
| `c9305e1` | DA-57 | 315 ms FAIL |
| `fa004df` | DA-78 | 323 ms FAIL |
| `7308efa` | DA-90 | 334 ms FAIL |
| `ed81928` | the tip | 347, 352, 392 ms FAIL |

Everything up to and including DA-53 is at or under 297 ms; everything from
DA-55 on is at or over 315. The separation is clean, it is about 35 % of the
lower group, and it is one commit: **`1079222`, DA-55.**

That confirms rather than contradicts
[DA-55.2](../../archive/DA-55.2-update-budget-step-up/task.md), which bracketed
the step to DA-55's own review round and could not prove it because the two
sides were never measured beside each other. Both commits of that round are
inside `1079222`.

`DA-90`, whose title names an added directory flush on every atomic write and
which was the one suspect a reading of the titles produced, is innocent: the
step is already there four commits before it.

**What weakens this, stated plainly.** One run per commit, not three — the
separation is wide enough that a median of three would have to move 18 ms to
close it, but it is one run. The nine-point pass shared one fixture, and the two
oldest points had to be re-measured with that fixture reset to what the
generator writes, because they cannot read a `diff.json` written by the schema
DA-53 introduced; the reset does not flatter the number (`1193ab3` gave 244 ms
reset and 286 ms unreset). Every point needed `DIFFALANCHE_DATA_DIR=.diffalanche`,
because `fixtureEnv()` arrived with DA-54.1, late in this range.

## Work to do

- Read `git diff 4be4936..1079222` over the paths `updateMs` actually measures —
  the watcher, the event stream, and the store's `applyRepositoryDiff` — rather
  than over the whole commit. What the harness times is the watcher, the
  debounce, the rescan, the stream, the fetch, the patch, and the paint, so a
  change anywhere else in DA-55 is not a candidate.
- DA-55.2's own worker already looked for a suspect among the review round's six
  changes and found none, and named what it checked: `repository(repo, undefined)`
  still goes through `current()` and never enters `freshRepository`, and
  `CentrePanel` gained no subscriptions. Start after that, not before it.
- Confirm the step with three runs on `4be4936` and three on `1079222` back to
  back before changing anything: this entry has one run per point, and a fix
  aimed at 37 ms deserves a median.
- The budget is 300 ms and the tip is at 347: a fix has to give back the whole
  step, not half of it.

## Verification

- `bun run perf` on a quiet machine measures the update line inside 300 ms,
  three times, on the tip of the main branch.
- The cause is named in the result with the share of the 37 ms it accounts for,
  measured rather than reasoned about; a fix that moves the number without a
  named cause is a fix nobody can maintain.
