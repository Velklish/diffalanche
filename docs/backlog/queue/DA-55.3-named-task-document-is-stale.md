# DA-55.3 · A named task's document is built from a cache the watcher never refreshes, so reloading it shows an old change set

- **Order:** 180
- **Scope:** 07-server, 05-watcher (see [reference](../../reference/README.md))
- **Created:** 2026-09-10
- **Dependencies:** none

## Context

Found in DA-55, and it is the half of a defect whose other half that task fixed.

The watcher rescans and rewrites `diff.json` for the **current** session only: `rescanRepository(config, session, …)` in [src/core/watcher/index.ts](../../../src/core/watcher/index.ts) takes its `session` from `readCurrent()`. A task that is not current therefore holds a change set frozen at the moment it was last read.

`build(config, session)` trusts that cache when `sameBase` and `sameScope` match — and they do, because neither the base nor the scope changed; only the code did. Nothing compares the cache against the working tree. So `GET /api/review?review=<name>` answers with the change set as of the last read, and a person who edits code and reloads a window on that task sees the diff they saw before the edit.

DA-55 found this by measuring rather than by reasoning. A window on a named task answered a live update **faster** than a window on the current session — 253 ms against 275 — and the reason was that it was answering with nothing: the card of the edited file did not show the edit, three times out of three, because the patch came from the frozen cache and the page found nothing to apply. That is the shape of the defect: it reads as a good number.

DA-55 fixed the live-update route by reading the one repository from the working tree (`freshRepository`), so a task's window now patches correctly while it stays open. **The document route was left alone deliberately:** rebuilding it means reading every repository in the scope, which is a different cost from reading the one that changed, and doing it on every open would undo the reason `other()` avoids keeping state at all.

So today: a window on a task is right while it is open, and can be wrong the moment it is opened.

## Work to do

- Decide what `GET /api/review?review=<name>` owes the reader. The options are not equal:
  - **Rescan the scope when the cache looks old.** Correct, and the cost is the scope's repositories rather than the root's — a task over two repositories pays for two. Needs something better than `sameBase && sameScope` to decide "old"; the working tree's own mtimes are the cheap candidate.
  - **Let the watcher follow the tasks windows are open on**, which is [DA-55.1](DA-55.1-watcher-follows-one-session.md) — the same fix serves both, and the two entries should be read together before either is taken.
  - **Say so on screen.** Cheapest and honest: the window knows it is on a named task and can say the change set is as of a time. It does not fix anything, and it is the option to reject if either of the others is taken.
- Whichever is chosen, the trap this defect sets has to be written down where the next reader of `other()` will see it: a cache that matches on base and scope is not thereby fresh.

## Out of scope

- The live-update route, fixed in DA-55 by `freshRepository`.
- Making the watcher follow several sessions ([DA-55.1](DA-55.1-watcher-follows-one-session.md)) — related, and possibly the same fix, but its own entry.

## Verification

- A window opened on a task whose code changed since that task was last read shows the change, not the change set of the previous read.
- The cost of opening a task is proportional to its scope, not to the root: a task over two of twenty-one repositories does not read the other nineteen.
- A window on the current session is unaffected by whatever is done here — same numbers before and after.
