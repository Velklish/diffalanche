# DA-34.2 · A brute-force query on Bun crosses ADR-014's memory ceiling past about 20 000 comments

- **Order:** 780
- **Scope:** 09-ml, 11-perf (see [reference](../../reference/README.md))
- **Created:** 2026-09-23
- **Parent:** DA-34
- **Cost:** minor

## Evidence

Finding discovered while working on DA-34. ADR-014 holds a process that loads
the model and embeds 200 comments to 768 MiB peak resident size:

<!-- quote:../../adr/adr-014-embedding-model-and-npm-delivery.md -->
- **Memory ceiling: 768 MiB** peak resident size for a process that loads the
  model and embeds 200 comments. The highest of the 16 runs of this pair was 651
  MiB, and the ceiling is 18 % above it.
<!-- /quote -->

A query over the index loads the model, reads `index/index.bin` whole and
searches it in memory, so its peak grows with the number of comments. Measured
on 2026-09-23 on the development machine (Apple M1 Pro, 8 cores, 16 GB; load
averages 8–19 on 8 cores, other agent runs sharing it), with
`/usr/bin/time -l <runtime> perf/index-scale.ts query --data-dir <d>`, the
10 000-comment index built by `index rebuild` over 50 copies of the synthetic
review's session and the 20 000 and 50 000 ones by
`perf/index-scale.ts fake`:

| Peak resident size | Bun 1.3.14 | Node 25.2.1 |
|---|---|---|
| the model alone: load, then one text embedded | 714 MiB | 697 MiB |
| a query over 10 000 comments (two runs) | 735, 736 MiB | 682, 692 MiB |
| a query over 20 000 | 736 MiB | 669 MiB |
| a query over 50 000 | **803 MiB** | 687 MiB |

**What the model weighs and what a comment adds.** The model's load is most of
the peak: 697–714 MiB here, 476–650 MiB in ADR-014's runs on the same machine
under other memory pressure. A comment adds a row of 384 `float32`, 1536 bytes,
plus its entry — session, id, severity, anchor and text — in the JSON line and
as a parsed object. On Bun, from 20 000 to 50 000 comments the peak rose 67 MiB,
about **2.3 KB per comment**; up to 20 000 the index's share stayed under the
transient of the model's load (10 000 and 20 000 peak alike). On Node the peak
is the load's transient at every size measured, which is why it barely moves.

So on the binary channel a query crosses 768 MiB somewhere between 20 000 and
50 000 comments — about 34 000 if the 2.3 KB per comment holds from 20 000 on,
which is an extrapolation and was not measured. The search itself stays under
the card's 50 ms to 100 000 comments on both runtimes
([09-ml.md](../../reference/09-ml.md#how-far-brute-force-goes)), so memory is
the bound, not speed. `index rebuild` of 10 000 comments peaked lower, at 680
MiB on Bun and 618 MiB on Node.

**The server comes closer than a command.** DA-35 measured `serve` after its
first `/api/suggest` with `perf/index-scale.ts serve` on a copy of the full
synthetic review — 240 comments in two sessions, the index built by that first
request — two runs a runtime, alternating, on 2026-09-24 at load averages of
6.6–15 ([09-ml.md](../../reference/09-ml.md), "The server's memory"):

| `serve` after the first suggestion | Bun 1.3.14 | Node 25.2.1 |
|---|---|---|
| peak, `/usr/bin/time -l` | 742 and **764 MiB** (777 732 096, 801 472 512 bytes) | 659 and 657 MiB |
| first suggestion | 2.3 and 2.4 s | 2.1 and 2.2 s |
| warm suggestions | 4–5 ms | 4–6 ms |

On Bun the server comes within 4 MiB of the ceiling with 240 comments, so a
larger history crosses it on the binary channel sooner than a query does.

## Decision

On 2026-09-24 the owner decided, on the numbers above: DA-34, DA-34.1 and DA-35
land as they are; the memory work is this entry, moved to the queue; ADR-014 is
not changed, so its 768 MiB ceiling stands for the query and the server alike.

## Work to do

- Bring the query and the server under ADR-014's ceiling on both runtimes. The
  candidates the owner named to weigh are an int8 model, the model in a process
  of its own, and unloading the model when it is idle; for the index's own
  share, mapping the vectors file instead of reading it, or keeping the vectors
  in `float16`. Which of them is taken is the owner's choice, not a worker's.
- Measure again with `perf/index-scale.ts`: `query` at 20 000, 50 000 and
  100 000 comments, and `serve` after the first suggestion, on both runtimes.
