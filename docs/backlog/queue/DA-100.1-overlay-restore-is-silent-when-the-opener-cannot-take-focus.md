# DA-100.1 · The overlay's focus restore does nothing, silently, when the opener cannot take the ring

- **Order:** 215
- **Scope:** 08-ui (see [reference](../../reference/README.md))
- **Created:** 2026-09-18
- **Dependencies:** none
- **Cost:** major

## Context

Found while closing [DA-100](../../archive/DA-100-overlay-captures-the-opener-during-render/task.md), whose
"Work to do" asks for exactly this and which this entry carries the rest of: *"make the silent no-op
at Overlay.tsx:143 impossible to reach unnoticed: a detached opener today is indistinguishable from a
successful restore."* DA-100 moved the opener from an `Overlay` instance to a **ladder**, which
removes the case it traced — the editor → confirmation → editor round-trip, where each swap recorded
the button it was replacing. The no-op itself is untouched.

[src/ui/components/Overlay.tsx](../../../src/ui/components/Overlay.tsx), in `leaveLadder`:

```ts
    const back = OPENERS.get(ladder) ?? null;
    OPENERS.delete(ladder);
    if (back instanceof HTMLElement && back.isConnected) back.focus({ preventScroll: true });
```

When the condition is false nothing happens at all, and nothing says so. The reference promises the
opposite — [08-ui.md](../../reference/08-ui.md): "when the overlay closes, by `esc`, by the scrim, or
by finishing what it was for, the focus goes back to the control that opened it." The reader is left
on `<body>` and the next `Tab` starts from the top of the page.

`isConnected` is also the weaker of the two conditions. A control still in the document but
**disabled** passes it, and `.focus()` on a disabled element does nothing — so the guard lets the call
through and the ring still goes nowhere.

**A candidate path, traced through the code and not observed in a browser.** It is written as a
hypothesis for that reason. `New task…` in select mode opens the form; `createSession`
([src/ui/store.ts](../../../src/ui/store.ts)) sets `newTaskOpen: false` **before** `await
showTask(name)`, so the form unmounts and the restore is scheduled on a macrotask. The review then
arrives, `fromDocument` takes the `switched` branch and clears `selectDraft`, and the select bar's
button becomes `disabled={empty}`
([src/ui/components/Sidebar.tsx](../../../src/ui/components/Sidebar.tsx)). Whether the scheduled
restore runs before or after the server's answer is what decides it, and that has not been measured.
Nothing in the suite asserts where the ring goes after a task is created from select mode.

## Work to do

- Decide what the restore does when the opener cannot take the ring, and write it beside the promise
  in `08-ui.md`. "Somewhere sensible" is what `<body>` already is, so the fallback has to be named: a
  landmark of the workspace, the control that now stands where the opener stood, or an explicit
  decision that this case is acceptable and the promise is narrowed to say so.
- Make the case observable. A restore that does nothing is currently indistinguishable from one that
  worked; whatever the answer is, the code should not be able to reach it silently.
- Check the disabled case with the `isConnected` one: they are two conditions and only one is tested.

## Out of scope

- The ladder itself and the opener it records, which DA-100 settled.
- The focus trap, which works and is asserted in `e2e/scope.spec.ts`.
- Changing when `createSession` clears `selectDraft`: the candidate path above is a symptom to
  reproduce, not the thing to fix.

## Verification

- The path above is reproduced or ruled out first, in a browser, with the element that holds the ring
  after a task is created from select mode written down. The entry is a hypothesis until then.
- Once the fallback is decided, a Playwright case closes an overlay whose opener has gone or been
  disabled and asserts the ring is where the decision says, not on `<body>`.
- Gates: `bun run lint`, `bun run typecheck`, `bun run test`, `bun run test:bun`, `bun run test:ui`.
