# DA-69.1 · The long-task budget line flips its verdict with the machine's load, not with the code

- **Order:** 740
- **Scope:** 11-perf (see [reference](../../reference/README.md))
- **Created:** 2026-09-21
- **Cost:** major
- **Dependencies:** none

## Context

Finding discovered while working on DA-69, which is about the gate reporting
`ok` for what it did not measure. This is the mirror: the gate reporting `FAIL`
for what it did not measure.

`Scrolling the diff: long tasks` has a budget of zero, and the `tasks` unit is
deliberately not widened by `RUNNER_ALLOWANCE` — 11-perf.md calls it "a count of
zero on every machine". It is not. Fifteen `bun run perf` runs on 2026-09-21,
one 8-core M1 Pro, three trees (a wave-2 branch, `ed81928`, `1193ab3`), with the
one-minute load average recorded at both ends of every run:

| tree | load average, busier end | long tasks | verdict |
|---|---|---|---|
| branch | 37.4 | 4 | FAIL |
| `ed81928` | 32.9 | 0 | ok |
| branch | 26.0 | 0 | ok |
| `ed81928` | 15.1 | 1 | FAIL |
| branch | 19.6 | 0 | ok |
| `ed81928` | 68.2 | 1 | FAIL |
| `ed81928` | 56.0 | 1 | FAIL |
| branch | 6.4 (quiet window) | 1 | FAIL |
| `ed81928` | 9.4 (quiet window) | 0 | ok |
| `1193ab3` | 10.3 (quiet window) | 0 | ok |
| branch | 10.3 (quiet window) | 0 | ok |
| `ed81928` | 8.8 (quiet window) | 0 | ok |
| `1193ab3` | 7.6 (quiet window) | 0 | ok |

The sign does not follow the tree. The same commit `ed81928` produced 0 at a
load of 32.9 and 1 at 15.1; the same branch produced 4 at 37.4 and 0 at 19.6,
and then 1 in the quietest window of the session and 0 in the next run of that
same window. A budget line that answers differently twice in a row on one commit
is not gating that commit.

DA-54.3's load precondition narrows this and does not close it: the quiet-window
reading of 1 was taken at 0.80 per core, well inside the 2.5 ceiling.

The median over three repetitions is what the gate compares, so a single
repetition's long task does not fail the run — two of three do. The readings
above are medians, so a `1` there means at least two repetitions of that run saw
a long task.

## Work to do

- Decide what this line is asking. A count of zero over a 600-frame scroll is a
  statement about the page's worst frame, and on a machine that is scheduling
  other work the worst frame is not the page's. The options are not equal:
  - **Report the long tasks' total duration beside the count** and budget that
    instead — `scrollLongTaskMs` is already measured and already in the
    `Measurement`, and it separates "one 51 ms task" from "one 400 ms task".
  - **Keep the count and give it the same treatment as the millisecond lines**:
    a long task under some duration is not one for the gate's purposes.
  - **Leave it and accept the flapping**, with the entry recording why. Only if
    the count is meant to be a tripwire that a human reads rather than a gate.
- Whatever is chosen, 11-perf.md's "a count of zero on every machine" has to
  stop saying what the measurements contradict.

- Three `bun run perf` runs on one commit at one machine state give the same
  verdict on this line three times.
- The reading that made this entry — a long-task count of 1 at 0.80 per core —
  either does not recur or fails the gate for a reason the output names.
