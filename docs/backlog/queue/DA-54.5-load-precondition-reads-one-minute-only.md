# DA-54.5 · A gates chain accelerates the machine into the zone where wall-clock assertions go red, and the load precondition cannot see it coming

- **Order:** 720
- **Scope:** 11-perf (see [reference](../../reference/README.md))
- **Created:** 2026-09-21
- **Cost:** major
- **Dependencies:** none

## Context

[ADR-013](../../adr/adr-013-perf-gate-off-ci.md) gave `bun run perf` a load
precondition: above `LOAD_CEILING` runnable tasks per core the gate declines to
produce a verdict rather than producing a wrong one. It reads the one-minute
average before the run and again after it and takes the busier of the two.

The refusal half works. The other half — what makes a **non**-refusal honest —
does not, and three runs on 2026-09-21 show it from both sides.

**1. The refusal, working as designed.** In a `backslop gates` chain on
`a009129`:

```
$ bun run perf
unable to measure: load average 24.638671875 over 8 cores is 3.08 per core,
ceiling 2.5 before the run. …
exit 1 after 321 ms — before the fixture and before the browser.
```

**2. A non-refusal on a machine that was not quiet.** The same branch, twenty
minutes later, given a window in which no other work was running and after a
five-minute wait for the one-minute average to fall:

```
QUIET-WAIT 303s load1=6.19
21:56  load averages: 6.19 12.50 19.12      ← at the start of the run
21:56  load averages: 9.27 12.43 18.75      ← at the end of it
```

0.77 per core before and 1.16 after, both far inside the 2.5 ceiling, so the
gate answered. What it answered:

| line | budget | this run | the same branch in a genuinely quiet window |
|---|---|---|---|
| CPU per frame | 9.5 ms | **10.2** FAIL | 8.6–9.0 |
| update after an edit | 300 ms | **380** FAIL | 321–347 |

The one-minute average had decayed to 6.19 while the five- and fifteen-minute
averages stood at 12.50 and 19.12: the machine was still working through the
queue of the previous worker's gates chain. **Both ends of the check read
"quiet" and the numbers are 1.2 ms and 40 ms worse than the same branch
measures when the machine really is idle.**

**3. The magnitude of what gets through.** A neighbouring worker's
`bun run perf`, entering its chain at a one-minute average of 9.89 and ending it
at 24.69, reported `update` 575 ms; the same sha measured on its own, minutes
later, reported 257.9 ms. That tree is branched from `ed81928` and carries no
precondition at all, so it is evidence about the size of the noise and not about
this mechanism — but 575 against 258 is the size.

**Why a `gates` chain makes this worse rather than better.** `perf` is the last
of the seven gates, and the two before it are `bun run test:bun` and, since
DA-54.2, `bun run test:ui` — a full browser suite that runs for 93 seconds. The
one-minute average at the moment `perf` starts is mostly the tail of those two.
Case 1 is that tail refusing the run; case 2 is that tail decayed just below the
ceiling and spoiling it instead. **`gates 7, green 7` in one pass is not
reachable for anyone while this holds.**

**4. And it is not only `perf`: the chain reddens any assertion that measures
time.** A twelve-run pass by a neighbouring track on 2026-09-21 set out to test a
different hypothesis and disproved it: five verdicts in `tests/events.test.ts`
and `tests/watcher.test.ts` went red on **both** trees it compared, in every
configuration, at a load average around 30, **no two of them twice**, and all
five are wall-clock waits. A `gates` run of this branch the same evening added
three more of the same shape:

| verdict | gate | the same suite, next gate |
|---|---|---|
| `cli.test.ts > output piped into a reader that stops early > ends at 0 with an empty stderr…` | `bun run test` 582/585 | |
| `events.test.ts > the live stream > carries a reply written by the CLI…` | `bun run test` | |
| `watcher.test.ts > watcher > rescans the edited repository alone and has the new hunk in diff.json in time` | `bun run test` | |
| — | | `bun run test:bun` **585/585**, same tree, same chain, minutes later |

The same suite on the other runtime, immediately after, was green on all 585.
So the defect is wider than the line this entry was opened for: **a `gates`
chain accelerates the machine it runs on, and by the fourth command the machine
is in the zone where a wall-clock assertion is a coin toss.** `perf` declining
last is the most visible case and not the only one — it is merely the one gate
that was given eyes.

That also means the load precondition, wherever it ends up, is not only a
`perf` question: it is the first instance of a problem the whole gate list has.

## Work to do

- Decide what the gate reads. The one-minute average is a lagging, coarse
  indicator and the run it guards is 40–55 seconds long. Candidates, and the
  choice is the decision this entry records:
  - **Read the longer averages too** and refuse when the five-minute figure says
    the machine is still working through a queue the one-minute figure has
    forgotten. Cheapest, and it would have caught case 2 — 12.50 over 8 cores is
    1.56 per core, which a second, looser ceiling would refuse.
  - **Wait for quiet inside the gate**, with a ceiling on the wait, instead of
    refusing immediately. Turns a refusal into a delay, which is what a person
    wants from a gate; the cost is a gate that can sit for minutes.
  - **Run `perf` first in the chain**, before the suites, so the machine it
    measures is the one the developer handed it rather than the one the previous
    six gates left. One line in `gates`, and it does nothing for a machine busy
    for other reasons.
  - **Take a metric shorter than the one-minute average** — sampled CPU idle
    over the seconds before the run. The most accurate and the least portable.
- Whichever is chosen, the verdict has to stay distinguishable: a number taken
  on a machine that was not quiet must not print as `ok` or as `FAIL` without
  saying so, which is what ADR-013 already established for the refusal.
- Decide whether the answer belongs to `perf` alone or to the gate list. Eight
  wall-clock verdicts across two tracks say the latter, and the cheapest form of
  the latter is ordering: `perf` and the timer-sensitive suites do not have to
  run after the three heavy ones. Giving every gate its own precondition is the
  expensive form and probably the wrong one — a chain that declines in four
  places is a chain nobody can get green.
- **Read this beside [DA-60](DA-60-flaky-test-hardening.md), which is the same
  problem from the other end.** This entry says the chain drives the machine
  into the zone where a timed assertion is a coin toss and the precondition
  cannot see it coming; DA-60 says those assertions measure wall-clock time
  where they could be measuring a condition. Either fix alone narrows the
  failure; the pair closes it, and whoever takes one should know the other
  exists. The verdicts catalogued there and the ones named here are the same
  verdicts.

## Out of scope

- The ceiling's own number, 2.5 per core, which ADR-013 measured. Nothing here
  says it is wrong — case 2 passed it on both ends, which is the point.
- Rolling back the refusal. It works, it is cheap, and the owner chose it; this
  entry is the missing second half, not a reversal.
- The two lines that came out red in case 2. Both are already attributed and
  neither belongs to the branch that measured them:
  [DA-56.4](../../archive/DA-56.4-cpu-per-frame-misses-its-budget-at-rest/task.md) and
  [DA-56.6](DA-56.6-update-step-lives-in-da-55.md).

## Verification

- A `bun run perf` started at a one-minute average under the ceiling but a
  five-minute average well over it either refuses, or waits, or prints that the
  verdict is not evidence — and does not print a plain `FAIL`.
- `npx github:Velklish/backslop#v0.9.0 gates` reaches `gates 7, green 7` in one
  pass on a machine with nothing else running on it — which no run of
  2026-09-21 managed, on any of the three tracks.
- The eight wall-clock verdicts named above pass three times in a row inside a
  full chain, not only when their file is run on its own.
