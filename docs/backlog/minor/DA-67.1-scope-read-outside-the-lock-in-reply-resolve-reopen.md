# DA-67.1 · `reply`, `resolve` and `reopen` read the scope outside the lock

- **Scope:** 04-domain
- **Created:** 2026-09-21
- **Parent:** DA-67
- **Cost:** minor

## Evidence

DA-67 moved the scope check of `addComment` inside the lock. The other three
comment writers still read it outside and use it inside:

<!-- quote:../../../src/core/domain/comments.ts -->
```ts
  await assertSession(dataDir, session);
  const scope = await sessionScope(dataDir, session);
  return updateComments(dataDir, session, (comments) => {
    const comment = find(comments, id, scope);
```
<!-- /quote -->

`grep -n "const scope = await sessionScope" src/core/domain/comments.ts` finds it
at three write sites — `reply`, `resolve` and `reopen` — and at two read sites,
`get` and `list`, where a read of a moment that has passed is what a read is.

It is `minor` rather than `major` because the damage the parent describes cannot
follow from it. `setScope` deletes the comments that fall outside a narrowing in
the same write, under the same lock, so there is no state in which a comment sits
in `comments.json` outside the scope for `find` to reach with a stale wide scope:
it re-reads the comments inside the lock and does not find the comment at all,
which is the right answer. What a stale scope can produce is the opposite and
harmless direction — a scope **widened** between the read and the lock gives a
comment that is now in scope a `no-such-comment` it would not get a moment later.
A spurious refusal that a retry fixes, not a write nothing can read back.

## What it would take

`find` would have to take its scope from `draft.review`, which means the three
move from `updateComments` to `updateSession` the way `addComment` did. That is
the whole change; the question worth answering first is whether a refusal that
can be one retry stale is worth three writers leaving the entry point that
"deliberately exposes only the comments"
([03-storage.md](../../reference/03-storage.md)).
