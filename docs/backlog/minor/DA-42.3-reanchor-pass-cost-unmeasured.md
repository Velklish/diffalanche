# DA-42.3 · The re-anchoring pass after every changing rescan is not measured against the update budget

- **Scope:** 05-watcher, 11-perf (see [reference](../../reference/README.md))
- **Created:** 2026-09-29
- **Parent:** DA-42
- **Cost:** minor (hypothesis)

## Evidence

A hypothesis, not measured: DA-42's brief said to measure nothing in perf, and the worker ran no
`bun run perf`.

Every write of `diff.json` now re-anchors in the same hold of the session's lock
(`docs/reference/05-watcher.md`, "Re-anchoring" and "Budget"): a read of `review.json` and
`comments.json` — about 100 KB on the synthetic review's 200 comments — and, per changed file with a
line comment, a read of the file; for a comment not in place, a read of its base and a `git blame`
with its `config --list`; then a `comments.json` write when anything moved, which comes back as a
burst of the data directory, `comment-status` frames, and a thread re-read per moved comment on an
open page. The rescan sends `diff-changed` before the pass, so the update the person sees does not
wait for it; the next rescan, and every other writer of the session, does, since the pass holds the
lock and the rescan queue.

**The perf harness would not exercise the pass.** `perf/harness.ts` measures an edit by appending
`PROBE_LINE` to the end of a file, so a comment on that file is in place after the edit — one read of
the file, no blame — and a file with no comment costs the two reads of the session's small files and
nothing else. A number from it says nothing about a comment that moved.

Check: `bun perf/compare.ts` of DA-42's commits against their base on the development machine, with
an edit that inserts lines above a line comment of the synthetic review, and a second edit to
another repository inside the first one's pass; if the update line of the second moves by more than
its spread, the pass waits for the lock to be free of a rescan queued behind it, or is folded to one
per burst window.
