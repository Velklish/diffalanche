# DA-56.12 · An edit a named task's path scope covers and the current one's does not reaches no window on that task

- **Scope:** 05-watcher, 07-server (see [reference](../../reference/README.md))
- **Created:** 2026-09-29
- **Parent:** DA-56.6
- **Cost:** major (hypothesis)

## Evidence

Finding raised by the review of DA-56.6. It is older than DA-56.6 and outside it. It was reasoned from the code and has not been reproduced.

Take repository `R` and two tasks. Task `X` is not current, and its path-level scope covers `R/B`. The current task's scope covers `R` but only `R/A`. A window is open on `?review=X`, and somebody edits `R/B`.

1. The watcher rescans `R` for the current session only. `rescanRepository` filters the read by the current task's scope and compares it with the cached entry. Without `R/B` the entry is the same, so it returns `changed: false`, and the callback that calls `onRepositoryChanged`, emits `diff-changed` and records activity is never run:

<!-- quote:../../../src/core/watcher/index.ts -->
    const rescanned = await rescanRepository(config, followed, repo, (outcome) => {
      options.onRescan?.(followed, outcome.cache);
      if (followed === session) scanWarnings = outcome.cache.warnings;
      // From inside the rescan, so it says the change set moved rather than
      // that a file was written: a save with the same bytes reaches no one.
      options.onRepositoryChanged?.(repo);
      bus.emit({ type: "diff-changed", repo, files });
<!-- /quote -->

2. The fallback does not catch it either. It fires only for a repository not yet in `settled`, and `settled` starts out holding every repository of the startup scan. It is cleared only when `current` moves:

<!-- quote:../../../src/core/watcher/index.ts -->
    if (!rescanned.changed && !settled.has(repo)) options.onRepositoryChanged?.(repo);
<!-- /quote -->

3. So `ReviewService.repositoryChanged("R")` is not called. `X`'s held document keeps its old change set, and the window on `X` gets no frame. The edit shows up only once something else drops that document: a burst of the data directory that changes `X`'s files, a move of `current`, or a reload after the document has left the four-entry cache.

What weakens it: it has not been reproduced, and it needs two tasks with overlapping path-level scopes. A task scoped by repository only, or a current task about the whole root, does not have the gap. Whether `settled` already holds `R` in every such case, and not only after the startup scan, was read from the code and not observed.

## Work to do

- Reproduce it at the service level: a watcher with `current` scoped to `R/A`, a held document of `X` scoped to `R/B`, an edit to `R/B`. Does `repositoryChanged` fire, and does a window on `X` get a frame?
- If it reproduces: when a rescan finds the current task's filtered entry unchanged, call `onRepositoryChanged(repo)` anyway whenever another held or followed task's scope covers a changed path of `R`. That drops `X`'s held document without costing the current task anything. Add a test that covers both scopes.

## Verification

- A test in which an edit covered only by a non-current task's path scope drops that task's held document and reaches a window on it, and goes red without the fix.
