# DA-96.1 · A stream the browser has closed leaves the footer saying watching

- **Scope:** 08-ui (see [reference](../../reference/README.md))
- **Created:** 2026-09-23
- **Parent:** DA-96
- **Cost:** minor

## Evidence

Found while pinning the connection state for DA-96, which put changing it out of
scope. `onerror` sets `reconnecting` only while the browser is retrying:

<!-- quote:../../../src/ui/live.ts -->
```ts
  source.onerror = () => {
    if (source.readyState !== EventSource.CLOSED) store().setConnection("reconnecting");
  };
```
<!-- /quote -->

When the browser has given up — `readyState` is `CLOSED` — nothing is set, so a
page that was `watching` keeps the green pulsing dot and the word `watching`
while no frame will ever arrive again. `tests/ui-live-recovery.test.ts` pins
exactly that ("leaves the footer as it was once the browser has given up"), as
DA-96 asked, which is why this is recorded rather than changed there.

**Reachability is an assumption, not measured.** An `EventSource` closes for
good when a reconnect is answered with a status other than 200 or a content type
other than `text/event-stream`. `streamEvents` in `src/server/events.ts` never
refuses a stream itself, so the cases left are something other than this server
answering the port after a restart, or the route failing before the stream
starts. Neither was produced here.

`PRODUCT.md` principle 5, "nothing is silently lost", is the rule the footer
would be breaking: live update stopping is shown only by the absence of updates.
A fix is a state of its own — say, `disconnected`, with a way to reconnect — and
a decision about what the footer offers, which is why it is not a one-line
change.
