# DA-58.2 · check-ignore reads the user's ignore file only at its default place, not a global core.excludesFile

- **Scope:** git reader, watcher ([02-git.md](../../reference/02-git.md), [05-watcher.md](../../reference/05-watcher.md))
- **Created:** 2026-09-28
- **Parent:** DA-58
- **Cost:** minor (hypothesis)

## Evidence

Found while moving the JSDoc of `checkIgnore` in `src/core/git/run.ts` into
[02-git.md](../../reference/02-git.md), "Asking what git ignores". The moved text
says the rules include "the user's ignore file". `checkIgnore` runs git with
`readOnlyEnv()`, which points `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` at the
null device ([02-git.md](../../reference/02-git.md), "What the reader trusts"),
so a `core.excludesFile` set in `~/.gitconfig` is never read. The hypothesis is
that git still falls back to `$XDG_CONFIG_HOME/git/ignore` (default
`~/.config/git/ignore`) when `core.excludesFile` is unset, so "the user's ignore
file" holds only at its default place. This is not verified: the worker's
container refused a git run outside its worktree.

Cost if true: a path ignored only by a global `core.excludesFile` is not
suppressed, so a build writing there costs a rescan that finds nothing. The
watcher over-reports; it never misses a change. The fix is a sentence in
02-git.md, or a decision to pin `core.excludesFile` the way the other keys are.

To check: in a scratch repository, put `x` in `$XDG_CONFIG_HOME/git/ignore` and
`y` in a file named by `core.excludesFile` in a config file, then run
`printf 'x\ny\n' | GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null git check-ignore --stdin`.
Expected under the hypothesis: `x` only.
