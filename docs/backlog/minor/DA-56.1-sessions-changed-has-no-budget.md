# DA-56.1 · No performance budget covers sessions-changed, the event the history mark rides on

- **Scope:** 11-perf, 08-ui (see [reference](../../reference/README.md))
- **Created:** 2026-09-10
- **Dependencies:** none
- **Cost:** minor

## Context

Found while accepting DA-56, and found by disbelieving a sentence rather than by a failure.

DA-56 added the quiet mark in the header that says a task appeared while the window was open. Its Playwright test holds a ceiling of 750 ms — 300 ms times the runner allowance — and the report that came with it said the strict figure was the perf gate's to enforce. It is not. `BUDGETS` in [perf/budgets.ts](../../../perf/budgets.ts) has seven lines and none of them measures this:

| label | field | budget |
|---|---|---|
| First render of the review after the server responds | `firstRenderMs` | 500 ms |
| Scrolling the diff: long tasks | `scrollLongTasks` | 0 |
| Scrolling the diff: CPU per frame | `cpuPerFrameMs` | 8.3 ms |
| Opening the comment form | `composerOpenMs` | 50 ms |
| Jumping to a file from the navigation | `fileJumpMs` | 50 ms |
| Switching review sessions | `sessionSwitchMs` | 100 ms |
| Update after an edit in one repository | `updateMs` | 300 ms |

The nearest, `updateMs`, measures a different path end to end: `measureUpdate` appends a line to a file in a repository and waits for `perf.liveUpdate`, which is set in `diffChanged()`. That is the `diff-changed` route — edit, rescan the repository, patch the card. The mark rides `sessions-changed`: a write to `reviews/<name>/review.json`, `reloadSessions`, a frame, the dot. The two share the SSE connection and nothing else.

So the number that stands between this mark and any future regression is the 750 ms in the Playwright test — two and a half times weaker than the sentence claimed. What was actually measured on this machine, twice: **246 ms and 234 ms**.

DA-56 deliberately did not add the budget line, and the reasoning holds. A new budget is not only `BUDGETS` and `Measurement`: `tests/perf.test.ts` holds the invariant that every budget in specification section 6 has a number, so the code's table and the spec's table move together. Adding one is a change to the contract that DA-56's card does not ask for — and it would have landed in a gate that is not being run per task in this package, so its first execution would have been in the final pass over merged main. Writing an untested contract change into the spec to be discovered later is worse than naming the gap.

The false sentence was also removed from where it would have outlived the report: the comment on `MARK_CEILING_MS` in `e2e/history.spec.ts` said the same thing.

## Work to do

- Decide whether `sessions-changed` deserves a budget of its own. It is a real user-facing path — the mark is how a reader learns an agent left them a task — and it is the only one of the live routes with no number on it.
- If yes, the change spans `perf/harness.ts` (the measurement), `perf/budgets.ts` (the line), and `docs/SPEC.md` section 6 (the row `tests/perf.test.ts` checks for). Run it at least once before it is committed; a budget nobody has executed is a claim, not a check.
- If no, say so in section 6 next to the five that are there: which live paths are budgeted and which are deliberately not. Today a reader counts seven lines and cannot tell whether the eighth is missing or unnecessary.

## Out of scope

- The Playwright ceiling itself. 750 ms is the right shape for a test on a shared machine; the question here is whether anything stricter exists behind it.
- Whether `perf` runs per task ([DA-54.3](../queue/DA-54.3-perf-budget-headroom.md)).

## Verification

- Section 6 of the specification answers, for each live-update route the UI has, whether it carries a budget — including the answer "deliberately not".
- If a budget is added, `bun run perf` reports it with a number on the first run after the change, not on some later one.
