# DA-24.1 · Switching a session takes 104 ms warm and 513 ms cold, against a 100 ms budget

- **Scope:** 11-perf (see [reference](../../reference/README.md))
- **Created:** 2026-09-05
- **Dependencies:** DA-24, DA-25

## Context

`docs/SPEC.md` section 6 budgets a session switch at 100 ms. Until the review
round of DA-25 the harness measured that line over the wrong window: it started
after `GET /api/review` had already been parsed (`painted - perf.responseAt`),
so the `POST /api/sessions/:name/use` and the read of the review that follows it
were outside the number. Only the first-render row of section 6 carries the
qualifier "after the server responds"; this row does not.

Measured over the whole wait now — the press, the `POST`, the read, the render —
three single-run processes on a quiet machine over the synthetic review, on a
freshly generated fixture:

```
old window (painted - responseAt)   44.3   43.5   38.3    median 43.5 ms
full window (press - painted)      512.8  104.2  102.1    median 104.2 ms
```

The spread is the finding. Run 1 is the first switch after the fixture was
generated: the document of that session is built and serialised for the first
time. Runs 2 and 3 find it warm. So the line says two things at once — a warm
switch is just over budget, and a cold one is five times over — and **the
reader's first switch to any session is always the cold one**.

Where the time goes, from numbers in the same table: first render, which is
parse-to-painted-frame over the same review, is 82–97 ms on those runs, so the
render is most of a warm switch and the server's share of it is small. On the
cold switch about 410 ms is the server: `POST …/use` invalidates the built
document ([`src/server/app.ts`](../../../src/server/app.ts)), and the next
`GET /api/review` builds it again — reading the change set, counting, and
serialising megabytes — with nothing to answer from.

This is a change-set and server question and not a UI one: nothing the page does
between the press and the frame accounts for four hundred milliseconds, and the
render half is already inside the first-render budget. The UI side is not what
should be changed to make this number smaller.

Until it is settled the budget line is measured, printed with this task named,
and does not fail the build — the mechanism `perf/budgets.ts` already has for a
row whose number does not yet cover what the budget is about.

## Work to do

The fork is the owner's, and DA-32 is where it is put to them.

- **Either** keep the budget and make a switch warm: hold the built document per
  session on the server rather than one at a time, so the first build of a
  session is paid once and a switch back to it is not paid again
  ([07-server.md](../../reference/07-server.md) — the document is built once and
  serialised once *for the current session*). The warm number is then 104 ms
  against 100, which is a rounding question rather than a design one.
- **Or** restate the budget in `docs/SPEC.md` section 6 as the window it can
  honestly hold — either by qualifying the row the way the first-render row is
  qualified, or by naming a number that covers the cold path.

Whichever way it goes, `perf/budgets.ts` loses the `pendingUntil` and
[11-perf.md](../../reference/11-perf.md) says what the line covers.

## Out of scope

- The window itself. It is the whole wait now, and that is not in question.
- The CPU-per-frame line (DA-16.1) and the gate that stops after one run
  (DA-25.2).

## Verification

- `bun run perf` on a quiet machine, three runs, with the median of
  **Switching review sessions** inside whatever budget the owner settles on, and
  no `pendingUntil` on the line.
- If the document is cached per session: a test that a second switch to a
  session the server has already built does not read the change set again.

## Deferred

- **Deferred:** 2026-09-05
- **Reason:** The fork is the owner's: the number is a spec budget of `docs/SPEC.md` section 6, and both outcomes — a server-side cache of the built document per session, or a restated budget — change a contract. Until then the line is measured, printed with this task named, and does not fail the build.
- **Return condition:** The owner picks one of the two outcomes in “Work to do” after the Phase 1 acceptance (DA-32) puts the numbers in front of them; the task then returns to the queue with that decision as its scope.
