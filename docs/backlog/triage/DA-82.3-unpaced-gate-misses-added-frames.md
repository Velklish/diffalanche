# DA-82.3 · The unpaced perf gate cannot see a regression that only adds frames

- **Scope:** 11-perf, 08-ui (see [reference](../../reference/README.md))
- **Created:** 2026-09-28
- **Dependencies:** none
- **Parent:** DA-82
- **Cost:** major

## Context

DA-82's verification names two probes that should move `fileJumpMs` once the hook
calls `revealCard`: a `ROUNDS` raised, and an added frame before the first scroll.
The first moved it; the second did not. On the 4-core container of 2026-09-28, five
`perf/run.ts` processes a variant, the jump window to the frame after the last round
read 69.8 ms (62.3–78.7) and 76.2 ms (63.1–95.0) with an `await afterPaint()` added
before the first `scrollIntoView` in `revealCard`; the window ending at the first
frame that shows the diff read 53.8 (47.4–85.7) and 52.1 (47.4–82.2). Both
differences are inside the spreads ([11-perf.md](../../reference/11-perf.md#the-gate)).

The assumed cause, not measured: since DA-115 Chromium runs with
`--disable-frame-rate-limit`, so a frame starts when the previous one is done, and
a frame with little to draw costs next to nothing. At 60 Hz, on the reader's
display, the same frame costs up to 16.7 ms. If that holds, every `ms` line that
ends at `afterPaint` — the first render, the composer, the jump, the switch, the
update — is blind to a regression that adds frames without adding work, and the
gate reads such a change as free.

## Work to do

- Measure the cost of an idle frame in the unpaced harness, to confirm or refute the
  assumption.
- If it holds: decide whether the `ms` lines also count the frames they span and hold
  that count against a ceiling, or say in 11-perf that frame-only regressions are
  outside the gate and why.

## Out of scope

- The frame-rate flag itself, which is DA-115's decision.

## Verification

- An `await afterPaint()` added before the first scroll of `revealCard` turns a gate
  line red, or 11-perf states that it does not and why.
