# DA-110.3 · On Linux, Node 22's userland recursive fs.watch reports a file replaced by rename only the first time

- **Scope:** [05-watcher](../../reference/05-watcher.md#what-it-watches-and-what-it-ignores)
- **Created:** 2026-09-29
- **Dependencies:** none
- **Parent:** DA-110.2
- **Cost:** major

## Context

Finding discovered while working on DA-110.2, from the reviewer's probes
(`rv1102/g.mjs`, `rv1102/d.mjs` in that run's scratchpad), reproduced by the worker.
On Linux, Node 22 does not recurse with inotify itself: `fs.watch(dir, { recursive:
true })` is emulated in `lib/internal/fs/recursive_watch.js`, one non-recursive watch
per path, all sharing the process's one inotify descriptor. That watch is set on the
inode that was there when it was taken. A file replaced by a rename — git's
`index.lock` → `index` and `HEAD.lock` → `HEAD`, or any atomic write — gets a new
inode: the watch on the old one fires once and then watches nothing, and the
directory's own event reports only names the emulation has not seen yet, which this
one is not. From the Node 22.22.2 binary:

```js
  #watchFolder(folder) {
    ...
        if (!this.#files.has(f)) {
          this.emit('change', 'rename', pathRelative(this.#rootPath, f));
```

The watcher's native tree takes whatever that watch reports, and nothing else:

<!-- quote:../../../src/core/watcher/tree.ts -->
```ts
    const watcher = watch(
      options.dir,
      { recursive: true, persistent: false, encoding: "utf8" },
      (_event, filename) => {
        if (filename === null) return;
        const path = String(filename).split("\\").join("/");
        if (path === "" || options.ignore(path, "file")) return;
        options.onChange(path);
      },
    );
```
<!-- /quote -->

Evidence, run by the worker on Node v22.22.2 (Linux), a fresh repository per run,
400 ms between steps, `.git/objects` and `.git/logs` filtered out
(`node g.mjs <repo>`, twice, identical output):

```
-- git add f
  change .git/index
  change .git/index
  change .git/index
-- git rm --cached -q f
-- git add f
-- git checkout -q -b b1
  rename .git/refs/heads/b1
  change .git/HEAD
  change .git/HEAD
  change .git/HEAD
-- git checkout -q -b b2
  rename .git/refs/heads/b2
-- git checkout -q master
```

and `node d.mjs <dir>`, three atomic writes of `reviews/s/comments.json` from a
shell (`printf > tmp && sync tmp && mv tmp comments.json`):

```
-- external atomic write 0
  change reviews/s/comments.json
  change reviews/s/comments.json
  change reviews/s/comments.json
-- external atomic write 1
-- external atomic write 2
```

The same scripts under Bun 1.3.14's native watch report every step, but by the
temporary name only: `rename .git/index.lock` on each of the three index moves,
`rename reviews/s/comments.json.tmp-…` on each write. For the data directory any
name is the signal; for a repository `repositoryIgnore` drops `.git/index.lock` —
an assumption, not checked here, that Bun's native path misses index moves by
another route.

Failure scenario: `node dist/cli.js serve` on Linux, where `supportsRecursiveWatch`
answers yes and every tree takes this watch, hears the first commit, index move or
branch switch of a repository and then misses the second and every one after it;
the review goes stale until an edit of a working-tree file triggers a rescan. By
the `d.mjs` run, an agent writing `comments.json` from another process may meet
the same gap in the data directory — assumed, not reproduced with the tool's own
`writeFileAtomic`.

The suite does not see it: its only wait on a repository's index is the `git add -f`
step of "asks git again once the index has moved", and it holds only because
nothing replaced that repository's index earlier in the file:

<!-- quote:../../../tests/watcher.test.ts -->
```ts
    await run("git", ["-C", join(root, REPO), "add", "-f", "dist/tracked.js"]);
    await waitForChangeOf(REPO, stagedMark, ".git/index");
```
<!-- /quote -->

## Work to do

- Decide how a tree on Node's emulated watch hears a file replaced by rename: for
  example, treat a rename in a watched directory as a signal whatever name it
  carries, keep `.git`'s three files on a watch of their directory rather than of
  their inode, or walk where the recursive watch is emulated. The choice is an ADR
  if it changes what `recursive` means.
- A test that replaces a repository's index, and its `HEAD`, twice in a row and
  expects a `diff-changed` for each, on the watcher the suite starts on Node.
- Check the data-directory scenario with `writeFileAtomic` from another process.

## Out of scope

- The Bun native path's `.git/index.lock`, beyond confirming or refuting the
  assumption above; it gets a card of its own if it holds.

## Verification

- The new test red on the current `native` and green after the fix, on Node,
  repeatedly; `bun run test` and `bun run test:bun` green.
