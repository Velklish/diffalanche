# DA-56.4 · CPU per frame misses its 8.3 ms budget at rest on this machine, and did so before the DA-53…56 package too

- **Scope:** 11-perf (see [reference](../../reference/README.md))
- **Created:** 2026-09-21
- **Cost:** major
- **Dependencies:** none

## Context

Finding discovered while running the perf pass of DA-56.3. That pass had to
attribute whatever was over budget to a commit. One line cannot be attributed to
any commit of this wave, and the measurement that says so is worth its own
entry.

`Scrolling the diff: CPU per frame` is budgeted at 8.3 ms, which is the frame of
120 fps that `docs/SPEC.md` section 6 asks for; a headless runner cannot measure
frame rate, so this number and the long-task count stand in for it.

Measured in the quietest window this machine reached on 2026-09-21 — no other
work running, one-minute load average 5.2 at the start, which is this machine's
own floor, 0.65 per core against the 2.5 ceiling of
[ADR-013](../../adr/adr-013-perf-gate-off-ci.md). Three trees, two `bun run perf`
runs each, alternating, under one lock, medians of three repetitions:

| tree | what it is | CPU per frame, run 1 | run 2 |
|---|---|---|---|
| wave-2 branch | DA-63, DA-69, DA-54.3 on top of `ed81928` | 9.0 ms | 8.6 ms |
| `ed81928` | main, after the DA-53…56 package | 9.0 ms | 8.6 ms |
| `1193ab3` | main, **before** the package | 8.9 ms | 8.6 ms |

Every run over budget, on every tree. The lowest single repetition of the whole
window was 8.5 ms. `1193ab3` predates all four tasks of the package and every
task of this wave, and measures the same as the tip.

What this says is about the page and not about the laptop: `cpuPerFrameMs` is
the application's own processor time per frame while scrolling, and the machine
is the instrument. At rest, on an M1 Pro, the scroll does not fit inside the
frame of 120 fps.

What it settles for DA-56.3 is narrower and is all that pass owes: **the line is
not attributable to any task of this wave or of the DA-53…56 package.**

DA-54's own commit has now been re-measured, and it settles the question this
entry first left open. A nine-point pass over `1193ab3..ed81928` on the same
day, one run per point at a load average of 7.6 to 10.8:

| commit | task | CPU per frame |
|---|---|---|
| `1193ab3` | before the package | 8.5 ms |
| `2925a19` | **DA-54** | **8.8 ms** |
| `4be4936` | DA-53 | 9.1 ms |
| `1079222` | DA-55 | 8.9 ms |
| `a8d673b` | DA-56 | 8.9 ms |
| `c9305e1` | DA-57 | 8.8 ms |
| `fa004df` | DA-78 | 8.7 ms |
| `7308efa` | DA-90 | 8.8 ms |
| `ed81928` | the tip | 8.7 ms |

8.5 to 9.1 with no trend. DA-54's own commit gives 8.8 ms today, not the 8.2 ms
its report recorded on 2026-09-10, so **there is no half millisecond hiding
between those commits**: the two sessions' "quiet" were different machine
states. The line has been above its budget for the whole of this range, and
nothing in the range moved it.

## Work to do

- The owner decides what an 8.3 ms budget means when the machine delivers 8.6 at
  rest. The options, in the order they cost:
  - **Set the gate on a number this machine reaches**, with 8.3 ms staying the
    frame of 120 fps in `docs/SPEC.md` section 6 and the current reading written
    down beside it. The trusted range — the readings taken where ADR-013's gate
    produces a verdict at all — is 8.5 to 9.1 ms, worst 9.1. A ceiling of 9.5
    leaves about four percent over that and still catches a regression the size
    of the one DA-54 hunted, which was 0.8 ms; 10.0 would leave ten percent and
    catch almost nothing, and 9.2 would sit against the worst reading and bring
    back the flapping DA-54.3 exists against.
  - **Change what the line measures.** 8.3 ms is CPU time per frame over a
    600-frame scroll that is far faster than a person scrolls — the stress case,
    by design. A budget met by no commit is not a budget, and a stress case that
    nothing passes gates nothing.
  - **Change the budget**, with the frame of 120 fps written down as what it no
    longer is. Last, and only with the first option's answer in hand.
