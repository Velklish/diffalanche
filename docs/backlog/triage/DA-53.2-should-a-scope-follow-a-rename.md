# DA-53.2 · Should the scope of a task follow a renamed file?

- **Scope:** 04-domain (see [reference](../../reference/README.md))
- **Created:** 2026-09-18
- **Dependencies:** none

## Context

Split out of [DA-53.1](../../archive/README.md), which named two questions and
answered only the first. That entry calls this one "squarely the owner's", so it
is filed rather than decided: **this is a question for the owner, not a defect
report.**

Today a scope does not follow a rename. A scope entry names a path; a renamed
file is at a path the scope does not name, so the task stops showing it, and the
new name is put back by hand with `review scope add` — or now with
`review scope set`. That is decisions 2 and 5 of
[ADR-010](../../adr/adr-010-review-task-scope.md) applied literally, and
[06-cli.md](../../reference/06-cli.md) documents it as the behaviour rather than
as a gap.

One alternative is already closed. Resolving renames **when the scope is read**
was measured during DA-53's review round and rejected: it means reading the
change set on every read of the comments, and it stops working the moment the
rename is committed, because the change set no longer carries the rename. Do not
re-propose it without new evidence.

What is left open is the other mechanism: the scope **written** at the moment the
rename is noticed. The watcher already sees the working trees change
([05-watcher.md](../../reference/05-watcher.md)), and a rename in a change set is
a `status` of `renamed` with an `oldPath` ([02-git.md](../../reference/02-git.md)),
so the information is there. What it costs is that a scope would change without
anybody asking it to, and a task's definition would move under the reader — which
is a product decision about what a task *is*, not an implementation detail.

## Work to do

- Ask the owner which of the two the product wants: a scope that is a literal
  list of paths and is edited by hand after a rename, or a scope that a rename
  rewrites.
- If it stays as it is: say so in [06-cli.md](../../reference/06-cli.md) and
  [04-domain.md](../../reference/04-domain.md) as a decision with its reason, so
  the next reader does not read it as an oversight, and close this entry.
- If it should follow: the mechanism is a write at the moment the rename is
  seen, and the task that carries it has to answer who writes it (the watcher
  writes no session files today), what happens to comments anchored at the old
  path, and what a scope edit racing that write does under the session lock.

## Out of scope

- Read-time resolution, rejected above with evidence.
- `review scope set`, which is DA-53.1 and is done.

## Verification

- Whichever way it goes, `06-cli.md` and `04-domain.md` say the same thing about
  a renamed file as the code does, and neither leaves it to be inferred.
