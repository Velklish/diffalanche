# DA-90.1 · The session directory itself is created without a flush, so a durable first write can be published into an entry that is not there

- **Scope:** 03-storage (see [reference](../../reference/README.md))
- **Created:** 2026-09-18
- **Dependencies:** none

## Context

[DA-90](../../archive/) gave `writeFileAtomic` a flush of the directory the rename publishes into,
so `review.json` and `comments.json` reach the disk under the name a reader looks for. The step
above that one is not flushed: the session directory is created and nothing syncs the entry that
puts it into `reviews/`.

[src/core/storage/index.ts:115-119](../../../src/core/storage/index.ts)

```ts
export async function ensureSessionDir(dataDir: string, name: string): Promise<string> {
  const dir = sessionDir(dataDir, name);
  await mkdir(dir, { recursive: true });
  return dir;
}
```

The hypothesis, stated as a hypothesis: on a file system that can lose a directory entry
independently of the file entries inside it, a crash right after the first write of a new session
leaves `reviews/` without `<name>` while `<name>/review.json` is durable — the write survives under
a name nothing lists, which is the same outcome DA-90 closed one level down. `grep -rn "mkdir" src/core/storage/index.ts`
returns the two creations (`ensureDataDir`, `ensureSessionDir`) and no flush beside either.

**What is not known is whether the case is reachable on APFS at all.** APFS is the file system the
tool is developed and measured on, and its metadata is journalled; whether the journal makes the
parent entry durable with the child, or whether the two are independent, has not been checked here.
On a file system where it is independent the case is real. Nothing in this entry was reproduced:
the probe that would settle it is below.

Not the same thing as DA-90, which is closed: that one is about the entry a `rename` creates inside
a directory that already exists, and it is fixed. This is about the entry `mkdir` creates one level
up, on the path that runs once per session rather than once per write.

## Work to do

- Settle the APFS question first, because it decides whether there is anything to fix: create a
  session, flush nothing, and establish from the file system's documentation — or from a crash-
  consistency probe — whether the parent entry can be missing while the child file is durable. If
  it cannot on every file system the tool ships for, close this as refuted and say so.
- If it can, decide where the flush goes: `ensureSessionDir` flushing `reviews/` on creation, or the
  first durable write of a session flushing its parent as well. The first pays once per session and
  is on the `review new` path only; the second couples two levels of the tree inside one function.
- Whatever is decided, `ensureDataDir` is the same question one level further up and is answered in
  the same pass or explicitly left out.

## Out of scope

- `writeFileAtomic` and the five call sites of DA-90, which are closed.
- The drive-cache window `F_FULLFSYNC` would close, named in
  [03-storage.md](../../reference/03-storage.md) and out of reach from Node and Bun alike.
- `ensureSessionDir` growing an `EACCES` wrapper, which is DA-99.

## Verification

- The APFS answer is written down with what it came from — a manual page, a documented guarantee, or
  a probe — rather than asserted.
- If a flush is added, a test counts the `open` of `reviews/` the way
  `tests/storage-atomic.test.ts` counts the flush of a session directory today.
- Gates: `bun run lint`, `bun run typecheck`, `bun run test`, `bun run test:bun`. `bun run perf` is
  in the set; the creation path is not measured by it.
