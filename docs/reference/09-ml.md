# 09 · Model, index, and suggestions

**The embedding model, the index, suggestions, their delivery and the symbol index are built.**
`src/core/ml/embed` turns texts into vectors, `src/core/ml/index` keeps a vector
for every comment of every review session, `src/core/ml/suggest` finds the past
comments nearest a text and the severity they vote for, and the model reaches a
user with each channel: downloaded once by the npm package, written out of the
binary by the binary. `diffalanche model status` says which model the build is
pinned to and whether it is on disk, `model pull --embedding` puts it there,
`index rebuild` and `index status` build the index and say what it holds, and
`suggest` and `GET /api/suggest` answer with suggestions. All of it starts from
[ADR-014](../adr/adr-014-embedding-model-and-npm-delivery.md), which the owner
**accepted** on 2026-09-23. `src/core/ml/symbols` holds the symbol index
(DA-39), below.

## The embedding model

`src/core/ml/embed/model.ts` pins one model and nothing else reads a model
name: `multilingual-e5-small`, the int8 ONNX export in
`Xenova/multilingual-e5-small` at commit `761b726dd34f`, 118M parameters and 384
dimensions. The manifest lists its three files with their sizes and SHA-256:

| File | Bytes |
|---|---|
| `model_quantized.onnx` | 118 308 185 |
| `tokenizer.json` | 17 082 730 |
| `tokenizer_config.json` | 443 |

The model was trained to see `query: ` in front of a text when two texts are
compared as equals, which is what "a comment like this one" is, so every text is
embedded with that prefix. Its window is 512 tokens; a longer text is cut to
the first 511 and its closing `</s>`.

The files are read by two libraries: `@huggingface/tokenizers`, the tokenizer in
plain JavaScript, and `onnxruntime-node` 1.30, ONNX Runtime's N-API addon. The
addon loads unchanged on Bun — no `Bun.*`, no branch on the runtime — so the
module is not a second runtime-specific module next to `src/server/runtime.ts`
([ADR-008](../adr/adr-008-diff-rendering-verdict.md)). ADR-014 has the
measurements behind the choice of both.

The addon ships native libraries for five of the six targets: there is no
darwin-x64 build since 1.24, so on an Intel Mac the module cannot be imported.
ADR-014 settles that an Intel Mac gets no model and no suggestions, and
`openEmbedder` refuses there before it imports anything (below, "The index").

## Where it lives

The npm channel keeps the model in the user cache, shared by every root:

```
$XDG_CACHE_HOME/diffalanche/models/multilingual-e5-small-761b726dd34f/
```

with `~/.cache` when the variable is unset or empty — the same rule as the user
configuration's `$XDG_CONFIG_HOME`. The directory is named after the revision,
so a new pin lands next to the old one instead of over it. On the two channels
the runtime's native files for the platform sit in a subdirectory of it keyed by
the runtime's version and the platform,
`multilingual-e5-small-761b726dd34f/onnxruntime-node-1.30.0-darwin-arm64/`, so that
two versions of the tool with two runtimes never overwrite each other's files; the
binding finds its library beside it there, as it does in the package ("Delivery",
below). That is ADR-014's 5B — the files travel with the model and land under its
directory. Nothing is removed on its own: the directory of an old pin or an old
runtime, about 180 MB with both, stays until it is deleted by hand, which is safe —
the next use fetches or writes what it needs again. From the sources they are the package's own,
and the model comes from `bun run model:fetch` (`scripts/fetch-model.ts`), which
downloads the three files from the pinned commit and refuses any whose SHA-256
is not the manifest's; CI runs it too.

## Loading and embedding

`embedder(location)` loads the model on its first call and hands every later
call the same promise, so a process pays for the load once; a load that failed
is forgotten, and the next call tries again. Before reading anything it checks
that every file has the size the manifest names, and a missing or truncated
file is one error naming the directory and the files. The load reads nothing
over the network.

`embed(texts)` returns one vector per text, in the order given: the mean of the
text's token states, scaled to unit length, as a `Float32Array` of 384. Two
vectors compare by their dot product. A vector belongs to the model, its
revision, the runtime's version and the platform together — onnxruntime-node
1.23.2 and 1.30.0 put the same text up to 0.0032 cosine apart, Linux and macOS
up to 0.0013 — and on one machine Node and Bun give the same bytes.

**One text per run, never a batch.** The model's activations are quantized per
tensor at run time, so in a batch the scale a text is multiplied by depends on
the texts next to it. Measured on 200 review comments, a text embedded alone and
the same text embedded in a batch of 32 came out as far apart as 0.9947 cosine.
One text per run makes a text's vector a function of the text: the index can
embed a comment when it is written and again on a rebuild and get the same
bytes. Batching bought nothing measurable on one thread — 2.6–2.9 s of CPU for
the 200 comments one by one, 2.3–2.7 s in batches of 32.

**Pool threads do not spin.** The session is created with
`session.intra_op.allow_spinning` at `0`: on a busy machine the spinning threads
cost about three times the CPU of the work itself, and switching them off changed no
vector. The thread count is ONNX Runtime's default.

**A run holds the thread that called it.** `onnxruntime-node` 1.30 runs a
session synchronously inside a `setImmediate`, so the event loop is blocked for
the length of one run. One text per run bounds that to one text. A command has
nothing else to serve and runs the model on its own thread; the server runs it
on a thread of its own, because one text at a time was measured not to be short
enough (below, "In the server").

## `model status`

```
$ diffalanche model status
embedding  multilingual-e5-small int8 @ 761b726dd34f
source     Xenova/multilingual-e5-small
location   /Users/me/.cache/diffalanche/models/multilingual-e5-small-761b726dd34f
state      present, 135.4 MB
runtime    onnxruntime-node 1.30.0, darwin-arm64: present, 44.9 MB
```

It reads no configuration and no session, and it looks at the sizes of the
files, never their contents, so it answers in a stat per file. A model that is
not there is `absent`, with the files that are missing or of the wrong size, and
exit code 0 — it is a state, not a refusal. The `runtime` row is the runtime
this process would load: `from node_modules` from the sources; on the two
channels its native files in their directory, `present` or `absent` like the
model's, so a model that is there with a runtime that is not says so before a
`suggest` downloads it; and `not available on this platform` on darwin-x64
(ADR-014, 3B). `--json` prints `{"embedding": {name, source, revision,
quantization, location, present, files}, "runtime": {name, platform, available,
from, location, present, files}}` with each file's size on disk and the size the
manifest expects; `from` is `node_modules` or `cache`, the last three come only
with `cache`, and on darwin-x64 `available` is `false` and nothing follows it.
The generative model joins it in Phase 4 (DA-46).

## The index

`src/core/ml/index` holds one vector per comment of every review session, with
what a suggestion shows of the comment: its session, id, severity, repository,
file, line and text. Replies are not in it: a suggestion is a comment, and a
reply has no severity to propose.

### On disk

```
<data directory>/
  index/
    index.bin         one line of JSON, then the vectors as raw floats
```

The first line is JSON and holds everything but the vectors: `version` (2, the
data directory's), the model, its revision, the runtime and the platform the
vectors came from, `dimensions`, `updatedAt`, the size and modification time of
every session's `comments.json` when it was last read, and the entries in the
order of the rows. `head -1 index.bin | jq` reads it. The vectors start at the
next multiple of four bytes, one row of 384 `float32` per entry in the
machine's own byte order — little-endian on all five platforms, and an index
never leaves the machine that built it — and are read in place as one
`Float32Array`.

It is a cache, like `diff.json`: the tool writes it and can always write it
again. A file whose version is not 2, whose line is not JSON, or whose vectors
are not exactly the entries times the dimensions is read as no index, with the
reason, and the next update embeds every comment. It is written the way every
file of the data directory is, to a temporary name and renamed over the old one,
so a reader sees the old index or the new one; it is not flushed to the
directory, because a crash costs a rebuild and not a comment.

**Why one file with a JSON line and not one JSON file.** The first build wrote
the vectors into the JSON as base64, one string per entry. At 10 000 comments
that file was 23.5 MB, a warm read took 23 ms on Bun and 38 ms on Node, and a
process that loaded the model and answered one query over it peaked at 790 MiB on
Bun — over the 768 MiB of ADR-014. The same entries with raw floats are 17.5 MB,
read in 8.5 and 8.9 ms, and the same query peaked at 736 MiB. Two files, the JSON
beside a vectors file, would have been as small, but a reader could then meet
the new JSON with the old vectors; one file renamed into place cannot be half
new.

### Bringing it up to date

`updateIndex(dataDir, embedder)` makes the index say what the sessions say:

- a session whose `comments.json` has the size, modification time and inode
  recorded for it is **not read at all**; its entries are carried over as they
  are. The inode is in because every atomic write makes a new file: two writes
  inside one tick of the filesystem's clock with the same size — an edit of the
  same length, `critical` for `question` — differ in it and in nothing else;
- in a session whose file changed, a comment keeps its vector when its text is
  the one indexed, and the anchor and severity are taken fresh; a new comment,
  or one whose text was edited by hand, is embedded;
- entries of a comment or a session that is gone are dropped — a
  `--drop-comments`, a session directory removed by hand;
- an index built by another model, revision, runtime or platform is not
  carried over at all: every comment is embedded again, and the update says so
  in `rebuilt` ([ADR-014](../adr/adr-014-embedding-model-and-npm-delivery.md),
  Consequences — a vector belongs to all four).

The fingerprint is taken **before** the file is read, so a write that lands
between the two is seen by the next update rather than lost. A `comments.json`
that no longer parses keeps what was indexed of it and its old fingerprint, and
is named in `warnings`: every update reads it again until it is fixed, and none
rewrites the index for it meanwhile; `index status` does not count its entries
as gone. Nothing is written when nothing changed, and **nothing at all where
there is no session**: an update of a data directory with no session and no
index answers an empty index and makes no `index/` — `suggest` and `index
rebuild` refuse there before they load anything, like `list`, so a command run
in a directory nobody reviewed leaves it as it was. Texts are embedded one per call, and
the loop awaits each: a run holds the thread that runs it ("Loading and
embedding", above).

Two processes can update at once — `index rebuild` in a terminal while the
server catches up — and the one that renames last wins. Both wrote a whole
index of what they read, so the loser's work is redone by the next update, and
nothing is half-written; there is no lock, because nothing is lost without one.

`index rebuild` is the same update with nothing carried over.

### Where the update attaches

**The reader brings the index up to date before it reads it.** Whatever needs
the index — `index rebuild`, and from DA-35 `suggest` and the composer's
suggestions — runs the update first, and the update finds every write by the
size and time of the files. The card offered two other places, and both lose
writes or cost the wrong command:

- **The domain write**, `addComment` under the session's lock
  ([04-domain.md](04-domain.md)). Every `diffalanche comment` an agent runs would
  then load the model — 0.7–4.8 s and 476–650 MiB peak per process in ADR-014's
  measurements — for a write that must work on a machine with no model, on an
  Intel Mac where there is none (ADR-014, 3B), and on the npm channel before
  anything has been downloaded (ADR-014, 4A). And a `comments.json` edited by
  hand, or rewritten by `review scope remove --drop-comments`, would still need
  a reader-side pass to be seen.
- **The event bus**, `comment-added` in the server
  ([07-server.md](07-server.md)). It exists only while a server runs, and only
  for the sessions the watcher follows ([05-watcher.md](05-watcher.md)): a
  comment an agent writes with no server running, or into a session no window
  is on, never reaches it, and the index would miss it until a rebuild.

Either would need the reader-side pass anyway; the pass alone is enough. What it
costs is paid by the first reader after the writes, measured on 2026-09-23 on
the development machine (M1 Pro, 8 cores; load averages 13–17), with the model
warm, on the synthetic review's 200 comments (`perf/index-scale.ts catch-up`):

| Comments not yet indexed | Bun 1.3.14 | Node 25.2.1 |
|---|---|---|
| 200 (no index) | 1175 ms | 1118 ms |
| 1 | 7 ms | 14 ms |
| 0 | 1 ms | 1 ms |

The one-comment case is what a composer query pays after a comment was written:
a stat per session and one run.

### Search

`nearest(index, query, { k, sessions? })` is brute force: the dot product of the
query with every row — the vectors are unit length, so that is the cosine — and
the `k` highest, highest first. `sessions` keeps the search to the comments of
those sessions. The product is summed four lanes at a time, which halved the
time of the plain loop on Bun (1.7 against 3.8 ms over 10 000 rows, warm).

### How far brute force goes

`perf/index-scale.ts search` writes indexes of random unit vectors and times a
read of the file and `nearest` with `k` 10, the median and the worst of twenty
warm searches; same machine and day, load averages 16–17:

| Comments | File | Read, Bun / Node | Search, Bun / Node | Worst search, Node |
|---|---|---|---|---|
| 1 000 | 1.7 MB | 1.6 / 1.4 ms | 0.2 / 0.4 ms | 0.9 ms |
| 10 000 | 17.2 MB | 8.5 / 8.9 ms | 1.8 / 3.6 ms | 3.9 ms |
| 20 000 | 34.4 MB | 17.5 / 19.4 ms | 3.5 / 7.1 ms | 7.5 ms |
| 50 000 | 86 MB | 43.2 / 54.6 ms | 9.1 / 18.2 ms | 22.9 ms |
| 100 000 | 172 MB | 111.7 / 101.1 ms | 17.7 / 36.8 ms | 43.1 ms |

The search itself stays under the 50 ms of the card to 100 000 comments on both
runtimes. **What stops being fine first is memory.** Peak resident size of a
process that loads the model, reads the index and answers one query
(`perf/index-scale.ts query`, `/usr/bin/time -l`), and of `index rebuild`:

| | Bun 1.3.14 | Node 25.2.1 |
|---|---|---|
| the model alone, with one text embedded | 714 MiB | 697 MiB |
| `index rebuild` of 10 000 comments | 680 MiB | 618 MiB |
| a query over 10 000 | 735–736 MiB | 682–692 MiB |
| a query over 20 000 | 736 MiB | 669 MiB |
| a query over 50 000 | 803 MiB | 687 MiB |

ADR-014's ceiling is 768 MiB. On Bun — the binary channel — a query crosses it
between 20 000 and 50 000 comments; on Node it is still under at 50 000. So the
index is fine as it is to about 20 000 comments for a command. The server is its
own measurement, below ("In the server"): it holds the review too. Past that the
next step is not a faster search but a smaller resident set: the vectors mapped
rather than read, or in `float16`. Whether the ceiling holds that far is the
owner's to say, and DA-34.2 carries the question. The peak moves with the memory pressure of
the machine as much as with the index — the model alone measured 476–650 MiB in
ADR-014 and 697–714 MiB here.

### `index rebuild` and `index status`

```
$ diffalanche index rebuild
indexed 200 comments of 1 review session in 3.1 s

$ diffalanche index status
index     /root/.diffalanche/index/index.bin
built by  multilingual-e5-small @ 761b726dd34f, onnxruntime-node 1.30.0, darwin-arm64
holds     200 comments of 1 review session, updated 2026-09-23T20:21:54.457Z
state     current
```

`index rebuild` loads the model from the user cache and embeds every comment
again; a model that is not there is exit code 1 with one line naming the
directory and the files, the same words `model status` uses. `index status`
reads no model: it compares the index with every session's comments and says
`current`, how many comments are still to embed and entries to drop, that the
index was built by another model or runtime, that it is absent, or that the file
cannot be read and why. An edited comment counts once in each. `--json` prints
`{"index": {location, present, problem, builtBy, build, comments, sessions,
updatedAt, missing, gone, warnings}}`. Warnings — a session that cannot be read —
go to standard error in the text form.

The model is imported only by these commands, through `openEmbedder`
(`src/core/ml/embed/open.ts`): it checks the platform against the five the
runtime ships for and the files against the manifest before it imports
`onnxruntime-node`, so every other command starts without the runtime, and a
refusal — `ModelError` — is one line and exit code 1
([06-cli.md](06-cli.md)).

## In the server

**The server runs the model on a worker thread.** `startThreadedEmbedder(location)`
(`src/core/ml/embed/threaded.ts`) starts `worker.ts` with `node:worker_threads`,
which Bun implements too, and answers with an `Embedder` of the same shape: a
call posts the texts and resolves with the vectors the thread sends back, their
buffers transferred rather than copied. The thread loads the model with
`embedder()`, the same module and the same session options, and gives the same
bytes as the thread that calls it. Nothing in it asks which runtime it is on,
so it adds no runtime-specific module ([ADR-008](../adr/adr-008-diff-rendering-verdict.md)).

What decided it is DA-34.1's measurement. `perf/run.ts --embedding main` rebuilds
the index of the synthetic review in a loop in the server's own process while
the harness measures the page, `--embedding worker` does the same through the
thread, and `--lag` only times the event loop, as the baseline
([11-perf.md](11-perf.md#the-measurement-harness)). Three runs of each,
alternating, on 2026-09-23 on the development machine at load averages of
7.7–15.7 on 8 cores — under the gate's ceiling of 2.5 per core, not quiet:

| | Update after an edit, 300 ms | Switching sessions, 100 ms | Timer lateness p99 / worst |
|---|---|---|---|
| no model (`--lag`) | 297, 293, 272 ms | 72.7, 66.5, 69.6 ms | 12–13 / 44–53 ms |
| the model on the server's thread | 422, 435, 427 ms | 71.8, 73.0, 71.4 ms | 21–26 / 80–211 ms |
| the model on a worker thread | 344, 295, 285 ms | 68.2, 71.4, 75.4 ms | 10–13 / 47–82 ms |

An earlier series of the first two rows gave 306, 336, 305 ms against 430, 639,
451 ms for the update. **On the server's thread the update budget fails by a
median of 127 ms**, while every run holds the loop for only 6–8 ms at the
median: an update is the watcher, a rescan with git processes, the stream and a
fetch, dozens of steps in a row, and each waits out the run in progress. On a
worker the update is back to the baseline and the loop's lateness is the
baseline's. Switching sessions stayed inside its budget in all three. The loop
is the worst case — a catch-up after hundreds of comments lasts about a second
(above), not the length of a measurement — but it is the case where the index
is rebuilt while the person works, which is the verification of the card.
The update line is over its budget on the base commit as well on some runs
(DA-110); the comparison that matters is between the rows, taken alternately.

The catch-up table above, through the thread: 200 comments in 1203 ms on Bun and
1094–1134 ms on Node, one comment in 8 and 12 ms, with the loop's worst lateness
during the 200 at 1.7–1.9 ms against 5–15 ms on the server's own thread.

Three things about the thread are there because a runtime needed them:

- **It ends itself.** `close()` posts `close`, and the thread calls
  `process.exit(0)`, which ends a worker and not the process. `worker.terminate()`
  of a thread that has loaded `onnxruntime-node` aborts Bun 1.3.14 with `NAPI
  FATAL ERROR: Error::New napi_create_error` in 2 runs of 2; the exit from inside
  ended it cleanly on both runtimes, and `parentPort.close()` left Bun waiting
  until it was killed.
- **It keeps no process alive while it waits.** The worker is held while it loads
  and while a call waits, and let go when it is idle, so a process that never
  closes it still exits. Let go too early — before the load answers — Node exits
  under the start with an unsettled `await` (exit code 13); held all the time, a
  Node process whose only work left is the idle thread did not exit in five
  minutes. With the reference following the work, a process that loaded the model
  on the thread, embedded, and then ended or called `process.exit(0)` exited 0 on
  Node 25.2.1 and on Bun 1.3.14, with no `NAPI FATAL`. `close()` holds it again
  until it has gone, and the server's `close()` calls it.
- **A load that fails is a `ModelError`.** The thread posts why, the start is
  refused with it, and the thread ends; a call after the thread has gone is
  refused with the exit code it ended with. **A thread that throws** — its module
  not found, the native runtime refusing to load — emits `error` on the `Worker`,
  and that is a `ModelError` too: without the listener the error is an uncaught
  exception in the process that started the thread, one `GET /api/suggest` would
  end the whole server, and the route answers 503 instead.

The worker file is found next to `threaded.ts` by `import.meta.url`: from the
sources it is `worker.ts`, and a channel's build replaces the expression with
`./embed-worker.js`, which the npm bundle carries beside `dist/cli.js` and a
binary beside its entry ("Delivery", below).

## Suggestions

`src/core/ml/suggest` answers "what did I write before about something like
this": `suggest(dataDir, embedder, text)` brings the index up to date, embeds the
text, takes its five nearest comments across every review session, and has them
vote on a severity. `diffalanche suggest --body <text> [--json]` and
`GET /api/suggest?body=` ([07-server.md](07-server.md#suggestions)) are its two
doors; the composer shows them while a comment is typed ([08-ui.md](08-ui.md#commenting)).

```
$ diffalanche suggest --body "The cache key does not include the region, so two tariffs overwrite each other."
severity  critical, confidence 1.00

0.94  critical  synth  repos/core/cargos-api/docs/cargo-163.md:41                      Missing the region in the cache key: two tariffs collide here.
0.94  critical  synth  repos/platform/loads-search/internal/invoice/invoice-281.go:62  Missing the region in the cache key: two tariffs collide here.
0.94  critical  synth  repos/platform/loads-search/app/cargo/cargo_404.py:26           Missing the region in the cache key: two tariffs collide here.
0.94  critical  synth  repos/services/quotes-worker/src/Cargos/CargoService497.cs:35   Missing the region in the cache key: two tariffs collide here.
0.85  warning   synth  repos/core/cargos-api/src/Carriers/CarrierService59.cs:21       Log level is wrong: a resolved request is not a debug event.
```

That is the small synthetic review (`bun run synth -- --out <dir> --small`).

Each suggestion carries its similarity, its severity, its source — the session,
then the repository, file and line as `list` prints an anchor — and the first
line of its text; `--json` prints `{severity, suggestions}` with every field of
the index entry and the similarity. Nothing near enough prints `none` for the
severity and the neighbours all the same.

**The vote.** Each of the five votes for its own severity with the weight
`exp((similarity − best) / 0.01)`, where `best` is the nearest one's similarity:
a neighbour 0.01 less similar than the nearest counts about a third as much, one
0.05 less counts under 1 %. The proposal is the severity with the most weight,
and its **confidence is that severity's share of all the weight**: never under
0.25, since there are four severities, and 1 when all five agree. When the nearest
comment is less similar than **0.86**, nothing is proposed: the history holds
nothing like the text, and its neighbours' severities say nothing about it.

**How the three numbers were chosen.** `perf/suggest-vote.ts` embeds forty
labelled comments — ten findings in four wordings each, two English and two
Russian, three findings `critical`, three `warning`, three `nit` and one
`question` — and asks each for its neighbours with itself left out, plus eight
texts like none of them ("Looks good to me.", "Спасибо, отличная работа.").
Measured on 2026-09-24 on the development machine:

- the nearest neighbour was a wording of the same finding for 40 of 40;
- the nearest similarity of those forty was 0.866–0.945 (median 0.916), and of
  the eight unrelated texts 0.802–0.859 — **0.86 is between the two**, with a
  gap of 0.007 on this corpus, so it is a line drawn on forty texts rather than
  a property of the model. What it costs shows on the small synthetic review:
  "Ключ кэша не учитывает регион" finds the four region comments first, at
  0.848, and proposes nothing — a short text in the other language sits under
  the line while its neighbours are right. The two longer Russian paraphrases the
  tests use against the English texts of the same review land at 0.9244 and
  0.8823 (darwin-arm64), 0.064 and 0.022 above the line, where another
  platform's kernels move a vector by up to 0.0013; the test prints the
  similarity with its verdict. Tuning the line on real history is DA-35.1;
- severities right out of 40, by `k` and temperature:

| `k` | 0.005 | 0.01 | 0.02 | 0.05 | equal weights |
|---|---|---|---|---|---|
| 3 | 40 | 39 | 38 | 34 | 31 |
| 5 | 40 | **40** | 38 | 35 | 25 |
| 10 | 40 | 40 | 39 | 29 | 24 |

Equal weights are wrong because a finding has three other wordings, so a fourth
and fifth neighbour are another finding's; a temperature of 0.005 is right
because it is nearly "take the nearest", and its confidence says little (0.97 on
average). 0.01 keeps every answer right at five neighbours and lets a close
second finding lower the confidence: at 0.02 the two wrong answers came with a
confidence of 0.55 against 0.84 for the right ones, which is what the number is
for. Five is also what the composer has room to show. Forty texts written for
the purpose tell a broken vote from a working one; they do not tune it finely,
and a history of real comments may want other numbers.

**Speed.** A warm request of `GET /api/suggest` — the thread started, the index
up to date — measured 5–7 ms at the median over the synthetic review's 200
comments and 21–36 ms over 10 000 (Node, Bun), at load averages of 28–40. The
server holds the index it last read or wrote and reads `index.bin` again only
when its size or time changed, and an update that finds no `comments.json`
changed returns the index as it is: without either, a request over 10 000
comments took 157–208 ms, most of it reading and copying the index. The first
request pays for the thread's load and the index's catch-up: 0.9–1.1 s on the
small synthetic review, 3.5 s on the full one with no index yet.

**The server's memory.** `perf/index-scale.ts serve --root <fixture>` starts the
server the way `serve` does on a copy of the full synthetic review with its index
removed, reads the review document of 30 000 lines, asks for a first suggestion —
the thread starts, loads the model and indexes the 240 comments of the review's
two sessions — and then three warm ones, sampling the resident size every 20 ms;
under `/usr/bin/time -l` it gives the operating system's peak as well. Two runs
each, alternating, on 2026-09-24 at load averages of 6.6–15:

| | Bun 1.3.14 | Node 25.2.1 |
|---|---|---|
| peak, `/usr/bin/time -l` | 742 and **764 MiB** (777 732 096, 801 472 512 bytes) | 659 and 657 MiB (690 487 296, 689 127 424 bytes) |
| peak, sampled | 742 and 752 MiB | 649 and 655 MiB |
| first suggestion | 2.3 and 2.4 s | 2.1 and 2.2 s |
| warm suggestions | 4–5 ms | 4–6 ms |

On Node the server stays about 110 MiB under ADR-014's 768 MiB; on Bun it comes
within 4 MiB of it with an index of 240 comments, so a larger history crosses it
on the binary channel sooner than a command does — DA-34.2 carries the question,
with about 2.3 KB per comment on Bun.

## Delivery

Each channel puts two things into the model directory the first time a command or
the server needs them: the model's three files and, in the runtime's subdirectory
("Where it lives"), the runtime's native files for this platform — the binding
and the libraries it loads from its own directory, two files on macOS and Linux
and five on Windows (`EMBEDDING_NATIVE` in `model.ts`, with a size and a SHA-256
each, like the model's). `prepare()` in `open.ts` does it, one preparation per
directory at a time within a process.

**A file of the right name is whole and right**, whatever else runs. Each file is
written under a name of this process's own, `<file>.partial-<host>-<pid>-<random>`,
so a `serve` and an agent's `suggest` preparing one directory at once never write one
file; it is checked against the pin as it arrives, renamed, and read back from
disk. A rename that fails because the other process got there first is its win
once the file there holds the pin, and any other failure is one line naming the
file. A file already there with its size is left alone, since nothing takes a
name before its checksum held. A download is never resumed: a command killed
halfway leaves its partial file, and the next preparation takes it away — at once
when the name carries this host and its process has ended, and after ten minutes
without a write when it carries another host's. A process id means nothing across
hosts, and a cache can be shared by a container and the machine it runs on, or by
two machines with one home on NFS; a download in progress writes every moment, so
ten minutes of silence is one nobody will finish. The body is read through a
reader rather than `for await`: Bun 1.3.14's async iterator of a fetch body failed
9–14 of 40 downloads in a row with `undefined is not a function`.

| Channel | Where the files come from | The binding |
|---|---|---|
| sources, tests | the model from `bun run model:fetch`; the runtime from `node_modules` | `onnxruntime-node`'s own |
| npm (`dist/cli.js`) | downloaded once from the release | the one in the cache |
| binary | carried inside it, written out on first use | the one in the cache |

The entry point says which: `src/cli/index.ts` calls `deliverFrom({ from:
"release" })` when it runs from a package that has `dist/ui` beside it, and the
binary's generated entry calls `deliverFrom({ from: "binary", files })` with the
files it carries.

**The release assets.** The release of each version carries, beside the six
binaries, nineteen files under names that keep every pin and every platform
apart — `multilingual-e5-small-761b726dd34f-model_quantized.onnx`,
`onnxruntime-node-1.30.0-linux-x64-libonnxruntime.so.1` — staged by
`scripts/assets.ts` from the user cache and `node_modules`, each checked against
its pin, and summed into `SHA256SUMS.txt` with the binaries. The npm channel
downloads them from

```
https://github.com/Velklish/diffalanche/releases/download/v<version>/<asset>
```

of its own version, or from `DIFFALANCHE_ASSETS_URL` when that names a mirror. A
download streams into its partial file, hashing as it goes, with its progress on
standard error — `downloading <asset>, 118.3 MB: 25% 50% 75% 100%` — and is renamed
into place only when its SHA-256 is the pin's. What one platform downloads:

| Platform | Runtime | With the model |
|---|---|---|
| darwin-arm64 | 44.9 MB | 180.2 MB |
| linux-x64 | 46.2 MB | 181.6 MB |
| linux-arm64 | 25.5 MB | 160.9 MB |
| win32-x64 | 67.1 MB | 202.5 MB |
| win32-arm64 | 72.7 MB | 208.1 MB |

The model's share is 135.4 MB; all nineteen assets are 391.8 MB. darwin-x64 has
no runtime and downloads nothing: it is refused before the platform is asked for
anything (ADR-014, 3B).

**When.** On first use and not before — ADR-014's 4A costs nothing to anyone who
never asks for a suggestion, so `serve` starts nothing. The first `suggest` or
`index rebuild` of a machine puts the files in place before it answers, and
`model pull --embedding` does that and nothing else. The first `GET
/api/suggest` starts the preparation in the background, with its progress on the
server's standard error, and does not wait for it: that request and every one
while the files arrive are answered 503 `model`, `the embedding model is being
put in place in <dir>: suggestions follow once it is there`. After a preparation
that failed, the next request gets its line once and the one after starts it
again. From the sources `model pull --embedding` downloads the model from the
release too, and the runtime stays the package's.

**The refusals** are one line and exit code 1, and write nothing:

```
diffalanche: model_quantized.onnx is not in ~/.cache/diffalanche/models/multilingual-e5-small-761b726dd34f and could not be downloaded from https://github.com/…/multilingual-e5-small-761b726dd34f-model_quantized.onnx: ENOTFOUND. Nothing was written; `diffalanche model pull --embedding` fetches it once there is a network
diffalanche: https://github.com/…/multilingual-e5-small-761b726dd34f-tokenizer_config.json has sha256 b884…, and this build pins a1d6…: nothing was written
diffalanche: model_quantized.onnx could not be written to ~/.cache/diffalanche/models/multilingual-e5-small-761b726dd34f: ENOSPC: no space left on device, write. Nothing was left behind; with room on the disk and the right to write there, `diffalanche model pull --embedding` puts it in place
```

A failure of the network and a failure of the disk are told apart: no network
helps a full disk or a directory the user may not write. A binary whose child
could not be started, or ended with another code than 0, says so in the same one
line with what the child wrote on standard error. Once the files are there
nothing reaches the network again.

**The binding, redirected at build time.** `onnxruntime-node/dist/binding.js`
requires `../bin/napi-v6/<platform>/<arch>/onnxruntime_binding.node` from its own
package, which neither channel carries. `scripts/bundle.ts` and the binary build
share one Bun plugin, `channel()`, that replaces that require with
`require(globalThis.__diffalancheOrtBinding)` — the path `openEmbedder` sets, and
the worker sets for itself from `workerData` since a thread has globals of its
own — and replaces the thread's `./worker.ts` with the channel's
`./embed-worker.js`. A new version of either file that no longer holds the text
fails the build rather than shipping a bundle that loads the wrong binding. The
binding's library is found beside it through `@loader_path` and `$ORIGIN`, which
is why the runtime's files share their directory.

**The binary writes its files out apart.** The files a binary carries live in
Bun's own filesystem, which `readFile` and `stat` reach and `copyFile` and a read
stream do not, so a file is read whole and written. Reading 180 MB of the
executable makes those pages resident, and a process that then loads the model
peaked at 913 MiB on its first run — over ADR-014's 768. So the binary runs `model
pull --embedding` as a child of itself (`process.execPath`, with
`DIFFALANCHE_WRITE_OUT=1` so the child writes rather than spawning again), and the
process that loads the model never touches those pages: the same first `suggest`
peaked at 628 MiB, the child alone at 388 MiB, and later runs at 684–713 MiB
(darwin-arm64, 2026-09-24, `/usr/bin/time -l`).

**Sizes.** With the model and its runtime inside, the binaries are 233.2 MiB
(darwin-arm64), 264.7 (linux-x64), 244.0 (linux-arm64), 288.3 (windows-x64) and
289.9 (windows-arm64), against 62–99 MiB for the six before (DA-31); darwin-x64
carries neither and stays at 67.2 MiB. The npm bundle is `dist/cli.js`, 0.4 MiB,
and `dist/embed-worker.js`, 0.1 MiB, with nothing native in either.

**Verified by hand on 2026-09-24**, darwin-arm64: a package made of `dist/cli.js`,
`dist/embed-worker.js` and `dist/ui` under Node 25.2.1, with an empty cache and a
local server standing in for the release, downloaded the five files once and
answered `suggest`; with the server stopped it answered again, and `serve` answered
`GET /api/suggest` through its thread; a mirror serving a changed
`tokenizer_config.json` was refused with the checksum line above; with no server
at all, the offline line. The binary, with an empty cache and a mirror that does
not answer, wrote its files out and answered `suggest` and `GET /api/suggest`. The
linux-arm64 binary, and the linux-x64 one under emulation, did the same for
`suggest` in a Debian bookworm container with no network and an empty cache.
`tests/delivery.test.ts` and `tests/bundle.test.ts` hold the parts that run
without a release: two preparations of one directory at once, a rename refused, a
write the disk refused, the partial files of an ended process, the binary's child
started with a stand-in for `process.execPath`, and the server's door refusing
while the files arrive.

## Tests

`tests/embed.test.ts` holds the arithmetic around the model without a model —
cutting to the window, the pooled mean, the directory name, a status read from
sparse files — and then the model itself, read from the user cache: a missing
model fails the suite with the command that fetches it rather than skipping.
With `fetch` replaced by one that refuses, it checks that the model loads once
per process, that a text's vector is the same byte for byte whatever it is
embedded with, that a Russian comment lands nearer its English paraphrase than
an unrelated comment does, that four texts land within 0.99 cosine of the
vectors recorded in `tests/snapshots/embedding-e5-small.json` — loose enough for
another CPU's kernels, tight enough to catch a dropped `query: ` prefix — and
that the other runtime — Bun under `bun run
test`, Node under `bun run test:bun` — started on `tests/helpers/embed-texts.ts`
gives the same vectors above 0.999 cosine. A Node on `PATH` older than 22.18
cannot run that helper from source, and the test says so and skips.
`tests/cli-model.test.ts` holds `model status` against a cache home of its own.

`tests/embedding-index.test.ts` holds the index with an embedder that is a
function of the text — what is embedded, kept and dropped for a new comment, an
edited text, a reply, a session removed and another model; that an unchanged
data directory is not rewritten; a broken `comments.json` and a torn index;
the order, `k` and the session filter of a search; `index status` and its
`--json`; `index rebuild` refused in one line without the model; and a search
over 10 000 vectors inside 50 ms; the update that finds nothing changed hands
back the index it was given; a session whose `comments.json` changed only its
inode is read again; a broken `comments.json` is read on every update without
the index being rewritten or its entries counted gone; a data directory with no
session gets no `index/`; and the watch leaves `index/` out.
`tests/embedding-model.test.ts` is the half
with the model: the worker thread embeds, refuses every call once closed and
refuses to start on a directory without the model; the calling thread then
gives the bytes the thread gave; an index rebuilt from scratch has the bytes the
incremental updates gave; and a comment written by `diffalanche comment` with no
server running, and one written through `POST /api/comments`, are each the first
answer to a paraphrase of them — one in the other language — after the next
update. For suggestions it checks the card's verification on the synthetic
review — a paraphrase of each severity's text, two of them in Russian, has a
comment of that text first and that severity proposed — `suggest` in text and
`--json`, and `GET /api/suggest` answering from the worker thread in under 100
ms at the median of seven once warm. `tests/suggest.test.ts` holds the vote
without the model — the floor, the weights against a count, the confidence and
a tie — and the route's shape, its 400 for a missing body and its 503 when the
model is absent; `suggest`'s refusals of a missing and a blank body and of a root
nobody reviewed, which is left without `.diffalanche`; and a thread whose module
throws as it loads, which is a `ModelError` and a 503 while the process goes on.

**The files that load the model run one at a time, after every other file.**
`vitest.config.ts` splits the suite into two projects: `unit`, and `model` —
`tests/embed.test.ts` and `tests/embedding-model.test.ts` — with
`fileParallelism: false` and `sequence.groupOrder: 1`, so a copy of the model
(476–714 MiB, above) is resident in one test process at a time and never beside
the timed tests of the watcher. The thread's tests come first in their file, so
the thread's copy has gone before the file loads its own. Every verdict is
printed with its project, `unit` or `model`, before its file.

CI caches `~/.cache/diffalanche/models` under a key made from the manifest's
hash and runs `bun run model:fetch` before the unit suite in `check` and in
`test-bun`, and before a binary is built — the `binary` rows of `smoke`, `e2e`
and the release — since the build embeds the model from there.

## The symbol index

`src/core/ml/symbols/` is tier 2 of `docs/SPEC.md` section 3, decision 11: the
definitions of every repository of the review, parsed with tree-sitter, found by
name. The binding and where the grammars come from are
[ADR-015](../adr/adr-015-symbol-index-binding.md) — `web-tree-sitter` over WASM,
the grammars of `@vscode/tree-sitter-wasm`, both bundled at build.

**The languages are data** (`languages.ts`). An entry is a grammar, the file
extensions it owns, and a tree-sitter query; the query's captures name the kind
of what they found — `@function`, `@class`, `@method`, `@type` — and a capture of
any other name is ignored. Eight entries ship:

| Language | Extensions | Definitions |
|---|---|---|
| TypeScript, TSX | `.ts` `.mts` `.cts`, `.tsx` | functions, generators and functions bound to a `const`; classes; methods; interfaces, type aliases, enums |
| JavaScript | `.js` `.mjs` `.cjs` `.jsx` | functions, generators, bound functions; classes; methods |
| C# | `.cs` | classes and records; methods; structs, interfaces, enums |
| Python | `.py` `.pyi` | functions and methods alike; classes |
| Go | `.go` | functions; methods; every `type` |
| Rust | `.rs` | functions, methods of an `impl` included; structs, enums, traits, type aliases |
| Java | `.java` | classes and records; methods; interfaces, enums |

`grammars` in `config.json` adds a language — `{ "kotlin": { "wasm": …,
"extensions": [".kt"], "query": … } }`, the WASM path relative to the root
([03-storage.md](03-storage.md)). An entry of the same name as a bundled one
replaces it, and an extension a configured language names is that language's.
A grammar that will not load, or a query that does not compile against it, costs
that language's files and nothing else: the language is remembered as failed with
tree-sitter's own message, and the route names it in `failed`.

**The index is per repository and lives in the server**, read in the background
once a review is open: `GET /api/review` hands it the repositories of the document
it served (`warm`), and each one not read yet has its files listed on disk (`listTree` of [02-git.md](02-git.md), tracked and untracked
alike, ignored ones not), reads each file a language owns and holds its
definitions — the repository, the path, the line, the name, the kind, and the
text of that line. A question that arrives before a repository is read waits for
that repository. The parse is one file after another on one `Parser` per build;
a grammar is loaded the first time a file needs it, and the runtime module is
imported only then and initialised once a process — a second `Parser.init` under
a parser in use corrupts the WASM memory they share — so a command that never
opens a review never loads it. A file over 512 KiB, a binary one, and one that
does not parse give no definitions. The index is shared by every task the server
shows, and the scope of a task is applied to what it answers
([07-server.md](07-server.md), "Symbols").

**Two things keep it fresh.** The server listens to its own stream once the
index exists, and each `diff-changed` frame has the files it names read again in
that repository — a file that is gone, or that no longer defines anything,
leaves the index. A frame that names nothing (a fallback rescan) or a path that
is not on disk (the temporary name of an atomic write, which Bun reports) cannot
be trusted to name the files that moved, so the whole repository is read again.
And every question and every review read compare each repository's change set
with the one the index last saw: a file whose content moved differs from the
base, so it is in the change set, and a patch that changed or a file that entered
or left it is read again. That second path is what reaches a repository whose
frames never come — one outside the scope of the task the watcher follows,
which another window's task can still show. Every update is chained onto the
repository's definitions, so a question waits for the updates asked before it;
an update that fails drops the repository, and the next question reads it whole.
The listener is one more subscriber of the stream, so `open()` counts it once the
index exists.

**A name is matched fuzzily** (`match.ts`), without regard to case: the whole
name first, then a name that starts with the query — the shorter the closer —
then one that holds it, the earlier the closer, then one whose letters come in
the query's order, `ctrlsvc` finding `ControllerService`, each skipped letter
costing a point. Ties go to the shorter name, then to the repository the review
lists first, then to the path and the line.

**How long it takes** is recorded, not budgeted to the millisecond: the machine
the numbers come from was shared and busy (load average 15–22 on 8 cores), so
they say what order of time to expect.

| what | Node | Bun |
|---|---|---|
| 300 generated files in four languages, `tests/symbols.test.ts` | 494 ms | 346 ms |
| the 252 code files of the full synthetic review, parse and query | 1 315 ms | 2 787 ms |
| the first `GET /api/search/symbols` over the full synthetic review | 1 072 ms | 1 000 ms (binary) |
| a query once the index is built | 44 ms | 61 ms |

`tests/symbols.test.ts` fails when indexing the 300 files takes longer than
`SYMBOL_INDEX_BUDGET_MS`, 20 s — forty times the measurement, because the suite
runs on loaded machines and the number is there to catch a parse that became
quadratic, not a slow afternoon.
