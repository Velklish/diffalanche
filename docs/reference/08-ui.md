# 08 · UI

`src/ui` is the review workspace of
[the handoff](../design/HANDOFF.md): the shell, its tokens and themes, the
store, the diff, the comment form, the threads, the header, the live update, the
keyboard map, global search, the empty states, and the scope of a review task —
the `SCOPE` pill, the editor, select mode, and the address that says which task
this window is on. What is not here yet is named by the task that brings it:
browsing a repository (DA-37) and the composer's suggestions (DA-35) are
Phase 2.

## The page

`main.tsx` installs the measurement hooks on `window.__perf` and mounts `App`.
`App` applies the theme to the root element, asks the store for the review once,
and lays out the five regions of handoff section 1:

| Region | Size | Component |
|---|---|---|
| header | 52 px | `components/Header.tsx` |
| sidebar | 308 px | `components/Sidebar.tsx` |
| centre | the rest | `components/CentrePanel.tsx` |
| right column | 392 px | `components/ThreadRail.tsx`, `components/ThreadCard.tsx` |
| status bar | 30 px | `components/StatusBar.tsx` |

The whole page is one vertical scroll: the header, the two side panels, and the
status bar are `sticky`, so the document scrolls and a file card is reached with
`scrollIntoView`. The repository bar sticks under the header at `top: 52px` and
is 38 px tall, so 90 px is everything fixed to the top of the page.

**Either side panel comes off the screen whole.** `[` and `]`, the text symbol in
the panel's own top row, and the stub the header keeps while the panel is gone
all call the same action; the panel is unmounted rather than narrowed, and the
centre column takes the freed width. The floor `.app` keeps is what the panels
still on the screen add up to — 860 px of reading column plus 308 and 392 for
whichever of them is there, so 1560 / 1252 / 1168 / 860 px, written as three
classes on `.app` (`sidebar-off`, `rail-off`). Below the floor the window scrolls
sideways and the panels keep their widths, as the handoff requires. **Nothing
here is a breakpoint**: no rule on this page reads the width of the window.

Both panels and the `wrap` / `scroll` choice are the reader's preference, not the
task's, so they live in `localStorage` under `diffalanche.sidebar`,
`diffalanche.rail` and `diffalanche.wrap` the way the theme does, and a value
that is not `off` counts as on — a browser with no storage and a first run give
the same page.

`GET /api/review` is asked once, when the page opens, and nothing is loaded
lazily afterwards.

## Tokens, themes, fonts

`tokens.css` carries every token of the handoff for both themes: the dark
palette on `:root`, the light one under `:root[data-theme="light"]`, plus the
`dcin` and `dcpulse` animations. The header's toggle writes `theme` into the
store and the store into `localStorage` under `diffalanche.theme`. An inline
script in `index.html` sets `data-theme` from that key while the document is
parsed, before any stylesheet applies, so a reload in the light theme never
flashes the dark palette; `App` keeps the attribute in step with the store
afterwards. Each theme also declares its `color-scheme`, so scrollbars and other
native controls follow it.

Both families are local assets under `src/ui/assets/fonts`, declared in
`fonts.css` with the fallback stacks of the handoff: Instrument Sans in latin
and latin-ext, JetBrains Mono also in cyrillic, because the interface has
Russian strings. The tool works offline, so the page asks Google Fonts for
nothing; a Playwright test asserts that no request leaves `127.0.0.1`.

The logo is three squares built in markup (`components/Logo.tsx`) and the
favicon is the same mark as an inline SVG data URI in `index.html`. There is no
raster file and no icon font.

`DESIGN.md` at the repository root is the token authority beside the handoff:
it records the visual system as `tokens.css` implements it, both themes, in the
DESIGN.md format that the Impeccable skill and its design detector read.
`tokens.css` and `DESIGN.md` carry the same values and change together; the
handoff stays the source of layout, screens, and behaviour, and remains the
document a token value is traced back to. What the format cannot hold —
the shadows, the two keyframes, the focus rings, the 1560 px threshold — is in
`.impeccable/design.json` beside it. A UI change starts by running
`node ~/.claude/skills/impeccable/scripts/context.mjs --target <file>`, which
loads those files together with `PRODUCT.md` and the review screen's surface
brief in `.impeccable/surfaces/`.

`tests/design-contrast.test.ts` holds the tokens to two contrast rules, in both
themes, as two groups with their own bounds: text pairs at the 4.5:1 of WCAG AA,
and the marks that are the only signal of a state — the history mark, the tick
and its unpicked `·`, the focus ring — at the 3:1 of WCAG 1.4.11 (DA-56.2). Which
marks count and which dots are decoration is `DESIGN.md`'s (Shapes). The focus
ring is `accBd` and measures 1.6–2.0:1, so its four pairs are listed in the test
as recorded exceptions: a new pair under 3:1 fails, and so does one of them
clearing it. The colour is DA-56.7's to decide.

## Store

One zustand store, `store.ts`. Its slices are the ones the handoff's "State
Management" section names — theme and base, sessions, navigation, commenting,
threads, search and overlays, feed, scanner — plus `review`, which holds what
the server sent, and the two the scope brought: the editor's own draft and
select mode's. The prototype had the review written into the page, so that slice
has no counterpart there.

A slice carries the state its screen needs from the first task that renders it,
and the actions of the task that makes it interactive: the composer's, the
rail's, the header's, and the live update's are all here.

The review is turned into derived state once, when it arrives: the flat list of
file entries the centre panel renders in order, and the counters of the document
indexed by repository and by `<repo>/<path>`, which is what the tree and the
card headers ask for. The counters themselves are the domain's
([04-domain.md](04-domain.md)) and arrive counted; the UI indexes them and does
not count anything of its own. A write recounts them with the domain's own
`countReview`, so the badges are right between the write and the next read.

**A request that fails says what the server said.** Every fetch in `store.ts`
and `live.ts` whose failure the reader is told about reads the body through
`refusal()` — the `{ error, message }` of [07-server.md](07-server.md) — and
shows its `message`, falling back to `the server answered <status>` only when the
body is not that shape. `refusal()` is exported from `store.ts` and `live.ts`
imports it: two modules are the whole API client, and a module of its own would
be one function with two callers. A live read puts what it was reading in front
— `the thread c_7 could not be read: <message>`, `the diff of <repo> could not be
read: <message>` — because a frame's failure reaches the toast without a gesture
that would say what it was about. The two live reads used to report the status
alone, so a hand-edited `comments.json` that the server named by file and field
reached the reader as `the server answered 500` (DA-102). **Background reads stay
silent**: `/api/config`, the sessions list and `/api/activity` return on a
refusal without a toast, because a feed or a list that did not load is not worth
putting in front of the reader. A 404 on `GET /api/repos/:repo/diff` is neither:
it is the repository leaving the review, and it is applied, not reported.

A file card subscribes to the store by its own id — the composer line of *this*
file, the view of *this* file, the hunks *this* file has collapsed. zustand
re-renders a subscriber only when its selected value changes, and the state a
card reads is stored per file rather than in one object for the whole review, so
opening the composer or collapsing a hunk touches one card and re-tokenizes one
diff, not three hundred.

## Types of the on-disk format

`types.ts` is one import for the components and no shapes of its own: it
re-exports `src/core` — the on-disk format of `docs/SPEC.md` section 7 from
`src/core/storage/types.ts`, the counters from `src/core/domain/counters.ts`,
and the change set with `ReviewDocument` from `src/core/types.ts`, which is what
`GET /api/review` answers with ([07-server.md](07-server.md)). The UI mirrored
those shapes while the domain was being written and now reads the originals, so
the two can no longer drift.

That puts a rule on `src/core`: everything `src/ui/types.ts` reaches has to stay
pure types and pure functions. `src/ui/tsconfig.json` compiles with
`"types": []` — no Node globals in the browser bundle — and type-checks that
graph through these imports, so a module in it that touched the Node API would
fail the build. `countReview` and `byCodePoint` are in the bundle for the same
reason and cost nothing else.

## Loading

While the server answers, the page shows the shell: the header is already real,
the sidebar keeps placeholder rows, the centre one empty card
(`components/Skeleton.tsx`). No spinner, and the panels have their final widths,
so nothing moves when the data arrives.

A review that cannot be loaded — the server answered with an error, or the
connection dropped — leaves the store in `failed` with the reason, and the
centre panel says so in one line.

A root with no current session is not one of those. `GET /api/review` refuses it
with `no-current-session`, which the store reads by its code rather than by its
sentence and turns into the `no-session` status: the first-run screen, not a
failure ([07-server.md](07-server.md)).

## The task this window is on

`?review=<name>` in the address is what this window shows, and `current` is what
it shows without one. The name is read once, when the store is created, and from
then on **every request of the page carries it** — the review, the threads, the
warnings, the repository a live update fetches, the scope editor's candidates,
the live stream itself, the export, and every write
([07-server.md](07-server.md)). `onTask()` in `store.ts` is the one place that
appends it, and `live.ts` fetches through it for the same reason the store does:
a window that read one task and wrote into another would put a person's comment
where nothing they can see reads it back.

Switching a task in the sessions menu writes the address and reads the review
again; it does **not** call `POST /api/sessions/:name/use`. There is no main
task, and `current` is the default for a human typing a command by hand, which
only `review use` moves ([ADR-010](../adr/adr-010-review-task-scope.md),
decisions 4 and 7). The address is *pushed*, so `Back` walks the tasks this
window has been on and `App` follows it with `syncTaskFromUrl`.

`Create`, in the sessions menu and behind `New task…` alike, sends
`use: false` — **except on the first-run screen**, which is the one state in
which there is no `current` to leave alone. A root whose only session the CLI
cannot name without `--review` is a root the tool half works in, so the first
session of a root becomes current and the window stays on the plain address. The
condition is `status === "no-session"` in `createSession`, which is that screen's
own state rather than a flag a caller passes, and `tests/ui-empty.test.ts` holds
both halves.

A name the data directory has not is a `no-such-session`, and the centre panel
answers it by naming the task and offering the current session. That address is
the one a person types and pastes by hand — an agent prints it, a human copies
it into a second window — so a typo in it is the failure most likely to be a
typo, and a screen that only said "the review could not be loaded" would leave
the reader with nothing to press.

**A window hears about its own task's comments, whichever task that is.** The
stream is opened as `GET /api/events?review=<name>`, which is how the server
learns the task this window is on and follows it
([05-watcher.md](05-watcher.md)); the three comment frames then carry the name of
the session their thread belongs to, and the page drops the ones that are not
about the review on screen. The parameter is a **registry and not a filter**: the
frames are still one broadcast on one sequence of ids, and dropping is the
client's own.

**Which frame a window answers depends on whether it has an address.** A window
with no `?review=` shows whatever `current` is *and writes there too*, so it
follows `current-changed` and re-reads; a window on a task of its own ignores
that frame entirely, which is what the address is for. Both re-read on
`session-changed` for **their own** task and neither re-reads for another's:
since the watcher follows several sessions, that frame now arrives for tasks a
window is not on, and re-reading megabytes for those is what
[ADR-010](../adr/adr-010-review-task-scope.md) forbids. A window that showed one
task while writing into another is the damage this prevents — the comment lands
in a task the reader cannot see, against a base that may not have the line.

Because an open `EventSource` keeps the address it was made with, **switching a
task reopens the stream** — otherwise the window would go on declaring the task
it left, and the server would follow the wrong one. `startLive` watches
`reviewName` for that and nothing else; the reconnect costs a `Last-Event-ID`
replay and no reload.

A response that belongs to a task the window has left is **dropped rather than
applied**. `loadReview` carries a generation checked after every await, which
covers the callers `switching` does not gate — `syncTaskFromUrl` and the two
stream handlers — and `applyRepositoryDiff` takes the session its patch was
fetched for. The damage it prevents is concrete: a repository unknown to the
review on screen is *appended*, so another task's change set would arrive whole,
computed against another base, with the composer usable on its lines.

`diff-changed` **is** delivered, and what the page fetches for it is read from
git rather than from that task's `diff.json`: the watcher rewrites the cache of
the current session only, so a task that is not current holds a change set
frozen at the moment it was last read ([07-server.md](07-server.md)). Served
from the cache, the card of an edited file never showed the edit — measured
three times out of three on the synthetic review — while the same event on the
current session showed it every time.

Closing the comment half of the gap means teaching the watcher to follow more
than one session: [DA-55.1](../archive/DA-55.1-watcher-follows-one-session/task.md).

## Empty states

Two screens of handoff section 10, and they answer two different questions.

**First run** (`components/FirstRun.tsx`) is a root nobody has opened a session
in. It takes the whole body under the header — there is no review to lay out —
and carries the mark, the title, the three metrics, the form, and the line that
does the same thing from a terminal. The metrics come from `GET /api/scan`, the
one route that reads git per request: repositories found, repositories with
changes, and linked worktrees. Until it answers they are dashes rather than
zeros, because nothing has been counted yet — and a scan that was **refused** is
not left to those dashes to say: `scanFailure` carries the server's own sentence
and the screen shows it under the metrics, in the warnings bar's idiom, with a
`повторить` that asks again (DA-98, product principle 5). A dash then means
"not asked", which is the only thing it ever meant. `Create` posts to
`POST /api/sessions` with the base written in the grammar the CLI and the server
share — `head`, `branch`, `branch:<name>`, or a ref — and then reads the review,
which the new session is now the current one of; a refusal leaves the screen
where it is and puts the server's own sentence in the toast.

The base on that screen is `newBase`, the field the sessions menu's own create
form writes and `createSession` reads, in the grammar the CLI and the server
share — so a session is created one way whichever screen asks for it. The three
modes are on the screen rather than behind the picker of handoff section 5,
because that picker applies a base *to a session* and on this screen there is
none yet.

**No changes** (`components/NoChanges.tsx`) is a session whose base resolves to
what the working trees already hold: the review is there and has nothing in it.
It replaces the file cards in the centre panel and offers the two things that
would change the answer — the base and the session. `Other session` opens the
header's own menu; `Change base` opens the base picker.

## Overlay and toast

`components/Overlay.tsx` is the scrim-and-panel primitive: the scrim closes on a
click and on `esc`, the panel does not, and it appears with `dcin`.

It also holds the focus while it is open. `Tab` and `Shift+Tab` cycle inside the
panel — an overlay a reader can tab out of is a page they cannot see and cannot
click, and the scrim itself is not a stop on the way round, since a ring that
landed on a full-window transparent button would look like a ring that had gone
nowhere. When the overlay closes, by `esc`, by the scrim, or by finishing what
it was for, the focus goes back to the control that opened it. A child that
takes the focus as it mounts — the search field does — keeps it. The listener is
on the document rather than on the panel, because a click on the page behind can
take the ring out of a panel that could then no longer catch it. The base
picker, the export, and global search are inside it; the sessions menu is a
popover on its pill rather than a modal, and closes on a press outside itself.
**One overlay is on screen at a time, and the keyboard enforces it.**
`src/ui/overlays.ts` is the ladder — every overlay in order, topmost first, each
with the store flag that opens it and the action that closes it — and `keys.ts`
asks it rather than enumerating flags. `esc` closes the **top one and nothing
else**; a letter under any overlay belongs to the overlay; and `⌘K` or `⇧⇧` over
an overlay that is not the palette is **refused**, because replacing it would
mean every overlay knowing how to close every other, and "one at a time" is the
rule this section already had. Adding an overlay is a row in that list and no
edit to `keys.ts`, which is what the hand-written lists cost: three flags of the
scope surface existed that neither of them mentioned, so one `esc` over the
scope editor closed the editor *and* threw away the composer's draft underneath
it, and `c` under the open editor opened a composer on the file behind (DA-70).

`Overlay` no longer listens for `esc` itself. Two document listeners answer one
press, and the second one reached past whatever the first had closed;
`App.tsx` still renders the overlays of the scope exclusively, so the
confirmation replaces the editor rather than stacking on it.

**The focus goes back to what opened the *ladder*.** The scope editor, its
confirmation and the new-task form occupy one position in `App.tsx`, so React
deletes one subtree and mounts the other: an opener recorded per overlay made
every swap record the button it was replacing, which was detached two commits
later and restored nothing at all — the ring ended on `<body>` and the next
`Tab` started from the top of the page (DA-100). `Overlay` takes a `ladder`
instead: `scope` for those three, and one of its own for the base picker, the
export and global search, which cannot swap with anything. The first overlay of
a ladder records `document.activeElement`, a swap keeps it, and the restore is
owed once the ladder has emptied — read after the commit rather than during it,
because React renders the arriving overlay *before* it cleans up the leaving
one, so a swap is only visible afterwards.

**An opener that cannot take the ring hands it to the header's control for the
same ladder** (DA-100.1). The opener may have gone — the no-changes screen
unmounts under a review that arrived — or still be in the document but disabled,
like the select bar's `New task…` once nothing is ticked, and `.focus()` on
either does nothing. `isConnected` passes the second, so the restore does not
guess from the element: it calls `.focus()` and asks the document whether the
element now holds the ring. If not, the ring goes to the control the header
marks with `ladderHome()` — the `BASE` pill, the `SCOPE` pill, search, `Export`
— which opens the same overlay again and stays on screen while the review does.
`<body>` was never a fallback: it is where the next `Tab` starts from the top of
the page. A whole-root session has no `SCOPE` pill, so the new-task form can end
with nothing to take it; that case is **not silent** — the restore writes a
`console.warn` naming the ladder, which is what a test or a reader of the console
sees instead of a restore that looked as if it had worked.

**The restore waits for a switch that is under way** (DA-100.2). Creating a task
from select mode and `Change base` → `Apply` on the no-changes screen both close
their overlay *before* they read the review the action produced, and the opener
survives the close only to lose the ring a moment later: the switched review
empties the draft and disables `New task…`, or replaces the no-changes screen and
`Change base` with it. Measured in Chromium, the restore put the ring on the
opener and the review took it to `<body>` 60 to 900 ms later. So the restore does
not run while `switching` is set — the flag the store holds across exactly those
reads, and whose meaning is "the review on screen is being replaced" — and runs
one macrotask after it clears, when the new review has been committed; by then
the opener is disabled or gone, and the header's control takes the ring: the new
task's `SCOPE` pill, the `BASE` pill. The other candidate was to watch the
restored control and move the ring if it lost it to nowhere; it needs no store,
but it rests on the browser sending `focusout` when the focused control is
removed or disabled — the Chromium this suite drives does, and no other engine
was measured — and on a timer for how long to watch, which would have been a
guess. The cost of
the one chosen is that `Overlay`, the primitive of every overlay, reads one flag
of the store: an action that closes an overlay and then replaces the review
without holding `switching` would slip past, which is why the rule is written
here. The wait also means a reader can put the ring somewhere while the switch
runs, so the restore is owed only while the ring is nowhere — on `<body>` — and a
reader who has already moved keeps where they are.

`components/Toast.tsx` shows the store's `toast` for 2.2 seconds at the bottom
centre, counted **from the raise and not from the text**. A toast is
`{ text, seq }`: `seq` comes from a counter in the store, so the same sentence
said twice is two toasts and the second one gets the whole 2.2 seconds. Keyed on
the string, a repeat compared equal under `Object.is`, the component never
re-rendered, the first deadline stood, and the answer to the second press was on
screen for whatever was left of it — which is exactly the moment a reader
repeats an action because they did not see the answer (DA-105). `raise()` is
what every site that sets a toast goes through, the seventeen that write
`set({ toast: … })` directly included; `null` still means nothing on screen.

## Navigation

The sidebar (`components/Sidebar.tsx`) is the tree of handoff section 1.3: one
branch per repository that has changes — repositories without changes never
reach the UI — with the caret, the path, the open-comment counter in the colour
of the worst of them, and `· N files`. Under it the files, indented 28 px, with
`+N`, `−N`, and the badge of open comments on that file. The selected file is
`--sel`, the repository of the selected file `--panel3`. Clicking a file selects
it and scrolls its card into view. The rows are buttons in the order they are
read, so the keyboard walks the filter, a repository, then its files.

A repository row is two targets, not one: the caret collapses the branch
(`collapsedRepos`), the rest of the row jumps to that repository's section with
the same `revealCard` a file uses. The row is one button, one tab stop and one
focus ring, and the two actions are told apart twice — the pointer by where it
landed (the click handler asks whether the caret is under it), the keyboard by
which key was pressed: `Enter` jumps, `Space` collapses. A button acts on both
keys by itself, so the handler cancels the native activation before it fires the
click. `aria-expanded` is on the row, where a screen reader reads it when the
row takes the focus; the caret glyph is `aria-hidden`, being the same state
drawn for the eye.

The filter is a substring over the repository path and the file path, folded to
lower case: a repository whose own path matches keeps all of its files, one that
matches through its files keeps the files that matched. The number inside the
field on the right is how many files matched — a collapsed repository still
counts its own; a query that matches nothing says so. A review with no changes
at all is a different thing and is DA-27's empty state, not a filter miss.

The current file follows the reading position. When the scroll stops — 120 ms
of quiet — the page asks which card lies under the header and the repository bar
(`document.elementFromPoint` at `PROBE_Y`) and selects it. One hit test after
the scroll, rather than three hundred intersections during it: the harness
scrolls the whole review in five seconds and the budget is 8.3 ms of CPU per
frame.

`PROBE_Y` lives in `reveal.ts` and is 100 px: 52 px of header, 38 px of
repository bar, and 10 px of clearance. There is **one constant, two importers
and three hand-written copies of the number, and all of them move together.**
`components/CentrePanel.tsx` asks there which card is being read and `live.ts`
asks there what is under the reader's eyes before it patches the page; both
import the constant and hold no copy. The three that cannot import it are
`.file-card { scroll-margin-top }` in `styles.css`, which is the same value so
that a card jumped to lands on the probe and is the current file once the scroll
settles, and the two Playwright helpers that hit-test the same point —
`underTheHeader` in `e2e/sidebar.spec.ts` and the placement of the card across
the probe in `e2e/live.spec.ts`. Move the constant without those three and the
gap shows up as a test that passes while measuring the wrong pixel.

A probe left inside the bar hits the bar, which is sticky and never moves: the
tree then stops following the scroll, and a live edit above the reader moves the
text under their eyes by everything it added (`e2e/live.spec.ts` measures that
drift).

The footer is the handoff's pulsing dot and `watching · 127.0.0.1:<port>`.
It says `watching` and nothing else until DA-25 gives it the state of the SSE
connection.

The two tabs are `changes` and `select`; the `all files` tab of the handoff is
Phase 2 (DA-37) and is not rendered. In `select` every row gains a tick and the
row's own action becomes picking rather than jumping, while the caret keeps
collapsing the branch — the same two targets told apart the same two ways, and
the sentence the rows point at with `aria-describedby` says which of them
`Enter` does in the mode it is in.

## The diff

One `Diff` of `react-diff-view` per file card, split view by default
([ADR-008](../adr/adr-008-diff-rendering-verdict.md)); `@git-diff-view/react`
and the query switches that let one build be measured every way are gone with
the verdict, and so is the dependency.

The library renders the lines; the project renders everything around them. The
card header (`components/FileCard.tsx`) carries the caret that collapses it, the
path — `old → new` for a rename — the open-comment badge in the colour of the
worst severity, the state chip (`new file`, `deleted`, `renamed`, `binary`,
`too large`), the counts, and the `split` / `unified` segments; the choice is
remembered per file in the store, so leaving a file and coming back to it keeps
the view. A file the reader listed without content — `FileChange.omitted` is
`binary` or `too-large` ([02-git.md](02-git.md)) — gets its chip and one line
saying so instead of an empty diff.

The hunk header is a `Decoration` row of the library's table: the `@@` line and
the control that hides the context lines around the changes or brings them back
(`↑ N lines`). The bundle carries three context lines per hunk (`git diff -U3`),
so that is the whole of what can be shown or hidden today; asking the server for
more is Phase 2.

The handoff puts that control at the right end of the hunk header. The header
row is as wide as the diff — over 1080 px — so at the right end it would sit
off-screen until the reader scrolled sideways. It is `position: sticky; left: 0`
next to the `@@` text instead, the way the composer strip sticks, and stays in
reach wherever the reader has scrolled to. That is the one place the diff view
departs from the handoff.

`renderers/ReactDiffFile.tsx` also holds the slots the surrounding tasks fill: a
selected range that draws over the lines the composer is being written for, and
rows inserted under a line — the composer itself and the inline thread cards
(DA-23). Both are given in line numbers of the new side, as the store holds
them; the change keys the library indexes by are worked out where the hunks are.
The same module binds the library's `gutterEvents` and `codeEvents`, which is
where the line under a pointer is known. A handler there is called with
`{ side, change }`: `side` is `old` or `new` in the split view and is **absent**
in the unified one, which has a single column, and the line is
`computeNewLineNumber(change)`, which is `-1` for a deletion. Reading the new
column off those two is the whole rule; walking `data-change-key` in the DOM
instead gets the split view right and the unified view wrong.

`react-diff-view` highlights through refractor tokens, not on its own. It was
written against refractor 3, whose `highlight` returned an array of nodes, while
refractor 5 returns a hast root; `ReactDiffFile` adapts the one to the other in
three lines. Without that adapter the page throws and renders nothing.

The renderer imports refractor's core and registers nine grammars —
TypeScript, TSX, JavaScript, JSX, C#, Python, Go, Markdown, JSON. The root
export of the package registers every Prism language and would put them all in
the bundle. A grammar registers the ones it builds on, so `tsx` pulls in `jsx`
and `typescript` by itself. A file whose extension is not in the table is
rendered without highlighting rather than with the wrong grammar.

The patch is parsed with `nearbySequences: "zip"`, which pairs a deletion with
the insertion beside it, so the two columns of the split view line up instead of
running one block after the other.

### Wrapping, and why `scroll` still gives the table a width

A line longer than its code column wraps inside that column, which is what the
header's `wrap` / `scroll` toggle leaves on by default: `.app.wrap` makes the
table `width: 100%` and the code cell `pre-wrap` with `word-break: break-all`,
and the card's own horizontal scroll goes away — the diff is as wide as the card.

`break-all` rather than a break at word boundaries, because the height of a card
is arithmetic and has to be right before the card is ever drawn
([ADR-008](../adr/adr-008-diff-rendering-verdict.md)). With `break-all` a wrapped
line fills its column exactly, so `ceil(length / columns)` is the number of
visual lines the browser will produce; breaking at words puts the break earlier,
the real row is taller than the count, and the scrollbar drifts under every file
that has not been drawn yet. `measure.ts` counts the width of a code column from
the widths `styles.css` fixes and never measures the DOM: the reading column is
`max(document.documentElement.clientWidth − panels, 860)` — the page the layout
lives in, which is the viewport **less a classic scrollbar**, where
`window.innerWidth` counts one the centre panel never gets — a card is 34 px
narrower than that (the centre panel's padding and the card's border), a row
spends 42 px per gutter and 20 px on the code cell's padding, and JetBrains Mono
advances 0.6 em, so a character of the 12 px code is 7.2 px. **An added or deleted file has one
gutter and one code column even in a split view** — the library calls it
`monotonous`, because it has one side to show — and counting it as two halves
overstated those cards by half their height.

**The card is sized and drawn from one answer.** `oneColumn(status)` in
`measure.ts` says whether an entry has one side — `added` or `deleted` — and it is
what `codeColumnChars` sizes by and what `mergedPatch` asks before it hands the
library a type. The library draws from the type the patch parses as, and a type
change with one half listed without content ([02-git.md](02-git.md)) is a
`modified` entry whose one remaining patch parses as `add`: drawn in one column
and sized as two, so with `wrap` on the estimate wrapped its lines at half the
width they had. `mergedPatch` now gives such an entry `modify`, as it already
did for one that kept both halves (DA-76.2). Nothing drifted on screen yet,
because the half that survives has so far always been a one-line link.

The placeholder of a card whose diff is not mounted takes that estimate **in the
render the estimate changed in**: `components/FileCard.tsx` keeps the last
measured height in state and drops it the moment a new estimate arrives, because
a measurement belongs to the width it was taken at and a panel that has just
gone changes the width. A height written to a ref after the render is a frame
late, and nothing re-renders the card to read it — which is the drift again,
under a promise that the width is recomputed.

`scroll` is the other half of the toggle and the behaviour that shipped before:
code in a diff does not wrap, and the library's table is `table-layout: fixed` at
`width: 100%`, so unwrapped lines spill out of their cells and the browser
measures every one of them on every frame that touches the card. Measured on the
synthetic review, that cost 2.5 ms of CPU per frame out of a budget of 8.3. So
the card gives the table its width: the widest line of the patch is counted when
the card is measured anyway, handed down as `--code-width` in `ch`, and the table
is `max(1080px, 84px + 2 × (--code-width + 20px))` — the handoff's minimum of
1080 px, the two 42 px gutters, and two equal code columns. Fixed layout with an
explicit width never measures its content. The card scrolls sideways as one,
which is the one scrollbar per file the handoff asks for.

A tab is counted as one character, which it is not on the screen; no fixture or
repository read so far has put one inside a diff line, and a file that does will
claim slightly less height than it takes.

**Every reader of a patch here stops at `diff --git`.** One entry can hold more
than one patch — a file that changes type is two, because git cannot write that
change as one ([02-git.md](02-git.md)) — and each of these readers used to skip
to the first `@@` and then read to the end of the string, which made the second
patch's `--- /dev/null` and `+++ b/…` a deletion and an addition like any other.
Measured on the change set of the reproduction in
[02-git.md](02-git.md) — a one-line `thing.txt` replaced by a link to
`/etc/hosts`, which git writes as two patches: `measurePatch` answered 140 px for
the pair against 48 + 48 = 96 px for the halves measured apart, the 44 px being
the second patch's `diff --git`, `--- /dev/null` and `+++ b/…` counted as rows;
and `firstAddedLine` answered 3 for a file whose first added line is 1, having
read `+++ b/thing.txt` as an addition. It touches
`measurePatch` and `hiddenLines` here, `splitHunks` and `hasNewLine` in
`patch.ts`, `firstAddedLine` in `anchor.ts`, `preview` in `search.ts`, and the
file card, which parses every patch of the entry rather than the first one.

## The header

The 52 px bar of handoff section 1.1 carries five things that do something, and
each is asked for only when it is opened — the review itself arrives in one
response, but these are not part of it.

**The history of tasks** (section 7) is what the session pill opens; it has its
own section below. The create form under it takes a name and a base written in
the CLI's own grammar (`head`, `branch`, `branch:origin/develop`, a ref),
because the server parses it with the domain's parser and one base should be
written one way everywhere; the same grammar is under the field as a hint.
`Comment on review` is in this menu for the reason DA-22 gives.

**The quiet mark** on the session pill is a task that appeared in the data
directory, or one that was closed or reopened, while this window was open. It is
a dot and a sentence for a screen reader, and it is raised by
`sessions-changed` and by nothing else; opening the menu clears it. What it
deliberately does not do is in the history's own section below.

**The `SCOPE` pill** (section 1.1) is beside `BASE` and the same control shape:
what this task is about, and the way into the editor that changes it. **A
session with no scope has no pill at all** — it is about the whole root, which is
not a narrowing, and there is nothing there to manage. What the pill counts is
the scope **as it is written**: an entry is a repository and the paths an entry
names are its files, so a repository held whole prints `1 repo` and adds no file
count. `src/ui/scope.ts` is the one place that counts and labels it, which is
why the pill, the editor's footer and select mode's bar never disagree — and why
the number does not move when a file of the scope stops changing, which is
decision 5 of [ADR-010](../adr/adr-010-review-task-scope.md) and an ordinary
state rather than an edge.

**The base picker** (section 5) is the three modes, and under `branch` the
candidates of the whole root from `GET /api/repos/branches`
([07-server.md](07-server.md)). The list is the union over repositories with how
many carry each, because a base is one spec applied to every repository
separately; the first row is the default branch of whatever remote each
repository has, which is `branch` with no name. `src/ui/base.ts` is
the one place that writes a base as an argument and reads it back as a label,
so what the picker's footer promises and what `Apply` sends cannot differ.
`Apply` calls `PUT /api/sessions/:name/base` and reads the review again — the change set is
computed against the base, so it is not patched — and says what it applied in a
toast.

A whole review arriving is a whole review replaced *when it is another
session's*: switching a session, creating one, and applying a base all read
`GET /api/review` again, and the draft in the composer, the selected range, the
open reply, the focused thread, the collapsed hunks and the changed-hunk marks
all point at lines and comments that are no longer on the screen, so none of
them survives it. The *same* session read again is not that — the stream asks
for one whenever anything under `reviews/` changes — and it keeps all of it: a
watcher waking is not a reason to take a form away from the reader. Split or
unified is about a file rather than about a review and is kept for the files the
new one still has, either way.

**The `wrap` / `scroll` toggle** is the theme toggle's control with words in it
(`.segments.labelled`): `wrap` is the default and lets a long line wrap inside
its code column, `scroll` gives the card back its own horizontal scroll and
columns aligned character by character. Like the theme, it is the reader's and
lives in `localStorage`.

**The stubs of a hidden panel** appear in the header only while the panel is
gone — `›` right after the mark for the sidebar, `‹` at the far end for the
rail — and the arrow points at the screen, which is where the panel comes back
from. The press that takes a panel away lives in that panel's own top row
(`components/PanelAway.tsx`), because while the panel is there the header has
nothing to say about it.

**The counters** are buttons: `N open` shows every thread of the review, `N
awaiting you` narrows it to the ones an agent has answered and nobody has
closed. That second filter is a chip in the rail while it is on, next to
`unanswered`, so a filter the header set can be taken off where it applies.

**The export** (section 9) asks `GET /api/export` twice when it opens: the
markdown, which is what `Copy .md` writes to the clipboard, and the same
comments as JSON, which the `rendered` view lays out. Rendering the markdown
back would mean a markdown parser in a page that already has the comments. The
two tabs are one export, so `rendered` groups and sorts exactly as
`exportMarkdown` does — the whole review first, then the repositories by code
point, then the comments by path and line, and "1 comment" in the singular
([04-domain.md](04-domain.md)).

**The scanner warnings** (section 1.2) are the bundle's own `warnings` — what
the scan and the base resolution had to say. Dismissing them is per session,
because a warning is about the base that session resolves and the next one
resolves its own, and it is remembered in `sessionStorage` under
`diffalanche.warningsDismissed`: a reload of the same review should not bring
the bar back, and tomorrow's run should not still be hiding it. The theme is a
preference and lives in `localStorage`; "I have read this" is not one. The bar is not sticky: the header is, and a second bar under
it would sit over the point the centre panel asks which card is being read at,
and over the top of a card a jump has just brought up.

**A list that says something new un-dismisses the bar, whatever produced the
list.** That is a property of the state and not of the live frame: `afterWarnings`
in the store is the one writer of the field, and the live frame and the review
re-read both go through it. A warning the scan has just found is news even to a
reader who put the bar away, because what they dismissed was the list before it
(`docs/SPEC.md` section 5 — nothing is silently dropped), and the remembered
dismiss in `sessionStorage` goes with it, or a reload would hide a bar the
reader has never seen. An identical list changes nothing, or an ordinary re-read
would bring the bar back.

**The comparison is between two reads of the same session.** Another session's
list is not this one's news, so a read that switches sessions — the first load
of a page included, which switches from no session at all — stores the warnings
and leaves the dismissal where it is. The key is the session name and it does
the rest: the new session's bar shows because the name does not match, and a
reader who leaves a task and comes back finds the bar as they left it.

The re-read is the path the per-session key cannot cover, and it is the reason
the rule lives in the state: `Apply` on the base picker and on the scope editor
both read the whole review again — the change set is computed against the base
and against the scope, so it is not patched — and the session's *name* has not
moved, so `warningsDismissedFor` still matches it. A base that stopped resolving
in one repository would otherwise put that repository's warning in the document
and show nothing at all. Neither path can be reached by a `warnings` frame
instead: a metadata change makes the watcher emit `session-changed`, and both
writers call `markSelf` before re-reading, so `live.ts` swallows that frame as
this page's own write.

The status bar's right-hand side is the context line of section 1.6: what this
review is read against, and how many threads are open in it. The prototype's
demo-state switcher sat there too; it is a prototype affordance and is not
built.

## The history of tasks

`components/SessionMenu.tsx` is handoff section 7: `GET /api/sessions` in two
groups — `Открытые задачи`, then `Закрытые` — split on `status` and on nothing
else. The order inside a group is the server's own, most recently updated first
([04-domain.md](04-domain.md)), so the split is a filter and never a sort. A
group with no rows is not drawn: an empty heading promises rows that are not
coming, and a root where nothing has been closed yet is the ordinary state.

A row is a container with two targets, the way a thread card is: the readable
body is one button that moves **this window** to the task, and the status
gesture is its own button beside it. A button inside a button is neither valid
markup nor reachable from the keyboard, and the row has two things to do.

### Two chips about where the task is, and why they are not one

`ЭТО ОКНО` is the task this window is showing — `store.session.name`. `CLI` is
`SessionSummary.current`, the pointer a terminal beside the window uses without
`--review`. **They are different facts and neither implies the other:**
switching a task in the menu moves this window's address and leaves `current`
where the human put it ([ADR-010](../adr/adr-010-review-task-scope.md), decision
7), so the reader is on one task while the command they type answers about
another. One chip for both would be wrong about one of them.

The pointer is not written `CURRENT`. In a list of tasks that word reads as "the
main one", and there is no main task — decision 7 again — so it is labelled as
what it is, with the sentence behind it in a `visually-hidden` span rather than
in a `title` alone: a `title` on a span is reachable by a pointer that hovers it
and by nothing else, while a screen reader announces the text of the button the
chip sits in. Both chips on one row is an ordinary state.

### The scope on a row, and the number beside it that is not the same number

The scope chip is `historyScopeLabel` in `src/ui/scope.ts` — `countScope` and
`scopeLabel`, the same two the `SCOPE` pill uses, plus `все репозитории` for a
session with no scope. The pill has no state for that session, because the whole
root is not a narrowing and there is nothing there to manage; a row has to say
what *every* task is about, so this is the one place the state has words.

The metric beside it says `N repos changed` and **not** `N repos`, and the two
numbers are about two different things:

| on the row | what it counts | where it comes from |
| --- | --- | --- |
| `2 repos · 5 files` | what the task **is about** | `scope` as it is written: an entry is a repository, the paths an entry names are its files |
| `1 repo changed` | what **had changes** at the last scan | `SessionSummary.repositories`, the length of `diff.json`'s repository list |

They agree while every repository of the scope is changing and **separate the
moment one stops** — a file the task is about that has gone back to what it was
is kept by the scope and not shown by the screen, which is decision 5 of
ADR-010 and an ordinary state rather than a defect. One word for both would read
as a contradiction on exactly that row, which is why the metric carries its
predicate. Do not reconcile the two numbers: they answer different questions,
and making them equal would mean either dropping the scope from the row or
counting the scope by what is currently changing.

Both sides of the row inflect: `1 repo · 3 files` beside `1 repo changed`, never
`1 repos`. The numbers are about different things; the grammar of the word they
share is not, and a singular next to a plural of one word reads as a defect
whatever the two are counting. A row that has never been scanned prints
`— repos changed`, because nothing has been counted rather than nothing found.

### Closing a task, and what the mark in the header is

`setTaskStatus` posts to `POST /api/sessions/:name/close` or `/reopen`. The name
is in the path, so `onTask()` is **not** used here: the row names its own task,
which is not always the task this window is on, and neither route moves
`current` ([07-server.md](07-server.md)). Nothing in the request says who is
writing — the server signs with `config.user` and `role: human`, and only a
human ever closes a task (ADR-010, decision 3). Closing is a marker and not a
lock: a closed task still takes comments, replies and resolves, and the same
press opens it again. That is why the button is a ghost and not the red
`primary` of the scope editor's confirmation, and why there is no dialog in
front of it — the one press that destroys review data is still the only one that
asks.

After the write the list is read again rather than patched, so the row moves
between the groups on what the disk now holds and its counters come from the
same read. When the closed task is the one this window is on, the answer's
`Review` replaces `session` as well: the screen would otherwise go on saying
`open` about a task the reader has just closed.

The header's mark is `historyMark`, raised by `sessions-changed` in `live.ts`
and cleared by `setSessionMenu(true)`. **The event is answered with a mark and
with nothing else** — no toast, no switch, no read of the review, and nothing
that scrolls the column or closes an open composer. A task somebody else made is
worth knowing about and is not worth taking the screen for; the reader opens it
when they are ready (ADR-010, decision 4). The list is not read again under an
open menu either: the mark is what says the rows are stale, and a row appearing
under the pointer is a press landing on the wrong task.

The page's own writes raise no mark. `selfWrites` in the store is the map of
"this frame is my own write coming back", keyed by **the kind of frame and the
session name** rather than by the name alone. One write can produce two frames:
closing the *current* task rewrites metadata the watcher compares and a status
the session snapshot compares, so `session-changed` and then `sessions-changed`
both arrive ([05-watcher.md](05-watcher.md)), and a mark is claimed once. With
one key the first frame would take it and the second would either read the whole
review again or raise a mark about the reader's own press.
`tests/ui-live.test.ts` holds both kinds apart.

## The scope editor

`components/ScopeEditor.tsx` is handoff section 12: an overlay over the **whole
root** with a tick per repository and per file, the count of what is picked, and
`Apply`. It is opened from the `SCOPE` pill and from nowhere else.

It shows what the task is not about, which nothing else on this screen does, and
that is why it is an overlay rather than a mode of the tree: a scope cannot be
widened from a tree that already hides what is missing
([ADR-010](../adr/adr-010-review-task-scope.md), decision 2). Its list is
`GET /api/sessions/candidates`, read every time it opens — a repository that
started changing while the page was open belongs in it — and its own header says
out loud that this list is the root and not the task, because everywhere else on
the surface the opposite holds.

The draft is `ScopeDraft` in `src/ui/scope.ts` and not a `Scope`: a picker has a
state the format has not, a repository with some of its files ticked, and the
mark for it (`◆`) is drawn and never written. A repository ticked whole is
`paths: null`; unticking one of its files turns the entry into the list of the
files it keeps, because "everything but that one" is not an entry the format
has. `draftToScope` sorts the entries and their paths by code point, so the same
picks write the same `review.json` whatever order they were made in, and
`tests/ui-scope.test.ts` checks what it produces against the domain's own
`assertScope` — a picker that could build a scope the format refuses would be a
picker whose `Apply` fails at random.

`Apply` calls `PUT /api/sessions/:name/scope` with the whole list and no
consent. Whether it needs consent is not the page's judgement: the server counts
the comments anchored under what is being removed and refuses with a 409 that
names them and writes nothing.

### The confirmation

The 409 becomes the one question in the product that stands in front of
destroyed review data:

> Убрать `repos/platform/loads-search/src/Tariffs/TariffService.cs` и удалить
> 3 комментария (1 открыт)?

What is being removed is `removedFrom(before, after)` — a repository the new
scope has not, and a path an entry no longer names, each written with its
repository, because two files of the same name in two repositories are
otherwise the same sentence. The count is the server's own, and how many of
those are open is read from the threads this page is already holding, which are
the very comments the ids name. The confirmation offers `Отмена` and
`Убрать и удалить`; that second button is the only red primary in the product
(`DESIGN.md`, Danger).

It **replaces** the editor rather than opening over it. Only one overlay is on
screen at a time (see [Overlay and toast](#overlay-and-toast)), and the draft
survives because it lives in the store: `Отмена` and `esc` put the editor back
with the list the reader had built. Answering the question applies **the scope
the question was asked about** and not the draft as it then stands — the consent
was given for that list.

Cancelling writes nothing, and nothing had been written: the refusal that raised
the question left both `review.json` and `comments.json` where they were.
Confirming sends the same scope with `dropComments: true`, and the scope and the
comments go in one write under one lock ([04-domain.md](04-domain.md)). This is
the only place in the product that destroys review data, and it never happens
without this dialog.

### Select mode

The `select` tab of the sidebar turns the tree into a picking surface: the same
rows, with a tick each, clicking to pick instead of to jump, and the caret still
collapsing a branch. At the foot of the sidebar a bar says what is picked in the
same words the pill uses and carries `Clear` and `New task…`, which asks for a
name and a base and creates the session with that scope in one write
(`POST /api/sessions`).

It picks from the **tree** — this task's own change set — rather than from the
whole root, because widening is the editor's job and this is how the review a
person is reading becomes the next task. Outside the mode the tree is exactly
what it was: reading is the main scene and the ticks are not there the rest of
the time. The draft is dropped when the window moves to another task, since what
it held were files of a review that has left the screen.

## Commenting

The composer of handoff section 2 opens where the finding is: a strip inside the
diff, under the last line of the range it is being written for. It is a widget
row of the library's table, so it is as wide as the diff; the block inside it is
`position: sticky; left: 0` and stays in reach wherever the card has been
scrolled sideways to, the way the hunk header does.

A selection starts on `mousedown` over the new column, grows on `mouseenter`,
and is fixed by `mouseup` on the document — the button is often let go outside
the card it started in. Shift-click widens a range that is already there.
The old column of a split view starts nothing, and neither does a cell with no
line on the new side; the unified view has one column and names no side, so it
is read the same way. While a drag runs, `.app` is `user-select: none`, so the
code is not selected as text underneath it. The range is drawn with `--accBg`
and a 3 px `--acc` bar through the library's own `selectedChanges`.

A comment attaches at one of four levels, and the level is read from what is
absent (`docs/SPEC.md` section 7). Each opens the same form, in the place that
belongs to it:

| Level | How it is opened | Where the form appears |
|---|---|---|
| a line, or a range of them | a drag, a click, shift-click to widen, or `C` on the first line the change set adds to the file being read | inside the diff, under the last line of the range |
| a file (`line` null) | `Comment on file` in the card header | under the card header |
| a repository (`path` null) | `Comment on repo` in the repository header | under the repository header |
| the whole review (`repo` null) | `Comment on review` in the session menu | at the top of the reading column |

A card that is collapsed when its form opens stops being collapsed: `C` and the
header's own button can both be pressed on one.

The form proposes `warning` and the reviewer may pick another of the four
(`docs/SPEC.md` section 5); the `AUTO` chip of the handoff and the suggestions
from history are the model's and arrive with DA-36. `⌘⏎` sends and `esc` closes,
both from wherever the focus is — the field is exactly where the reviewer is
when they send. `Comment` posts to `POST /api/comments` with the anchor and the
severity; the server fills the anchor's context from the change set and signs
the comment with `user` from `config.json` and `role: human`
([07-server.md](07-server.md)). The comment the response carries goes into the
store at once, so the badge and the counters move before the next read, and a
toast names the file it was written to. A refusal leaves the form open with the
server's own sentence in the toast.

A card the reader is writing in is not unmounted, whatever the intersection
observer says: virtualisation may not take the lines out from under a drag or a
composer ([ADR-008](../adr/adr-008-diff-rendering-verdict.md)).

## Threads

A thread is one card (`components/ThreadCard.tsx`), drawn the same in both
places it appears: in the rail, and as a widget under the line it is anchored
to. `scope` is the only difference — the rail's `Review` tab opens the header
with the repository, which on the file's own tab would be the same word on every
card. That name is a target of its own and jumps to the repository's section,
with the `revealCard` the tree jumps with. It is a button beside the one that
focuses the thread rather than text inside it, and it is first in the row for
that reason: the focus click owns everything else in the header — the chip, the
anchor, the state and the space between them — in one piece, so pressing any of
them focuses the thread, as pressing the whole header did before the repository
became a target. The card carries the severity chip, the anchor, `awaiting` or
`RESOLVED`, the body, the replies coloured by role — an agent's on `--accBg`,
a human's on `--panel2` — `Resolve` / `Reopen`, `Reply`, and the author with a
relative time. `orphaned` and the `auto` / `labelled by` markers of handoff
section 3 belong to the phases that produce them: re-anchoring (DA-43) and the
model (DA-36).

**The open reply field is the one place the two copies are not interchangeable.**
`replyId` names the thread and `replyAt` names which copy `Reply` was pressed on,
and only that copy draws the field; the card takes a `place` — `widget` or
`rail` — which is not its `scope`, because both copies of a thread on the file
being read are `scope="file"`. Without it both drew a field, both textareas
focused themselves as they mounted, and the rail's won because it comes later in
the tree: pressing `Reply` under the line sent the caret and the scroll to the
right column while the field under the line sat open and inert, and a screen
reader found two controls labelled `reply` for one thread (DA-94). The field
stays where the reader pressed `Reply`, which is the composer's rule as well. A
thread with no widget — anchored to a line a collapsed hunk hides, or to the
whole file, which has no row to sit under — is drawn in the rail only, and opens
its field there.

The rail has the two tabs of handoff section 1.5 with their counts — the open
threads of the current file, the open threads of the review — and the
`unanswered` chip, which is the domain's own `isUnanswered`: an open thread
whose last message is a human's. The tabs count what is still to be done, like
the header's counters, the tree's badges, and the card's own badge; threads are
*listed* whatever their status, and a resolved one stays where it was at
`opacity: .55`.

Focus runs both ways. Clicking a card's anchor in the rail sets `focusId`, makes
its file the current one, brings the card into view, and then scrolls the page —
and only the page — to the widget under the anchored line; `scrollIntoView`
there would also take the card sideways and leave the reader looking at a diff
whose left column has slid out of it. From the diff back to the rail, the header
of the widget under the line does the same: it is the same card and the same
`focusId`.

A thread anchored to a line a collapsed hunk hides has no row to sit under: it
gets no widget, no marker, and no height in the card's estimate, and it is
reached from the rail, which lists it either way. Asking for it there shows that
hunk's context again and then scrolls to it, rather than leaving the click with
no answer.

A line that carries threads is marked with a bar in its gutter in the colour of
the worst open one, as the handoff draws it — a class on the row from
`generateLineClassName` and a `box-shadow` in the stylesheet. The bar is a
marker and not a control: an element drawn per *cell* through `renderGutter`
cost about a millisecond of the 8.3 a scrolled frame has, which is a ninth of
the budget for a second way to press what the widget right underneath already
does.

A widget on an added line lands in the new side's half of the split table:
`react-diff-view` gives a cell across the whole row only when both sides carry
the same node, and an insertion has no old side. The row is put back across the
whole diff in CSS, which is both what the handoff's strip is and what gives the
block inside it the width to stick to the left edge over.

`Reply`, `Resolve` and `Reopen` all go through one `write()` in the store: the
card changes before the server has been asked, the answer replaces it, and a
refusal puts the thread back as it was **before this write** — not before
everything that has happened since — and says why in the toast. What is rolled
back is that one comment and not the whole list, and `busy` is a set of thread
ids rather than one flag: a reply on one thread and a resolve on another are two
writes, and neither the refusal of one nor a press on the other may be swallowed
by the first. A reply is drafted under `user` from `GET /api/config`, which is what
the server will sign it with, and the field closes only once the reply is really
there. Only a human ever resolves through this server
([ADR-004](../adr/adr-004-agent-contract.md)).

**A live frame that lands during a write cancels the rollback.** `patchThread`
counts the frames each thread has taken and `write` reads that count on both
sides of its request; overtaken, the refusal drops the rollback and keeps what
the frame brought. That is not a compromise between two truths: the frame is the
server's own read of the thread and replaced the whole comment with it, the
optimistic draft included, so there is nothing left to undo and restoring the
object the write started with would delete the agent's reply from the rail, the
counters and `awaiting` — while the toast talked about the reader's own failed
reply, so nothing on screen said one had gone (DA-93).

`patchThread` deliberately has no `busy` guard, unlike the two writers beside
it. A live frame is the server's truth and the store takes it; what the guards
protect is a second *write* on a thread already being written, which is a
different question.

A card carrying threads claims their height before it has ever been mounted, the
way it claims the height of its diff: `measureThreads` counts the parts
`styles.css` fixes — the borders, the padding, the header, the actions row — and
the lines the body wraps to at the block's width. Without it the scrollbar
drifts by more than the two per cent the diff test allows.

Each widget is `contain: layout paint style`. It sits inside the same
`table-layout: fixed` table as the diff, and without containment a card's own
layout and paint are the table's: measured on the synthetic review that was
8.7 ms of CPU per scrolled frame against a budget of 8.3, and it is 7.8 with it.
That is the same reason the marker is a class on the row rather than an element
in the cell.

## Live update

The page holds one `EventSource` on `GET /api/events` for as long as it is open
(`live.ts`), and what arrives is a name and an id — never the data. The client
fetches what an event names and patches the store; the review is read again only
when an event says to ([ADR-005](../adr/adr-005-live-update.md)).

Reconnecting and `Last-Event-ID` are the browser's own and are not implemented
here: `EventSource` retries a stream that dropped and sends back the id of the
last frame it saw, which is the reason ADR-005 chose SSE over a socket. What the
client adds around that is the `reload` frame — the ring can no longer reach
back, so nothing it holds can be repaired event by event and the review is read
again — the connection state, and the ring of activity lines read from
`GET /api/activity` on every open and merged by id, so a page that has just
connected does not start with an empty feed and a reconnect does not double it.

| Event | What the page does |
|---|---|
| `diff-changed` | fetches `GET /api/repos/:repo/diff` and patches that repository; a 404 is the repository leaving the review |
| `comment-added`, `comment-status` | fetches `GET /api/comments/:id` and puts the thread in place — unless `session` names a task this window is not on, which is dropped unread |
| `reply-added` | the same, and a reply whose role is `agent` also raises a toast |
| `session-changed` | reads the review again when `name` is the task on screen: the change set and every comment are another session's — unless this page's own write caused the frame |
| `current-changed` | a window with no `?review=` reads the review again, because the pointer is what it shows and writes to; a window on a task of its own does nothing |
| `warnings` | the list the frame carries replaces the bar's, under the rule below |
| `activity` | one line appended to the feed |
| `reload` | reads the review again |

Every handler runs in one queue. Two events that arrive together are two
patches, and a patch that read the store while another was halfway through it
would write back a state that never existed.

A page's own session writes — `use`, `new`, a change of base — come back through
the watcher like anybody else's, and the review they name has already been read
by the time they do. The store keeps the sessions it has just written, with the
moment of each, and the stream takes the matching entry instead of reading
megabytes a second time. It is a map rather than one name because two switches
in a row are two writes in flight, and each entry carries its age because a
write does not always produce a frame: a switch away and back inside the
watcher's debounce leaves `current` where it was and emits nothing, and a mark
left behind for ever would swallow the next real event for that session.

### Patching, not repainting

The handoff forbids repainting a file card on an update: only the affected lines
and threads change. That is what `patch.ts` is for. A repository's new change
set is merged into the one the page holds file by file — a file whose patch,
status, counts, and omission all say the same thing keeps *the object* it was
rendered from, so `FileCard`, which is memoised, does not re-render and its DOM,
its tokens, and the reader's place in it survive. A repository in which nothing
changed at all comes back as the object it already was, so a watcher that woke
on a file the change set does not carry costs the page nothing.

Hunks are compared the same way: a hunk is the same hunk when its `@@` header
and its body are both unchanged, and the headers of the ones that are not go
into `changed`, keyed by `<repo>/<path>`, with the moment they arrived. The
renderer gives such a hunk the accent border and `updated 12s ago`, recounted
from one clock in the store that moves every five seconds — the same clock the
activity panel's relative times are read from. One timer for the page, and only
a hunk that changed subscribes to it.

### The reading position and the open form

Every patch is bracketed by the scroll anchoring: the narrowest element under
the probe just below the header is measured before the state is set and put back
where it was once the patch is on the page. Content that grew above the reader
would otherwise push what they are reading down the page by the difference.

**"Once the patch is on the page" is not "after the next frame", and the
difference is the whole of DA-55.4.** A store write only schedules React's work.
Under load React can land it after the one frame `settle()` used to wait for,
and a measurement taken then reads an unchanged DOM: the delta is nothing, no
correction is issued, and the growth arrives when nobody is looking — the
reader's place lost by the whole of it, which is the `44` of two diff rows the
e2e assertion caught once in six runs. So the anchor is watched over up to four
frames: a move is corrected and ends the wait, and a frame where nothing moved
ends it only if the page's own height has already changed, which is what tells
"the patch landed and did not touch anything above the reader" from "the patch
has not landed yet". A patch that changes neither the height nor the anchor —
an edit of the same size, below the reader — spends the whole budget doing
nothing, which is four frames and no scroll.

A reader who scrolls while this is waiting ends the wait untouched: `capture()`
records `window.scrollY` with the anchor, and a page that has moved by something
other than the correction is the reader's own doing, not the patch's. Taking
that back out would be the page fighting them.

`window.__perf.settles` is the record the fix was found with, and it stays. Each
correction reports the delta, the page's height before, **at the first frame**,
**at the frame the loop stopped on** and after, and `grewAfter` — the growth
that arrived after the loop finished, counted from `heightAtEnd`. Counting it
from the first frame instead would make it non-zero exactly when the loop had
done its job, which is the opposite of the property: a late commit means frame
zero is short and the stopping frame is not. `heightAtMeasure` stays for
diagnosis, and `heightAtMeasure !== heightAtEnd` is what says the commit was
late.

**`corrected` is the stronger half of the record, and the numbers say so.**
Forced in a browser by delaying the store write past the frame, the one-frame
wait moved the reading position on 30 samples out of 30 and reported
`corrected: false` on all 30 — but `grewAfter` was non-zero on only 17, because
on the rest the growth had not landed even by the record's own extra frame. The
loop under the same forcing holds the position on all 30, with `corrected: true`
and `grewAfter: 0`, and `heightAtMeasure` short of `heightAtEnd` on every one.

The composer is left alone unless the patch is of its own file, and then it is
re-validated: its line has to still be on the new side of the diff. When the
edit took that line away the form does not vanish — the renderer keys it to a
row of the diff and would simply stop drawing it — it drops to the file anchor,
which every file has, keeping what has been typed, and says so in a toast.

### The activity panel and the footer

`components/ActivityPanel.tsx` is handoff section 4 at the foot of the rail:
collapsed by default, a header saying how many agents wrote or edited inside the
two-minute window the watcher attributes changes for, and the lines newest
first with their times in seconds. The verbs are the watcher's — `changed`,
`editing`, `replied`, `commented` ([05-watcher.md](05-watcher.md)) — and the
sentence around each one is written here. The sidebar footer says what the
stream is doing: `watching` with the living dot, `reconnecting` while the
browser is retrying, `connecting` before the stream has answered. It answers at
once: the server writes a comment line as soon as it has subscribed the client,
so `onopen` is the moment the connection is made rather than the moment the
first heartbeat happens to land ([07-server.md](07-server.md)).

## The keyboard map

`keys.ts` is the handoff's table in one listener on the document. What each key
does is an action of the store, so the map is a list of names and not a place
where behaviour lives, and the same action is reached from the pointer as well.

| Key | What it does | Where |
|---|---|---|
| `⌘K` / `Ctrl+K` | opens and closes global search | `setPalette` |
| `⇧⇧` | the same, two presses inside 400 ms; in a field only inside the modal it closes | `setPalette` |
| `⌘K` / `⇧⇧` over another overlay | refused: one overlay at a time | `overlays.ts` |
| `↑` `↓` `⏎` in search | move the selection, open the hit | the modal's own field |
| `J` / `K` | the next and previous open thread of the whole review | `stepThread` |
| `C` | the composer on the first added line of the file being read | `commentOnCurrentFile` |
| `R` | resolves the focused thread | `resolveFocused` |
| `B` | says that browsing a repository is Phase 2 (DA-37), and does nothing else | `setToast` |
| `[` / `]` | takes the sidebar and the thread rail off the screen, and brings them back | `toggleSidebar`, `toggleRail` |
| `⌘⏎` | sends the comment being written | `submitComment` |
| `esc` | closes the topmost thing that is open | `overlays.ts`, then `openReply`, `closeComposer` |

Two rows of the handoff's table are not in this listener and are not meant to
be: `⏎` and `Space` on a repository row belong to the row, which is the only
place that knows which repository the focus is on. They are the tree's own keys
rather than the document's (`components/Sidebar.tsx`).

Three rows of the handoff's table are not wired, and each one is waiting for the
thing it acts on rather than for a key: `↑` / `↓` and `TAB` in the composer move
through the suggestions from the reviewer's own history, which are Phase 2
(`docs/SPEC.md` section 5; DA-35), and `⏎` in the base picker belongs to the
picker, which owns its own field.

`esc` closes in one order and stops at the first thing it found: the overlay
ladder of `overlays.ts` — search, the scope's confirmation, its editor, the
new-task form, the base picker, the export, the sessions menu — then an open
reply field, then the composer. Without the order one `esc` over the search
modal would also throw away the comment being written under it.

A letter typed into an `input` or a `textarea` is text and not a command, which
is the handoff's own rule. Its exceptions are `⌘⏎` and `esc`, which are commands
wherever they are pressed — the field is exactly where the reviewer is when they
send — and `⌘K`. `⇧⇧` is not among them: it is not in the handoff's list, and a
person typing capital letters into a comment is not searching.

`J` and `K` walk the *open* threads of the whole review in reading order — by
repository as the centre panel lists them, then by file inside it, then by line,
with the anchors that have no line first in their scope — and wrap at both ends.
Focusing a thread makes its file the current one, so the rail follows on its own
and the diff is scrolled to the widget by the same `revealThread` a click in the
rail uses.

## Global search

`⌘K` opens the modal of handoff section 6: 880 px by 60 vh over the scrim, the
field with the focus, the results on the left and the preview of the selected
one on the right. It covers what the MVP has — the files of the change set and
the comments of the session. Of the handoff's five tags two are drawn: unchanged
files come with browsing (DA-37), text search with the index (DA-38) and symbols
with tree-sitter (DA-39), all Phase 2 (`docs/SPEC.md` section 3, decision 13),
and `orphaned` is not a status the on-disk format carries yet.

Ranking (`search.ts`) is substring first and word overlap second, which is what
a path and a sentence both answer to: the whole query inside the target scores
most, more again when it starts at a path segment or a word, and each word of a
multi-word query that appears anywhere adds to it. Ties are broken by the path,
so the same query always lists the same rows in the same order.

The preview is twelve lines of the file's own patch around the target, the
deletions kept in place beside what replaced them, the target line on `accBg`
with the accent bar and added lines on `add`. A file has no target of its own
and centres on its first change, which is what the person searching for a path
came to look at; a comment centres on its line and its body is under the code.
The pointer selects as well as opens, so moving over the list moves the preview.

`⏎` on a file selects it and scrolls to its card; on a comment it focuses the
thread and brings the diff to its widget — the same path `J` and `K` take.

## Reaching a card

A jump to a card — from the tree, from a thread — scrolls, waits for a painted
frame, and scrolls again (`reveal.ts`). A card that has never been
mounted holds its place with a height counted from its patch, and every card
around the target swaps its estimate for its real height the moment it mounts,
which moves the target out from under the reader after the jump has already
happened. On the small fixture that was a whole file's worth of drift, and the
current file the rail follows was the wrong one within 120 ms of the click. The
first scroll is synchronous, so the jump is still one frame and inside the 50 ms
budget; the rest only correct it.

A repository is reached the same way and by the same function: the name in the
tree and the repository on a thread card both call `revealCard` on
`[data-repo-section]`, and `revealThread` already used it for a comment on a
whole repository. `.repo { scroll-margin-top: 52px }` is what puts the section's
top under the header, which is where its bar then sits — the bar is the top of
the section, so a jump lands on the bar rather than behind it.

## Virtualisation

A file card mounts its diff when an `IntersectionObserver` with a margin of
1000 px reports it near the viewport, and unmounts it when it leaves. Before a
card has ever been mounted its height is counted from the patch (`measure.ts`):
one row per hunk header, one per context line, and per block of changed lines
`max(deletions, insertions)` rows in split view or their sum in unified. The row
heights are fixed in `styles.css` — 22 px for a line, 26 px for a hunk header —
so the count is the height, and the scrollbar does not drift while unseen files
are scrolled past ([ADR-008](../adr/adr-008-diff-rendering-verdict.md)). Once a
card has been mounted the measured height is kept instead. The arithmetic has
its own unit test, and a Playwright test scrolls the whole small fixture and
checks that the page height it ends with is within two per cent of the one it
started with.

The card's own horizontal scroll exists only while the card is mounted: three
hundred empty scroll containers cost the compositor a frame it does not owe.

Virtualisation is what makes the budgets reachable
([ADR-008](../adr/adr-008-diff-rendering-verdict.md)); the handoff allows it as
long as drag selection and thread anchors keep working, which the Phase 1 tasks
must hold up.

## Measurement hooks

`perf.ts` exposes `window.__perf` for the harness. Every duration ends at a
painted frame — `requestAnimationFrame` followed by a `setTimeout(0)`, which
runs after the paint — not at the end of a React commit.

| Member | What it reports |
|---|---|
| `responseAt`, `firstRender` | when the review response was parsed, and the milliseconds from there to the frame that showed it |
| `longTasks` | every long task since the page opened, from `PerformanceObserver` |
| `scrollRun(step, maxFrames)` | scrolls the whole review one step per frame; returns frames, duration, distance, and the long tasks of that window |
| `openComposer()` | opens the composer placeholder and returns the milliseconds to the painted frame |
| `jumpToFile(index)` | scrolls a file card into view and returns the same |
| `liveUpdate` | the repository whose new diff was painted last, and the wall clock of that frame |

The hooks ship in the page rather than in the harness because only the page
knows when a frame it caused has been painted; they cost nothing when the
harness does not call them.

`responseAt` is stamped by the store the moment the response is parsed, right
before the state is set, so the first-render number is the distance from the
data to the frame that showed it.

`liveUpdate` is the other end of the live-update budget and is stamped in
`Date.now`, not `performance.now`: the harness edits the file from another
process, and the two ends of that 300 ms have to be on one clock. The harness
scrolls the card into view first and looks for the edited line in it afterwards,
so what the number covers is a diff on the screen and not one held in the store
([11-perf.md](11-perf.md)).

## TypeScript configuration

The UI is browser code and the rest is not, so they are checked apart:

| Config | Covers | `lib` | `types` |
|---|---|---|---|
| `tsconfig.json` | `src/core`, `src/cli`, `src/server`, `scripts` | without `DOM` | `node` |
| `src/ui/tsconfig.json` | `src/ui` | with `DOM` | none |
| `tsconfig.tools.json` | `tests`, `perf`, `e2e` | with `DOM` | `node` |

TypeScript project references: a referenced project may not disable emit
(TS6310), and every project here is `noEmit`.

`Change base` → `Apply` with a base that brings changes leaves the ring on the

What such a root answers is the server's own test.

The live update is checked with the writes coming from where they come from in
the product: `diffalanche reply` in a shell reaches the rail, raises

The Vitest half needs no browser: `tests/ui-anchor.test.ts` for where `C` opens

The header is checked for the menu creating a session that `diffalanche list`

A spec that changes the fixture puts it back, in `afterEach` and not at the end
of the test, so an assertion that failed half way cannot hand the next spec a
fixture sitting on a session it invented. Through the API rather than the CLI,
because the server holds the review document until one of its own write routes
drops it and a CLI write is only noticed when the watcher gets round to it.

**The sidebar footer is masked in both screenshots.** It prints
`127.0.0.1:<port>`, and since the suite stopped holding a fixed port — see the
port collision below — those four digits differ every run: 33 pixels of a
1.4-megapixel baseline, enough to fail both shots and nothing a reader would
spot. It is masked for the same reason `/api/activity` is stubbed in `open()`:
a baseline may only carry what does not vary. Nothing is lost by it, because the
footer's text is asserted directly in six specs, `shell.spec.ts` among them.

The baselines are per platform, and the ones in the repository were taken on
macOS: a baseline taken there is not the pixels a Linux runner draws. That is
why CI runs `bun run test:ui:ci`, which is the same suite with
`--ignore-snapshots` — every spec of `shell.spec.ts` still runs, and only its two
screenshot comparisons are left to the gate on a developer's own machine.

**The suite is a gate and a CI job both** (DA-54.2). `bun run test:ui` is the
sixth of the seven entries of `gates` in `backslop.json`, between
`bun run test:bun` and `bun run perf` — the two browser gates adjacent, so a machine that serialises
them serialises one window and not two — and the `ui` job of `ci.yml` runs
`test:ui:ci`. Before that the ninety-five tests here ran only when somebody
typed the command, and a UI regression reached the main branch through six green
gates and a green CI. A CI job alone would have been the weaker half: a gate is
what a worker runs before reporting, and CI answers after the work is handed
over.

The collision with the acceptance suite is handled structurally rather than by a
rule somebody remembers. The two share `dist/` — see [the acceptance
suite](#the-acceptance-suite) — and they never meet: each worker has a worktree
of its own and therefore a `dist/` of its own, `backslop gates` runs its
commands one after another, `bun run test:e2e` is not among them, and in CI the
two are separate jobs on separate runners.

**The second collision is the port, and a gate is what made it one.** A worktree
per worker separates `dist/`, but the loopback interface is the machine's and
not the worktree's. This configuration held a fixed 4881 with
`reuseExistingServer: false`, which is right for one person running the suite by
hand and wrong the moment two workers on one machine run the gate at the same
time: the second gets `port is already used` and a red gate with nothing behind
it. It now asks the operating system for a free port the way
`acceptance.config.ts` does — a child process binds port 0 and prints what it
was handed — pins the number in `DIFFALANCHE_UI_PORT` so the workers Playwright
forks inherit it rather than choosing a second one, and passes it to
`e2e/server.ts` as `PORT`. Setting `DIFFALANCHE_UI_PORT` by hand pins the port
for a debugging run, as `DIFFALANCHE_E2E_PORT` does for the acceptance suite.

One measured cost, stated because it is paid on every report: the command takes
71–78 seconds, which is the UI build, the small fixture, the server, and the
ninety-five tests together — not the tests alone. And the suite is about time,
so a busy machine can redden a live-update spec that a quiet one passes; that is
DA-54.4, and until it closes the rule is the one `perf` already follows — prove
the red with a re-run on a quiet machine and a run on the base commit, or it is
yours.

## The acceptance suite

`e2e/acceptance.spec.ts` is the acceptance list of `docs/SPEC.md` section 10 in
executable form: one named test per line of it. `bun run test:e2e` runs it, over
its own configuration, `e2e/acceptance.config.ts`.

It runs against **the binary**. The web server command builds the target of the
machine it is on, makes the fixture, and serves it:

```
bun run build -- --target current
rm -rf .perf/acceptance
bun e2e/fixture.ts .perf/acceptance
./dist/diffalanche-<platform>-<arch> serve --root .perf/acceptance --port <free>
```

and every `diffalanche` the tests shell out to is that same file. The acceptance
list is about the artefact that ships, so a suite that ran the sources would be
checking something else. `bun run test:ui` keeps its fast path — the sources,
the dev server, no binary. Both configurations scan the same directory, so each
names the other's file: this one matches only `acceptance.spec.ts`, and
`playwright.config.ts` ignores it.

The two have their own fixture and their own port, and they still cannot run at
the same time, because they share `dist/`. `scripts/build.ts` empties that
directory before it builds, and the dev server serves `dist/ui` from disk on
every request: starting `test:e2e` under a running `test:ui` takes the page away
mid-suite, and `build:ui` under a running `test:e2e` replaces the chunks the
loaded document names. Run them one after the other.

The port is a real free one, asked for by binding port 0 in a child process,
because a Playwright configuration is read synchronously and cannot await a
listener. The number is put in `DIFFALANCHE_E2E_PORT` the first time the file is
read, and the workers Playwright forks inherit it rather than choosing a second
one. Setting that variable by hand pins the port for a debugging run.

### The fixture

`e2e/fixture.ts` calls `generate()` of `scripts/synth.ts` with the small
profile, and adds the one repository section 10 asks for that the generator does
not make: `repos/tools/tariff-store`, cloned from `sources/tariff-store-upstream`
— outside `repos/`, so no scan finds it — checked out on `feature/rounding` with
one commit ahead of `origin/main` and a clean working tree. In `head` mode it
has nothing to show and is not in the review; in `branch` mode it is the whole
of what that branch committed. That difference is what the `branch` criterion
reads.

That repository also holds the second half of the nesting criterion: a worktree
checked out *inside* it, at `nested/inner`. The generator's submodule covers a
submodule nested in a repository, and this covers a worktree nested in one —
section 10 forbids both. It is ignored by the repository that holds it, so the
clean working tree the `branch` criterion needs stays clean. What the test
asserts is the outcome — nothing under the holding repository is listed under
any name — not the mechanism: in the `repos/<group>/<repo>` layout the scan's
depth limit and its rule of not descending into a found repository stop at the
same point, so the fixture cannot tell them apart.

All of it is the acceptance fixture and not the generator's profiles, because
those profiles are what the performance gate measures: a repository added there
would move the gate's numbers to prove something the gate does not check.

### The criteria and the tests

Each line of section 10 that involves the UI has a thin test here that asserts
the sentence, and the spec that owns the screen behind it covers the behaviour
in depth on the fast path. Both are named:

| Criterion of section 10 | Acceptance test | Covered in depth by |
|---|---|---|
| every repository with changes is listed | `serve lists every repository with changes` | `sidebar.spec.ts` — the tree lists the repositories with changes, and only those |
| a sibling worktree is its own repository | `a worktree checked out as a sibling directory is its own repository` | `tests/scanner.test.ts` — lists the sibling worktree as its own repository and warns about it |
| a nested submodule **or worktree** is not listed | `a submodule or worktree nested inside a repository is not listed` | `tests/scanner.test.ts` — does not descend into a repository, so the nested submodule is not listed |
| an untracked file is in the diff | `an untracked file is in the diff` | `tests/change-set.test.ts` — shows an untracked file as an addition |
| `git status` is unchanged after a scan | `a scan leaves git status as it found it` | `tests/git.test.ts` |
| `branch` mode on a feature branch | `branch mode shows what a feature branch committed ahead of the remote default branch` | `header.spec.ts` — the base picker applies a branch and the repository header says so |
| a comment from the UI in `list --json` | `a comment written in the UI is in list --json without a restart` | `composer.spec.ts` — `⌘⏎` sends the range, and the CLI reads back both its lines |
| a reply from `reply` in the UI | `a reply made with reply is in the UI without a refresh` | `live.spec.ts` — a reply written from a shell reaches the rail, the counter, and the feed |
| `resolve` from the UI out of `list --status open` | `resolve in the UI takes the comment out of list --status open` | `threads.spec.ts` — resolve takes the thread out of the open list, and reopen brings it back |
| the reply in the activity feed under its `--author` | `a reply made with reply is in the activity feed under the agent's --author` | `live.spec.ts`, the same test |
| `review use` switches both sides | `review use switches the UI and the CLI at once` | that test is the whole of it: `review use` is a CLI gesture, and since DA-55 it is the only thing that moves `current` — `header.spec.ts` covers the other half, a menu that switches this window and leaves `current` alone |

The lines of section 10 with no UI in them — `resolve` from the CLI without
`--role human`, two CLI processes writing at once, the budget table, the six
binaries — are not here; they belong to the unit suite, the performance gate,
and the smoke matrix.

### Running and debugging it

```
bun run test:e2e                       # the whole list
bun run test:e2e -- -g "branch mode"   # one criterion
bun run test:e2e -- --headed --debug   # with the inspector
```

A run rebuilds the binary. When nothing but the tests changed, the way to skip
that is to serve the fixture by hand and point the suite at it:

```
bun e2e/fixture.ts .perf/acceptance
./dist/diffalanche-darwin-arm64 serve --root .perf/acceptance --port 4890
DIFFALANCHE_E2E_PORT=4890 DIFFALANCHE_E2E_REUSE=1 bun run test:e2e
```

`DIFFALANCHE_E2E_REUSE=1` is what lets a run attach to a server that is already
up instead of insisting on starting one. It is off by default, so an ordinary
run always tests the binary it just built.

Every test puts the fixture back on the session `synth` and the base `head` in
`afterEach`, through the API for the reason the specs above give. A test that
writes a comment leaves it: the fixture is made from scratch by the web server
command, so residue never reaches the next run — which is also why a hand-served
fixture wants regenerating between rounds.

In CI the suite is the `e2e` job of `.github/workflows/ci.yml`, on ubuntu and
macOS ([11-perf.md](11-perf.md)); the criteria and their verdicts land in the
run summary, one row each.
